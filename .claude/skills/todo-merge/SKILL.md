---
name: todo-merge
description: Merges a reviewed todo/<id> branch (left by todo-loop in status review) into the base branch of its repository. Prints a short report of what was done, asks the owner whether to merge, and only after a yes merges with --no-ff, closes the entry in the todo store (as `/todo-loop close` does), deletes the branch and, for an engine branch in a game, commits the moved pointer of engine/. For an engine entry it also writes the changelog fragment and commits it as `Changelog: <title> (<version>)` on the base. Use when the user asks to merge a todo branch, accept the result of the todo loop, says "смержи ветку", "todo-merge", or wants a report before merging a todo branch.
---

# todo-merge

You are the **conductor** and do everything yourself, no agents. The skill takes one branch `todo/<branch-id>` whose entry `todo-loop` left in status `review` in the todo store, shows the owner what it holds, **asks**, and only then touches the base branch. The store and its CLI are `<engine>/tools/todo/CLAUDE.md`; the closing steps are in `.claude/skills/todo-loop/SKILL.md` ("Closing merged entries").

`/todo-merge [<id or branch>]`

The terms `<area>`, `<R>` (repository of the area), `<base>`, `<engine>` and `todo` (`python3 <engine>/tools/todo/todo.py --actor todo-merge`) are the ones of `todo-loop/SKILL.md` ("Areas and the repository rules"), taken from `.claude/rules/todo-project.md`. Read that file first.

**The changelog** (`<engine>/tools/changelog/CLAUDE.md`) belongs to an entry of the **engine** area (in a game, `<R>` = `engine`; in the engine's own repository `<R>` = `.`); an entry of a game area has none. It is **on** for a run when the area is the engine's and `<engine>/tools/changelog/changelog.py` exists on `<base>` (step 4 looks once); otherwise every changelog step is skipped with one line in the report. `<changelog>` is `python3 <engine>/tools/changelog/changelog.py`, `<header>` is `src/Modules/BECore/Utils/EngineVersion.h`.

Run it in the main checkout, the one that holds the base branches; a worker folder of the loop (`worker.py`) cannot switch to them. Before the answer of step 5 you change nothing: only reads, `git -C <R> switch <base>` (the one change to the checkout; step 5 undoes it on `No`), `git merge-tree`, and, after the owner's yes to the question of step 3 (a conflict found by the dry check), the `worker.py remarks` of that step.

## Steps

1. **Preconditions.** Every area repository is clean (`git -C <R> status --porcelain`; in a game the game repository with `--ignore-submodules=all`) and `todo ping` answers; otherwise stop with a message. Remember the starting branch of every area repository. Never `fetch` and never `push`.
2. **Choose the branch.** `git -C <R> switch <base>` for each area. `todo list --status review --area <area> --json` for each area of the rules file (only those: the store also holds other games' entries, `todo-loop/SKILL.md`, "Only the areas of the rules file"). Candidates: entries in `review` whose `branch` is in `git -C <R> branch --list 'todo/*' --no-merged <base>` of their area. Unmerged branches that are not candidates (their entry is `in progress ... stopped`, or open) are only named, with the `statusLine`.
   - A **stacked** branch (its `statusNote` ends with `stacked on todo/<parent>`: `todo-loop/SKILL.md`, "Stacked branches") is a candidate only when its parent is merged: the parent branch is gone or is in `git -C <R> branch --list 'todo/*' --merged <base>`. Otherwise it is named as `waits for todo/<parent>`; merging it first would bring the parent's commits in unreviewed by the owner and under the wrong entry.
   - An entry with an open blocker (a `blockedBy` that is not `closed`: a **paired** game entry waits for its engine entry, `todo-loop/SKILL.md`, "Paired") is a candidate only once the blocker is merged and closed; until then it is named as `waits for <id>`. Merge the engine entry first: its pointer commit is what the game entry was built on.
   - With an argument (`<id>` or `todo/<branch-id>`): take that branch. If it is not a candidate, stop and say why: no such branch, already merged into its base, the status is not `review`, or it is stacked on a parent that is not merged (name the parent: merge it first).
   - Without an argument: one candidate is taken as is; several candidates go to the owner in one AskUserQuestion (area, title, branch, the note of the status); none: say "nothing to merge" and stop.
3. **Dry check.** `git -C <R> merge-tree --write-tree --name-only <base> <branch>`: a non-zero exit code means conflicts; the skill never resolves them and merges nothing. Compare `git -C <R> merge-base <base> <branch>` with the tip of `<base>`: if they differ, "the base moved since the branch was cut" is a flag for the report and for step 6.
   **Conflicts: send the branch back to its worker.** Print, in Russian, the report of step 4 reduced to what the owner needs to decide: the entry, the branch, the conflicting files (the names the `merge-tree` output lists under the tree id), where the branch can be tried (as in step 4), and that the base moved. Then **one** AskUserQuestion: `Send back to the worker (conflict round)` / `No`.
   - `No`: switch every area repository back to its starting branch (as the `No` of step 5) and stop.
   - Yes: `python3 <engine>/tools/todo/worker.py remarks <id> --file - --start`, the text on stdin from a heredoc (no file is written):

     ```
     **Conflict round**
     Merging <base> into todo/<branch-id> conflicts in: <files>. Merge <base> into the branch, resolve each conflict keeping what both sides meant, build, test, and commit the merge.
     ```

     For a stacked branch whose parent is merged since, add one line that `<base>` now holds the parent's commits. The command's answer is reported as it is (the plan name, the worker that holds the branch, whether a session started). When no worker holds the branch or the start is refused, the remarks plan is stored all the same and the report says that the owner starts the round (the panel of `worker.py`, or `/todo-loop <id>`: `todo-loop/SKILL.md`, "Remarks"). Then switch every area repository back to its starting branch and stop: no merge, no close, no delete, no changelog. The developer of the loop resolves the conflicts and the entry returns to `review` with the note `conflict round: <files> resolved`; the next `/todo-merge` takes it.
4. **Report.** In Russian, short, printed before the question:
   - the title of the entry, the area and the branch, and where it can be tried live: the worker folder that has it checked out (`git -C <R> worktree list`; the loops run in worker folders, `todo-loop/SKILL.md`, "Parallel workers"), else the main checkout with `git -C <R> switch <branch>`;
   - if the `statusNote` has `slice K of M, after the merge set the status back to open`: a warning that the merge does not finish the entry (closing sets it back to `open` instead of closing it);
   - what was done and how it was checked: the `statusNote` of the entry;
   - `git -C <R> log --oneline <base>..<branch>` and `git -C <R> diff --stat <base>...<branch>`, plus two to four lines of your own on what changed, from the commit subjects and a look at the diff of the non-test files;
   - from the slice plan (`todo plan get todo-loop-<branch-id>.md --stdout`, if the store has it): "Review notes" (non-blocking findings; the `[followup]` lines are listed apart, with the rolling entry they will go to: `todo-loop/SKILL.md`, "Follow-ups", step 3) and what the architect left for the owner to check by hand, with the link `todo plan url todo-loop-<branch-id>.md`;
   - decisions: the dated decision paragraphs of the entry's body (`todo show <id>`; "Decided by the owner", "Owner decision", "Taken over") in one line each (date, what it decides) and, from grepping the `*.md` of `<R>` and the titles of the open entries for their words, the places that still state a policy a later decision replaced (`file:line` or entry id); `none` when there are none. Reads only: a warning for the owner, never a stop;
   - screenshots: when `~/.claude/plans/todo-loop-<branch-id>-shots/` (a through entry: also `todo-loop-<branch-id>-s*-shots/`) exists, the folder as a `file://` link, the `summary:` line of its `diff.txt` and its changed pairs (the lines that are not `unchanged`), and that the pictures are for the owner's eyes: do not open them. A folder that is not there on this machine (the plans folder is local) is one line, not an error;
   - the `merge-tree` result (clean) and the "base moved" flag;
   - a busy worker, when the repository has workers (`worker.py list` names some, as in step 11): `python3 <engine>/tools/todo/worker.py merge <id> --dry-run` (reads only; it sees the loops) and from its output the `warning:` lines (a worker's loop runs in `<R>` on `<base>` or detached: the merge moves the base under it) and the `problem:` lines that name a loop (`runs a loop on <branch>`: the owner stops it first); the other `problem:` and `conflict:` lines are checks of this skill and are not repeated;
   - changelog on: the **draft fragment** (`tools/changelog/CLAUDE.md`, "Fragments": English, no `Version` and `Date` lines; `Entry` is the entry id) written to the scratchpad as `changelog-<branch-id>.md` and printed. Write it from the entry body, the slice plan, `git -C <R> diff --stat <base>...<branch>` and a look at the diff of the public headers: `Added` and `Changed` for what a game can now use or what behaves differently, `Breaking` for what stops compiling or changes behaviour, each bullet ending `Adapt: <how a game follows>.` (a deprecated name that stays one merge is a `Changed` bullet), `Migration` and `Content version: <kContentVersion of the branch>` when `ContentVersion.h` changed or `tools/migrate/steps/` got a file (the migrate command and the step). Then `<changelog> propose --draft <file>` for the bump, `todo version get` for the counter's current value, and `<changelog> add --draft <file> --bump <it> --version <forecast> --content-version <kContentVersion of the branch> --dry-run`, where `<forecast>` is that value raised by the bump (`patch`: PATCH + 1; `minor`: MINOR + 1, PATCH 0). The report calls it a forecast: the number is given only in step 8, after the owner's yes, and another merge may take this one first; `version next` is never run here. When `version get` fails, dry-run without `--version` for the refusals alone and say that there is no forecast and step 8 needs the service (`--content-version` because `<R>` stands on `<base>` here, whose `ContentVersion.h` still holds the old number; read it with `git -C <R> show <branch>:src/Modules/BECore/Config/ContentVersion.h`, the draft's `Content version` line equals it; step 8 runs after the merge and passes nothing); a refusal of the dry run is shown as it is and the draft is fixed first;
   - for an engine branch in a game: that the answer also makes a separate commit in the game repository that moves the pointer of `engine/`, named `Update engine: <title> (<version>)` when the changelog is on.
5. **Ask.** One AskUserQuestion: `Merge + close + delete branch` (for an engine branch in a game: `+ move the pointer of engine/`), `Merge only (no close, the branch stays)`, `No`. `No` ends the skill with nothing changed: switch every area repository back to its starting branch first, so the owner stays on the branch they were trying. When the full answer is chosen and the changelog is on, a second AskUserQuestion on the bump: the proposed one first, the other as the alternative (`minor` / `patch`; a draft with a non-empty `Breaking` offers only `minor`). `Merge only` writes no fragment.
6. **Merge.** `git -C <R> merge --no-ff -m "Merge branch '<branch>'"` on `<base>` with the Co-Authored-By line the conversation gives (the history uses this form). If the merge fails for any reason: `git -C <R> merge --abort`, switch back to the starting branches, report, stop. If the base had moved (step 3), also build with the preset of `build` and run `ctest --preset <p>` on the result (the targets of the rules file; the default test preset, without the label `extended`, which belongs to the skill `alltests`); red tests: stop before step 7 (the close), name the failing tests, leave the merge commit (it is local; no reset, the owner decides).
7. **Close** (only for the full answer). Do step 3 of "Closing merged entries" in `todo-loop/SKILL.md` for the entry of this branch only: `todo close <id> --reopen` for a slice that does not finish the entry, else `todo close <id>`. Other entries that wait to be closed are named in the report and left alone. No commit: the store holds the status. Then file the branch's follow-ups (`todo-loop/SKILL.md`, "Follow-ups"), and record what the entry cost: `python3 <engine>/tools/tokstats/tokstats.py record <branch-id> --entry <id>` from the checkout's root (`tools/tokstats/CLAUDE.md`; it writes outside every repository), both before step 9 deletes the branch; a failure of either is a line in the report, never a stop. The report of step 13 gives its one line (weighted tokens and dollars).
8. **The changelog** (only for the full answer, only when it is on). Take the draft file of step 4 (with the owner's corrections, if the answer asked for any), then `todo version next --bump <chosen> --entry <id>`, which prints the number. A non-zero exit stops this step: no number is made up locally and `add` is not run without `--version` (the merge and the close stay; the report says to rerun step 8 once the service answers, and a repeat with the same bump returns the same number). Then `<changelog> add --draft <file> --bump <chosen> --version <number>`: it writes `<R>/changelog/<id>.md`, rewrites the three version lines of `<header>` and regenerates `CHANGELOG.md`. A refusal stops this step with its message (the merge and the close stay; the report says so and names what the owner fixes by hand). Then `git -C <R> add changelog CHANGELOG.md <header>` and one commit `Changelog: <title> (<version>)` with the Co-Authored-By line the conversation gives, on `<base>`; nothing else is staged. It comes after the close and before the branch is deleted, so the commit sits on the merged `<base>` and, in a game, before the pointer commit of step 10.
9. **Delete the branch** (only for the full answer, after step 8). A branch checked out in a worker folder cannot be deleted: find it in `git -C <R> worktree list --porcelain` (for an engine branch in a game, the worktree is the worker's `engine/`) and, when `git -C <worktree> status --porcelain` is empty, `git -C <worktree> switch --detach <base>`; when it is not empty, leave the branch and say which folder holds it. Then `git -C <R> branch -d <branch>`. On failure report it and leave the branch.
10. **Move the pointer** (only for the full answer and only for an entry of the engine area in a game). `engine/` now stands on the merged `<base>` (and on the changelog commit of step 8, when there is one). Before `git add engine`, `<old>` = `git rev-parse HEAD:engine` of the game repository; after the commit, with the changelog on, `<changelog> breaking --since <old> --repo engine` and its output goes into the report of step 13 (what the move breaks for the game). In the game repository: `git add engine` and one commit `Update engine: <title> (<version>)` (without the version when the changelog is off) with the Co-Authored-By line the conversation gives, on the branch the game repository stands on (it is the owner's own; if that is not its base branch, say so in the report and still commit only the pointer). Nothing else is staged. The pointer is never moved before the merge, and never to a commit that is not in `<base>`.
11. **Start the idle workers** (only after the full answer, and only when the repository has workers: `python3 <engine>/tools/todo/worker.py list` names some). `python3 <engine>/tools/todo/worker.py kick --merged <id>`: the workers that held the entry count their entries in a row from zero again, and every idle worker (finished, clean, its queue not paused) starts on the first takeable entry of its queue, detached (`<engine>/tools/todo/CLAUDE.md`, "Workers"). Name what it started and what it skipped; a failure is a note, never a stop.
12. **Perf sentinel** (optional; only after the full answer, and only when the repository has `.claude/rules/perf-project.md`). Its setting is the line "The sentinel (`todo-merge`)" of that file: `off` skips it, `always` runs it, `ask` (the default) asks one AskUserQuestion: `Run the fast perf set` / `Skip`. It runs the fast subset of the set of the checkout's root on the merge (in a game after step 10, so the game is measured with the merged engine): `python3 <engine>/tools/perf/perf.py --fast --json <scratchpad>/sentinel-<branch-id>.json` (`.claude/skills/perf/SKILL.md`, step 1 first: a busy machine is reported, not measured). Exit 0: one line with the verdicts. Exit 3: repeat the regressed benchmarks once (`--only <names> --repetitions 10 --no-build`); if they still regress, file an entry through the `todo-add` steps with the id `perf-<branch-id>` (`-2` if taken), in the area of the merged entry, title `Perf regression after merging <branch>`, whose body names the merge commit, the baseline commit, the machine and, per regressed metric, the mean ± half-width, the baseline mean and the change, and ends with "investigate: `/perf-investigate <benchmark>`". Exit 1: report the error. The sentinel never reverts, never updates the baseline and never blocks: the merge stays.
13. **Report the result.** In Russian: the merge commit, the changelog commit and the version (or why there is none), the pointer commit and the `breaking` listing, the workers the kick started, the new status of the entry (`closed`, or `open` for the next slice), the follow-ups filed (the rolling entry and the count, and a repeated finding proposed as a rule), whether the branch was deleted, whether build and tests ran, where the checkout stands now (the base branch, since the work branch is gone) and the worker folder moved off it, if any. Name the other branches in `review` of the same area: their base has moved now, and their own `merge-tree` check comes when they are merged (a branch whose dry check conflicts then is sent back to its worker as a conflict round, step 3, not only named). Name first the branches stacked on the one just merged (their note says `stacked on <this branch>`): they can be merged now, and the next `/todo-merge` takes them. End by saying that `git push` is the owner's.

## Forbidden

`git push`, `fetch`, `--force`, `reset --hard`, `branch -D`, `clean`, `stash`, `--no-verify`; resolving conflicts (the developer of `todo-loop` does, in a conflict round); editing code or any file (the only file writes are the tool's files of step 8 (committed as `Changelog: ...` on `<base>`) and the pointer of step 10; each stages only its own); a fragment before the merge or without the owner's answer on the bump; a write to the store other than the `close` and the follow-ups of step 7, the `version next` of step 8, the entry of the sentinel (step 12) and the `worker.py remarks` of step 3 (only after the owner's yes); merging a branch whose entry is not in status `review`; any change before the answer of step 5, except that `remarks` of step 3.
