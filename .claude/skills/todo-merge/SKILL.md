# todo-merge

You are the **conductor** and do everything yourself, no agents. The skill takes one branch `todo/<branch-id>` whose entry `todo-loop` left in status `review` in the todo store, shows the owner what it holds, **asks**, and only then touches the base branch. The store and its CLI are `<engine>/tools/todo/CLAUDE.md`; the closing steps are in `.claude/skills/todo-loop/SKILL.md` ("Closing merged entries").

`/todo-merge [<id or branch>]`

The terms `<area>`, `<R>` (repository of the area), `<base>`, `<engine>` and `todo` (`python3 <engine>/tools/todo/todo.py --actor todo-merge`) are the ones of `todo-loop/SKILL.md` ("Areas and the repository rules"), taken from `.claude/rules/todo-project.md`. Read that file first.

Run it in the main checkout, the one that holds the base branches; a worker folder of the loop (`worker.py`) cannot switch to them. Before the answer of step 5 you change nothing: only reads, `git -C <R> switch <base>` (the one change to the checkout; step 5 undoes it on `No`) and `git merge-tree`.

## Steps

1. **Preconditions.** Every area repository is clean (`git -C <R> status --porcelain`; in a game the game repository with `--ignore-submodules=all`) and `todo ping` answers; otherwise stop with a message. Remember the starting branch of every area repository. Never `fetch` and never `push`.
2. **Choose the branch.** `git -C <R> switch <base>` for each area. `todo list --status review --area <area> --json` for each area of the rules file (only those: the store also holds other games' entries, `todo-loop/SKILL.md`, "Only the areas of the rules file"). Candidates: entries in `review` whose `branch` is in `git -C <R> branch --list 'todo/*' --no-merged <base>` of their area. Unmerged branches that are not candidates (their entry is `in progress ... stopped`, or open) are only named, with the `statusLine`.
   - A **stacked** branch (its `statusNote` ends with `stacked on todo/<parent>`: `todo-loop/SKILL.md`, "Stacked branches") is a candidate only when its parent is merged: the parent branch is gone or is in `git -C <R> branch --list 'todo/*' --merged <base>`. Otherwise it is named as `waits for todo/<parent>`; merging it first would bring the parent's commits in unreviewed by the owner and under the wrong entry.
   - An entry with an open blocker (a `blockedBy` that is not `closed`: a **paired** game entry waits for its engine entry, `todo-loop/SKILL.md`, "Paired") is a candidate only once the blocker is merged and closed; until then it is named as `waits for <id>`. Merge the engine entry first: its pointer commit is what the game entry was built on.
   - With an argument (`<id>` or `todo/<branch-id>`): take that branch. If it is not a candidate, stop and say why: no such branch, already merged into its base, the status is not `review`, or it is stacked on a parent that is not merged (name the parent: merge it first).
   - Without an argument: one candidate is taken as is; several candidates go to the owner in one AskUserQuestion (area, title, branch, the note of the status); none: say "nothing to merge" and stop.
3. **Dry check.** `git -C <R> merge-tree --write-tree <base> <branch>`: a non-zero exit code means conflicts, so report the files and stop (the skill never resolves conflicts). Compare `git -C <R> merge-base <base> <branch>` with the tip of `<base>`: if they differ, "the base moved since the branch was cut" is a flag for the report and for step 6.
4. **Report.** In Russian, short, printed before the question:
   - the title of the entry, the area and the branch, and where it can be tried live: the worker folder that has it checked out (`git -C <R> worktree list`; the loops run in worker folders, `todo-loop/SKILL.md`, "Parallel workers"), else the main checkout with `git -C <R> switch <branch>`;
   - if the `statusNote` has `slice K of M, after the merge set the status back to open`: a warning that the merge does not finish the entry (closing sets it back to `open` instead of closing it);
   - what was done and how it was checked: the `statusNote` of the entry;
   - `git -C <R> log --oneline <base>..<branch>` and `git -C <R> diff --stat <base>...<branch>`, plus two to four lines of your own on what changed, from the commit subjects and a look at the diff of the non-test files;
   - from the slice plan (`todo plan get todo-loop-<branch-id>.md --stdout`, if the store has it): "Review notes" (non-blocking findings) and what the architect left for the owner to check by hand, with the link `todo plan url todo-loop-<branch-id>.md`;
   - screenshots: when `~/.claude/plans/todo-loop-<branch-id>-shots/` (a through entry: also `todo-loop-<branch-id>-s*-shots/`) exists, the folder as a `file://` link, the `summary:` line of its `diff.txt` and its changed pairs (the lines that are not `unchanged`), and that the pictures are for the owner's eyes: do not open them. A folder that is not there on this machine (the plans folder is local) is one line, not an error;
   - the `merge-tree` result (clean) and the "base moved" flag;
   - for an engine branch in a game: that the answer also makes a separate commit in the game repository that moves the pointer of `engine/`.
5. **Ask.** One AskUserQuestion: `Merge + close + delete branch` (for an engine branch in a game: `+ move the pointer of engine/`), `Merge only (no close, the branch stays)`, `No`. `No` ends the skill with nothing changed: switch every area repository back to its starting branch first, so the owner stays on the branch they were trying.
6. **Merge.** `git -C <R> merge --no-ff -m "Merge branch '<branch>'"` on `<base>` with the Co-Authored-By line the conversation gives (the history uses this form). If the merge fails for any reason: `git -C <R> merge --abort`, switch back to the starting branches, report, stop. If the base had moved (step 3), also build with the preset of `build` and run `ctest --preset <p>` on the result (the targets of the rules file); red tests: stop before step 7, name the failing tests, leave the merge commit (it is local; no reset, the owner decides).
7. **Close** (only for the full answer). Do step 3 of "Closing merged entries" in `todo-loop/SKILL.md` for the entry of this branch only: `todo close <id> --reopen` for a slice that does not finish the entry, else `todo close <id>`. Other entries that wait to be closed are named in the report and left alone. No commit: the store holds the status, and the service mirrors it into Vikunja.
8. **Delete the branch** (only for the full answer, after step 7). A branch checked out in a worker folder cannot be deleted: find it in `git -C <R> worktree list --porcelain` (for an engine branch in a game, the worktree is the worker's `engine/`) and, when `git -C <worktree> status --porcelain` is empty, `git -C <worktree> switch --detach <base>`; when it is not empty, leave the branch and say which folder holds it. Then `git -C <R> branch -d <branch>`. On failure report it and leave the branch.
9. **Move the pointer** (only for the full answer and only for an entry of the engine area in a game). `engine/` now stands on the merged `<base>`. In the game repository: `git add engine` and one commit `Update engine: <title>` with the Co-Authored-By line the conversation gives, on the branch the game repository stands on (it is the owner's own; if that is not its base branch, say so in the report and still commit only the pointer). Nothing else is staged. The pointer is never moved before the merge, and never to a commit that is not in `<base>`.
10. **Perf sentinel** (optional; only after the full answer, and only when the repository has `.claude/rules/perf-project.md`). Its setting is the line "The sentinel (`todo-merge`)" of that file: `off` skips it, `always` runs it, `ask` (the default) asks one AskUserQuestion: `Run the fast perf set` / `Skip`. It runs the fast subset of the set of the checkout's root on the merge (in a game after step 9, so the game is measured with the merged engine): `python3 <engine>/tools/perf/perf.py --fast --json <scratchpad>/sentinel-<branch-id>.json` (`.claude/skills/perf/SKILL.md`, step 1 first: a busy machine is reported, not measured). Exit 0: one line with the verdicts. Exit 3: repeat the regressed benchmarks once (`--only <names> --repetitions 10 --no-build`); if they still regress, file an entry through the `todo-add` steps with the id `perf-<branch-id>` (`-2` if taken), in the area of the merged entry, title `Perf regression after merging <branch>`, whose body names the merge commit, the baseline commit, the machine and, per regressed metric, the mean ± half-width, the baseline mean and the change, and ends with "investigate: `/perf-investigate <benchmark>`". Exit 1: report the error. The sentinel never reverts, never updates the baseline and never blocks: the merge stays.
11. **Report the result.** In Russian: the merge commit, the pointer commit, the new status of the entry (`closed`, or `open` for the next slice), whether the branch was deleted, whether build and tests ran, where the checkout stands now (the base branch, since the work branch is gone) and the worker folder moved off it, if any. Name the other branches in `review` of the same area: their base has moved now, and their own `merge-tree` check comes when they are merged. Name first the branches stacked on the one just merged (their note says `stacked on <this branch>`): they can be merged now, and the next `/todo-merge` takes them. End by saying that `git push` is the owner's.

## Forbidden

`git push`, `fetch`, `--force`, `reset --hard`, `branch -D`, `clean`, `stash`, `--no-verify`; resolving conflicts; editing code or any file (step 9 stages only the pointer); a write to the store other than the `close` of step 7 and the entry of the sentinel (step 10); merging a branch whose entry is not in status `review`; any change before the answer of step 5.
