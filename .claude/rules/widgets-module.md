# Widget System Guidelines

## Overview

Widgets are the engine's per-frame building blocks implementing `IWidget` (a `FACTORY_BASE` that also derives `SubscriptionHolder`). `WidgetManager` creates them from XML (the reflected holder `WidgetList`, filled by `MakeFromConfig`) and drives them every frame. There are two kinds:

- **Editor panels**: `SceneEditorWidget`, `AssetPanelWidget` (a panel asset hosted as a widget; `WidgetsConfig.xml` lists `<widget type="AssetPanelWidget" asset="FileChangesPanel"/>`: the File changes panel, hidden at start, command `view.fileChanges`, is `config/panels/FileChangesPanel.xml` over `FileChangesPanelModel`, a reflected view of `FileChangesModel` (no ImGui); **Rescan** lists the files that differ on disk from what the engine last knew, **Apply all** and a per-row apply deliver them; the disk is read only on a button press; `FileSystem/CLAUDE.md`, "FileWatcher"), `AssetPanelWidget` for the Sprite Library (`asset="SpriteLibraryPanel"`: the window `Sprite Library###SpriteLibrary`, the entries with a thumbnail, a "Slice sheet" section, an "Atlas" section that packs and unpacks a group of sprites and an "Atlas preview"; `config/panels/SpriteLibraryPanel.xml` over `SpriteLibraryPanelModel` and the slots `spriteList`, `spritePreview`, `spriteAtlasPreview`; open at start; `src/Widgets/TextureEditor/CLAUDE.md`), `EditorLayoutWidget`, `ViewportWidget`, `AssetPanelWidget` for the Profiler (`asset="ProfilerPanel"`: frame bars with budget lines and stage split, a "Work only" switch that leaves the backend's display wait (the `Wait` stage) out of the bars and their scale, and a mean work / mean wait line, counter graphs, paused frames as flat muted bars, zone timeline and table, spike capture, heap, allocations per zone, Chrome trace export; `config/panels/ProfilerPanel.xml` over `ProfilerPanelModel` and the slots `profilerFrames`, `profilerTimeline`, `profilerZones`, `profilerSpikes`, `profilerMemory`, `profilerZoneAllocs`; `src/Widgets/Profiler/CLAUDE.md`; switches the zone ring on while open; hidden until Ctrl+Shift+P or `view.profiler`), `AssetPanelWidget` for the Console (`asset="ConsolePanel"`: the log history with filters, Pause and Clear, and a control API command line at the foot, `config/panels/ConsolePanel.xml` over `ConsolePanelModel` and the slots `consoleRows`, `consoleOutput`, `consoleCommandLine`; `src/Widgets/Console/CLAUDE.md`; hidden until Ctrl+Shift+L or `view.console`), `AssetPanelWidget` for the Generate panel (`asset="GeneratePanel"`: the window `Generate###Generate`, a style preset and a subject become image variants through the art generation service and an accepted one a sprite of the game; `config/panels/GeneratePanel.xml` over `ArtGenPanelModel` and the slots `artgenWorkflowInputs`, `artgenReferencePicture`, `artgenVariants`, `artgenSounds`, `artgenSetTab`; the model exists while the window is closed, so the control methods and the drop answer do too; `src/Widgets/ArtGen/CLAUDE.md`; hidden until `view.generate`), `AssetPanelWidget` again for the Config Editor (`asset="ConfigEditorPanel"`: the window `Config Editor###ConfigEditor`, `config/panels/ConfigEditorPanel.xml` over `ConfigEditorPanelModel`, open at start; `src/Widgets/ConfigEditor/CLAUDE.md`) and for the Game panel (`<widget type="AssetPanelWidget" asset="GamePanel"/>`: `config/panels/GamePanel.xml` over `GamePanelAssetModel` and `ActiveGameSourceModel`: the active game's state, its actions as buttons, its reflected fields and `BE_FUNCTION`s, through `IControllableGame` and the reflection only; `src/Widgets/GamePanel/CLAUDE.md`; hidden until Ctrl+Shift+G or `view.game`), for the Preferences window (`asset="PreferencesPanel"`: `window="Floating"`, tabs General and Hotkeys and the Rebind Shortcut modal, `config/panels/PreferencesPanel.xml` over `PreferencesPanelModel`, hidden until Ctrl+, or `view.preferences`) and, as hosts with no window of their own (`window="Dialogs"`), for the dialogs `EditorDialogsPanel` (Save Layout As, over `EditorDialogsModel`) and `SceneDialogsPanel` (the Scene Editor's Add Node and Add Component, over `SceneDialogsModel`). They build ImGui windows. `EditorLayoutWidget` also hosts the dock space, the command palette and, as the windows that draw them, the two bars that are assets without a window (`window="Bar"`: the menu bar `MainMenuPanel` over `MainMenuModel` and the main toolbar `MainToolbarPanel` over `MainToolbarModel`; "Bars"; "Editor commands, hotkeys and settings"). `ViewportWidget` draws a "Paused" mark in the image corner while `CoreManager::GetPause()` is paused, and drops the mouse it would forward to the game then (an edit click still goes through); the image is covered by an `InvisibleButton` (an item with an id: a press on it is always seen and never starts a window move, which a plain `Image` does not give) and its mouse is the game's input as the window's (`ViewportPointer`, no ImGui: target pixels, a press and its release go the same way). An input mode `Play` / `Edit` (`ViewportInputMode`, a toolbar button and the command `viewport.inputMode`, F8) says where a press goes: `Play` to the game, `Edit` to nobody but the editor as `ViewportEditClickEvent` (target pixels, once per press); Alt held flips it for one click, and a corner badge and, in `Edit`, an outline show the effective mode. - **Frame widgets**: steps of the render frame that are not UI. The application opens the frame itself (`IRenderer::BeginFrame(clearColor)`, the `clearColor` of `ApplicationConfig`) before any widget, so no widget clears. `SceneRenderWidget` draws the scene (Game mode; a widget, like `ViewportWidget` in the editor, because it is the mode's way to show the scene: a config may drop or replace it and the frame is still the clear colour), `ImGuiWidget` begins and renders the ImGui frame (Editor mode; on the manual clock its `io.DeltaTime` is the frame's clock delta, at least `kMinImGuiFrameSeconds`, not the backend's wall time, so double click, tooltip delays and fades repeat on every run: `ImGuiFrameSeconds`), `ProfilerOverlayWidget` (last in `GameWidgetsConfig.xml`) draws the profiler overlay over the scene with the engine's rects and text (no ImGui), shown and hidden by Ctrl+Shift+P, its draws and allocations left out of the frame statistics (the Profiler panel holds the same allocation pause while it is open); it is in every build but does nothing in a plain Release (`kProfilerViewsBuilt`, `BECore/Profiler/CLAUDE.md`).

The frame widgets and `ImGuiWidget` are in every build, because a game may list `ImGuiWidget` in its own `GameWidgetsConfig.xml` for a HUD.

**Panels as data.** A simple tool panel is described by an asset (`config/panels/<Name>Panel.xml`: elements, bindings to reflected sources, buttons that run editor commands) instead of C++. The format, the loader and the reads of a bound value are in `src/Modules/BECore/Widgets/PanelAssets/CLAUDE.md` (every build); the interpreter that draws an asset, the widget that hosts it, the model interface and the slot registry are editor code in `src/Widgets/PanelAssets/` (its `CLAUDE.md`). A button's click is an `EditorCommandEvent` with an argument; the model that owns the command runs it only while its panel is open (`fileChanges.rescan`, `fileChanges.applyAll`, `fileChanges.apply` and the Game panel's `gamePanel.reset`, `gamePanel.perform`, `gamePanel.call`, `gamePanel.copyState`: rows of the command table). What stays hand-written is a slot: the Config Editor's objects or XML tree (`configTree`, `src/Widgets/ConfigEditor/CLAUDE.md`).

A widget is not game UI. In-game UI is a scene feature, canvases of `UICanvasComponent` (`src/Modules/BECore/UI/CLAUDE.md`); do not build it on `IWidget`.

## IWidget Interface

The lifecycle is called by the loader and `WidgetManager` through `IWidget`, never by name, so no widget method is `BE_FUNCTION` (a mark would list it in the schema as callable for nothing); a test holds it.

| Method | Purpose |
|--------|---------|
| `Initialize(IDeserializer&)` | Called by the loader after the widget's reflected fields are read, inside its own `<widget>` scope (read an attribute or child that is not a field here, subscribe to events); return `false` on failure (the widget is then logged and not registered). Do not call `Deserialize(deserializer)` here: the loader has done it |
| `Update()` | Every frame. An ImGui panel builds its window here (`ImGui::Begin` ... `End`), between `ImGui::NewFrame` and `ImGuiWidget::Draw`. A frame widget issues its render commands here when they must come first |
| `DrawScreen()` | Optional, default is empty. Draws into the back buffer after every `Update()` (`SceneRenderWidget` draws the scene here) |
| `Draw()` | Every frame, after `DrawScreen()`. Normally empty; `ImGuiWidget::Draw()` runs `ImGui::Render()` and the ImGui draw event |

## Widget Lifecycle

1. `WidgetManager::CreateWidgets()` (from `CoreManager::OnApplicationInit`) reads the run mode (`mode` in `ApplicationConfig.xml` or `--editor` / `--game`, see `BECore/CLAUDE.md`) and fills a `WidgetList` with `MakeFromConfig<WidgetList>(configName)`: each `<widget type>` is created through `AbstractFactory<IWidget>` with the default constructor and its reflected fields are read. A missing config is logged (`WidgetManager: config '...' not found`) and no widget is created.
2. `Initialize(deserializer)`: subscribe to events, read what is not a field. An unknown `type` or an `Initialize` that returns `false` is logged once as `Config '<name>': widgets[N]...` (`Unknown factory type: 'X'` / `<Type> failed to initialize`) and the widget is skipped. A `<widget>` without `type` is skipped silently, and `enabled="false"` is honored.
3. Every frame, from `CoreManager::OnGameCycle`: `UpdateAll()` → (queued events) → `DrawScreenAll()` → `DrawAll()`, in registration order.
4. Destruction: `SubscriptionHolder` drops the event subscriptions. A widget can die in the middle of the run, not only at program end: in a build with the editor `WidgetManager::ApplyPendingMode()` replaces the widgets of one run mode by those of the other (Ctrl+Shift+E, applied at the end of a frame after `WaitIdle`; the order and what is lost: `BECore/CLAUDE.md`, "Run mode"). At program end `Application::Cleanup` calls `WidgetManager::DestroyAll()` before `ApplicationCleanUpEvent`. Both destroy the widgets **last created first**, with the GPU idle, and the renderer and its device are alive. So a destructor must give back what the widget set globally and release its GPU objects:
   - `ImGuiWidget::~ImGuiWidget()` calls `Destroy()` (idempotent through `_isInitialized`; the `ApplicationCleanUpEvent` subscription goes with the widget): it waits for the GPU, emits `ImGuiShutdownEvent` (the Vulkan backend frees ImGui's descriptor pool and pipeline there) and shuts the ImGui backends down.
   - `ViewportWidget::~ViewportWidget()` clears the safe-area override of `CoreManager::GetUIEnvironment()` (so a canvas does not keep the simulated safe area in Game mode) and releases its render target, whose destructor waits for the GPU and needs the ImGui context, which is why `ImGuiWidget` must come first in `WidgetsConfig.xml` (it dies last).
   - A new widget that sets something on `CoreManager` or in the scene resets it in its destructor. A mouse button pressed in the viewport and not released at a switch is lost (no button-up reaches the scene).

## XML Configuration

File: `config/WidgetsConfig.xml` (Editor mode) or `config/GameWidgetsConfig.xml` (Game mode: `SceneRenderWidget` + the profiler overlay, no ImGui, so a Game-mode widget must not touch ImGui). Entries `<widget type="..."/>` under `<widgets>`:
- `type`: widget class name (`ImGuiWidget`, `EditorLayoutWidget`, `ViewportWidget`, `SceneRenderWidget`, ...)
- widget-specific settings as `BE_REFLECT_FIELD` fields (for example `<clearColor r g b a/>` of `ViewportWidget`), filled by the loader; anything else is read in `Initialize`
- `enabled="false"` skips the entry
- the file order is the creation and update order; there is no `name` or `priority` attribute

The order is a contract, nothing checks it:
- `ImGuiWidget` is first in `WidgetsConfig.xml`: it creates the ImGui context, and every panel after it needs one.
- `RemoteSessionWidget` (no window; `src/Widgets/RemoteEditor/CLAUDE.md`) comes right after `ImGuiWidget`: panels read what it polled this frame. A game with its own `WidgetsConfig.xml` lists it and `<widget type="AssetPanelWidget" asset="AttachPanel"/>`, or its editor cannot attach.
- `SceneRenderWidget` comes before `ProfilerOverlayWidget` in `GameWidgetsConfig.xml`: the overlay is drawn over the scene.

## Best Practices

- **Single Responsibility**: one widget, one purpose.
- **XML Configuration**: tunable parameters come from the widget's XML node.
- **Event-Driven**: communicate through events, not direct widget-to-widget calls.
- **Lazy Initialization**: set up resources in `Initialize()`, not in the constructor.
- **ImGui in `Update()`**: a panel calls `ImGui::Begin()` / `ImGui::End()` inside `Update()` and leaves `Draw()` empty. `ImGuiWidget::Draw()` renders the ImGui frame first in `DrawAll()`, so a window built in a later widget's `Draw()` would miss the frame.
- A widget that runs in Game mode must not touch ImGui (there is no context).

## Editor commands, hotkeys and settings

Code in `src/Widgets/EditorLayout/`. The logic (`KeyChord`, `HotkeyMap`, `FilterCommands`, `EditorSettings`, `LayoutStore`, the atomic write, `WriteFileAtomically` of `File/File.h`) needs no ImGui context and is tested without one (`tests/BECore/*Test.cpp` named in the regex above); `CommandPalette` and `EditorLayoutWidget` are the ImGui part (the Preferences window is the asset `PreferencesPanel`).

- **Commands.** `GetEditorCommands()` is a static table `{id, title, defaultChord, rebindable}` (ids in `EditorCommandIds`), so it does not depend on which panels are alive (they are re-created at a mode switch). A browser editor offers fewer of them (`EditorLayout/CLAUDE.md`, "The editor in a browser"). The palette filters once per change of its query (`CommandMatchList`), not per frame. The palette, a menu item and a hotkey all emit `EditorCommandEvent{commandId}`; a panel subscribes in `Initialize` and acts on the ids it owns: `EditorLayoutWidget` (quit, layouts, palette, `mode.toggle` through `WidgetManager::RequestToggle()`), the Scene editor, the Config Editor's model and the Sprite Library's model (`scene.save`, `config.save`, `texture.save`: the same method as their Save button, so the command does nothing while the button is disabled; `texture.save` is the model's own subscription, so it saves while the panel is closed too). `game.play` (Play / Stop: `EditorPlayModel::PressPlay`, no chord), `game.pause` and `game.step` (`EditorLayoutWidget`, also in the Game menu; default F6 and F7) drive the same `GamePause`, and are the commands the toolbar's buttons run; `layouts.menuOpened` (the `openCommand` of the two layout menus: rescan the folder), `layouts.load` and `layouts.delete` (argument: the name) run in `MainMenuModel`, are not rebindable and do nothing without a name; `view.console` (the asset's `command`, default Ctrl+Shift+L, rebindable) shows and hides the Console panel, `console.pause|clear|clearOutput` (`ConsolePanelModel`, only while its panel is open, no chord) are its buttons, `profiler.trace` (a literal `argument`: `record`, `restart`, `write`, `writeFrames`), `profiler.spikeLive|spikeClear|resetZoneAllocs` (`ProfilerPanelModel`, the same) the Profiler's; `configEditor.select|reload|reloadDiscard|reloadCancel|switchDiscard|switchCancel` (the model of the Config Editor, only while its panel is open, not rebindable), `view.game` (the `command` of the Game panel's asset, default Ctrl+Shift+G, rebindable) the Game panel; `view.generate` (the Generate asset's `command`, no chord) and `artgen.service|setup|preset|saveAsOpened|reference|run|accept|listen` (`ArtGenPanelModel`, only while its panel is open, not rebindable; a literal `argument` names the action, `ArtGenPanelArgs`) the Generate panel; `sceneEditor.addComponent` (the inspector bar's Add Component, not rebindable) is answered by `SceneEditorWidget` with `SceneAddComponentRequestEvent` for a selected, unlocked node; `spriteLibrary.rename|rescan|add|delete|dropAccept|dropCancel|sliceFindIslands|sliceAdd|atlasName|pack|unpack` (`SpriteLibraryPanelModel`, only while its panel is open, not rebindable) the Sprite Library; `view.preferences` (the Preferences asset's `command`, Ctrl+, : it toggles, so the menu item and the chord close an open window) and `preferences.commit|rebind|clear|reset|resetAll|swap|cancelRebind` (`PreferencesPanelModel`, only while its panel is open, no chord), `view.saveLayout` and `layouts.saveDialog.save|enter|cancel` (`EditorDialogsModel`; `view.saveLayout` opens nothing without a layouts folder), `sceneDialogs.addNode|addComponent|cancel` (`SceneDialogsModel`; `addComponent` takes the class name as the argument) the dialogs; `view.attach` (the `command` of the Attach asset, no chord) shows and hides the floating Attach panel and `remote.attach|detach` (`AttachPanelModel`, only while its panel is open, not rebindable) link the editor to a running game and end the link; `view.viewport`, `view.sceneEditor`, `view.configEditor` and `view.spriteLibrary` (the assets' `command`, no chord) show and hide the panels that are open at start (each owns its command and a close button; a closed one is skipped like a hidden dock tab and opens again at a mode switch, and a reveal opens the Scene Editor); the View menu lists every panel, the Profiler too; `viewport.inputMode` (default F8) flips the viewport's input mode and `viewport.tool.translate|rotate|scale`, `viewport.gizmoSpace`, `viewport.snap` set the gizmo's choices (`ViewportToolbarModel`, always: a `Bar` is always open), `viewport.frameSelected` and `viewport.cameraReset` (the toolbar's Reset) move the camera (`ViewportWidget`); all but `viewport.inputMode` have no chord, because a bare letter is refused as a hotkey (W / E / R / X / F are read by the viewport itself, the first four handed to the model through `IViewportToolbar`); a row with `repeats` (`game.step`) fires again while its chord is held (`ImGuiInputFlags_Repeat`). `EditorCommandEvent::argument` is the value a button of an asset panel passes (a `String`, empty by default; for a plain button the literal `argument` of the asset, for a table cell the text of its row). A new command is a row of the table and a subscriber.
- **`Ctrl+Shift+E` and `Ctrl+Shift+P` are outside the map.** `Application` reads the first from the raw SDL event before ImGui (`RunMode.h`), `ProfilerPanelModel` / `ProfilerOverlayWidget` the second (`Profiler/ProfilerToggle.h`), so `mode.toggle` and `view.profiler` are listed (palette, hotkey table) as fixed and `Assign` refuses them.
- **Chord rules.** Text form `Ctrl+Alt+Shift+Key`, case-insensitive on read, canonical on write; `Ctrl` is `ImGuiMod_Ctrl` (Cmd on macOS). A hotkey needs Ctrl or Alt or is an F-key, so typing in a text field never runs a command. Reserved: `Ctrl+Shift+E`, `Ctrl+Shift+P`, the text-editing chords `Ctrl+A/C/V/X/Y/Z` and `Ctrl+Tab`. `Assign` reports `Conflict` with the other command (the window offers `AssignSwapping`) or `NotAllowed` and changes nothing. Dispatch (`ImGui::Shortcut` with `RouteGlobal`) is off while any popup is open (a menu, the palette, the layout name or the chord capture, which are popups).
- **Per-user files**, never in the repository: `EditorUserDirectory()` is `SDL_GetPrefPath` of the engine's organization and `Editor`, or `$BAGI_EDITOR_DIR` when it is set (tests, CI; a test uses `TestTempDirectory`, never the real folder). There: `preferences.json` (font scale 0.75..2, viewport grid and step 4..256, the `viewportPreview` object: the viewport's size, rotation, safe area and overlays, the device by name; `viewportInputMode`, `"play"` or `"edit"`; `externalEditor`, the command template that opens a file of the Console, 512 bytes; `consoleHistory`, the last 64 commands of the Console), `hotkeys.json` (only the bindings that differ from the table, `""` is unbound, so a later change of a default reaches users who never rebound it) and `layouts/<name>.ini`. Both JSON files keep keys this build does not know, including a binding of an unknown command, and write them back. A file that does not parse or a wrong type gives the default for that field and one warning; `Load` never writes, and the first save after an unreadable file moves it to `<name>.json.bad`. A hotkey entry with a bad chord, for a fixed command or in conflict is dropped with a warning. Writes go through `WriteFileAtomically` (`<name>.tmp`, renamed over the file), so a failure keeps the old one (the window shows the error). Read through a `JsonTape` with the checked helpers of `ControlParams.h`, keep the unknown keys in a `JsonMemberMap` (`BECore/Control/CLAUDE.md`) and write them back sorted with indent 2. A UTF-8 byte order mark at the start is skipped before the tape, which refuses it (Notepad writes one); of two equal keys the first is read.
- **`IEditorLayoutHost`** (`EditorLayout/IEditorLayoutHost.h`) is what the models of the Preferences window and the Save Layout dialog use of the layout widget: its `EditorSettings`, `LayoutStore`, `GetPlayModel` (read by `MainToolbarModel`), `SaveCurrentLayoutAs`, `LoadLayout` and `NotifyPreferencesChanged`. `EditorLayoutWidget` registers itself in `EditorLayoutHostRegistry` for its lifetime (`Initialize`); a model asks for the host in each call and never keeps it (a reply such as an assigned chord or an error sentence does not fit a one-way event, and a pointer to the widget would be a widget-to-widget call). `GetSettings()` is set after `Initialize`; `GetLayouts()` is null without a per-user folder. A test registers `ProbeEditorLayoutHost` (`tests/BECore/EditorLayoutHostProbe.h`).
- **Preferences reach other panels by event.** `EditorLayoutWidget` owns the settings and emits `EditorPreferencesChangedEvent{viewportGrid, viewportGridStep, the preview fields, viewportInputMode, externalEditor, consoleHistory}` on its first `Update` (the panels subscribed in `Initialize`) and on each change; a panel never reads the files. `ViewportWidget` draws the grid from it; `ViewportToolbarModel` restores the preview choice and the input mode from it and tells a change with `ViewportPreviewChangedEvent` or `ViewportInputModeChangedEvent` (on a real change only), which `EditorLayoutWidget` stores and saves without announcing it again (its asset line comes before `EditorLayoutWidget` in `WidgetsConfig.xml`, so the model hears the first event); a command run in the Console is told with `ConsoleCommandSubmittedEvent` (added to `consoleHistory`, saved).
- **Layouts.** The dock layout of the last session is restored by ImGui's own ini (`config/imgui.ini`, `ImGuiWidget`), so nothing of ours restores it. The named layouts (`LayoutStore`, names `[A-Za-z0-9_ -]`, 1..64, not a Windows device name) hold the text of `ImGui::SaveIniSettingsToMemory`. A chosen layout is kept as pending text and loaded in the handler of `RenderEvents::ImGuiNewFrameEvent` (emitted right before `ImGui::NewFrame`); `LoadIniSettingsFromMemory` in the middle of a frame can assert, and it clears the dock tree even for a bad text, so a text without the `[Docking][Data]` section is refused and the current layout stays. The Layouts and Delete Layout menus read the names from `MainMenuView::layouts` (`MainMenuModel` scans the folder on `layouts.menuOpened`, one frame after the menu opens, never on every frame it is open). A loaded ini or layout text goes through `MigrateLegacyWindowNames` first, which renames the legacy windows `Config Editor` and `Sprite Library` to the assets' `ConfigEditor` and `SpriteLibrary` (a window id change needs a row in its table). A window the loaded layout does not mention floats at its default place; "Reset to Defaults" rebuilds the default tree.

## Editor look

`ImGuiWidget` (every build) sets up the look of the ImGui context; the code is in `src/Widgets/ImGuiFonts.*`.

- **Fonts.** The default font is Inter Regular with Lucide merged into it (a label can hold an icon glyph, `ICON_LC_*` of `Icons/IconsLucide.h`, and a word). Inter has glyphs of its own in the private use area, on Lucide's codepoints, and the first source wins, so the Inter source excludes the Lucide span (`GlyphExcludeRanges`); `ImGuiFontsTest` holds that every Lucide codepoint is drawn from the icon source. The second font is JetBrains Mono, for numbers (`ScopedMonoFont`; null-safe, so a missing file costs the look, not the start). The files are `assets/fonts/` read through the layered file system (a game's file with the same name replaces ours) into `ImGuiFontBuffers`, which `ImGuiWidget` keeps until after `DestroyContext` (ImGui 1.92 reads the bytes while its atlas lives). Sizes are the named `k*FontSize` constants of `ImGuiFonts.h`. No bold or second weight. `IconsLucide.h` is vendored (kept out of clang-format).
- **Scale.** ImGui's backend sets the rasterizer density from the framebuffer scale, so a Retina display needs nothing from us. What is left is `FontScaleFor(displayScale, pixelDensity)` (the display scale the user set over the pixel density; 2/2 is 1, 1.5/1 is 1.5), kept in `style.FontScaleDpi` and re-read every frame, so moving the window to another display needs no rebuild. `FontScaleMain` stays the user's preference (`EditorPreferences::fontScale`); the two multiply.
- **Theme.** One theme only, in `ImGuiTheme.{h,cpp}` (every build): `GetImGuiPalette()` holds the colour roles (window / panel / frame surfaces, border, text, the violet accent with hover, active and muted fill, success, warning, error) and `ApplyImGuiTheme(style, uiScale)` builds the whole style from them and from named sizes, from a fresh `ImGuiStyle` each time (so a scale change never scales twice) and keeping only the font fields. `ImGuiWidget` applies it at start and when the window's scale changes. Panels take a colour from the palette (`GetImGuiPalette().warning` for "(unsaved changes)"), never a literal. There is no theme preference: the `theme` key of an older `preferences.json` is kept as an unknown member and written back; a light theme would be a new entry on top of the palette.
- **Icons.** A class declares its icon with `ICON=<lucide-name>` in `BE_CLASS` (`ClassMeta::icon`, `reflection-module.md`); the editor maps the name to a glyph with `IconTable` (`EditorLayout/IconTable.*`, a sorted `constexpr` array: a new icon is a new row in its place, a `static_assert` holds the order; `IconTableTest` also checks every row and every `ICON_LC_*` the widget sources use against the font). `IconOfClass` gives the generic `box` for an empty or unknown name and logs an unknown one once; `IconOfNode` takes the icon of the node's main component (the first one, in the node's order, that names an icon). A hierarchy row and the Add Component list show it before the name. Per-frame code builds no string for it: icons are static `const char*`, ImGui formats `"%s %s"` itself.
- **Controls.** `EditorLayout/EditorControls.*`: `IconButton` (icon only, the word in the tooltip; the tooltip shows on a disabled button too) and `IconTextButton` (icon and word) for every button of a panel; a menu item takes the icon as a literal (`ICON_LC_TRASH_2 " Delete"`). No `[+ Add]` brackets. A number field (drag, input) draws in the mono font through `ScopedMonoFont`; ImGui draws a field's label in the field's font, so a drag field whose name should stay in the UI font hides its label (`##id`) and writes the name after it (`DrawNumber` in `ImGuiPropertyVisitor`). Labels are built in a stack buffer, never in an `eastl::string` per frame.
- **Toolbars and empty states.** Every control of a toolbar (the viewport's size, safe-area and view combos, Rotate, Overlays, the custom W / H) has an icon and an `ItemTooltip` that says what it is, so a bare "Free" or "Auto" is never alone. A combo shows its icon and current value from a literal (`ICON_LC_EYE " Auto"`) or, for a name that varies, from a member string made again only when the value changes. A panel with nothing to show calls `EmptyState(icon, text)` (a large icon and one wrapped line, centered; it takes only the room it needs, so it can sit inside a section) instead of a bare `TextDisabled`.
- **Bars.** `EditorLayoutWidget` draws two fixed-height children of its `##EditorRoot` host (not windows, so they are not draggable and not in `imgui.ini`, and the dock layout is unchanged): `MainToolbar` under the menu bar and `StatusBar` at the bottom. The menu bar (`BeginMenuBar` of the host) and the toolbar's content are assets of the window kind `Bar` (`MainMenuPanel.xml`, `MainToolbarPanel.xml`; `src/Widgets/PanelAssets/CLAUDE.md`, "Bars"): `DrawMenuBar` and `MainToolbar::Draw` only keep the frame (the menu-bar flag, the child, its height and colour) and call `PanelBarsRegistry::Draw(<asset>)`. Both assets are listed in `WidgetsConfig.xml` before `EditorLayoutWidget`; a game with its own `WidgetsConfig.xml` adds the two `AssetPanelWidget` lines or has an empty menu bar and toolbar. The Viewport's toolbar is a third `Bar` (`ViewportToolbarPanel`, drawn by `ViewportWidget`, listed before `EditorLayoutWidget` too); a game without its line has a Viewport with no toolbar and every choice at its default (Free, Play, no overlays, Auto view, Move / World / no snap), and F8 and W / E / R / X do nothing there. The Scene Editor's Save row and inspector frame are two more, drawn by `SceneEditorWidget` ("Scene Editor Conventions", "Save row and inspector frame"). The chord of a menu item comes from `EditorChordText` (a member of the widget, installed as `PanelChordText`, cached per `HotkeyMap::Revision()`); the dock space gets the height that is left (`CloseItemGap` pulls the cursor back over ImGui's gap so the three touch). Heights are the frame height plus the theme's padding, never a pixel constant. The toolbar's buttons run the commands `game.play`, `game.pause` and `game.step` and read `EditorPlayModel` (pure, `Stopped` / `Playing` / `Paused`, owned by the widget) through `MainToolbarModel`, a view that the host's `GetPlayModel()` fills (the menu's Step One Frame reads the same view). **Play / Stop is state only** (the editor's game runs live, which the model calls `Stopped`, until `editor-play-in-editor` gives Play its meaning; the tooltips say so). **Pause and Step are real**: the engine's `GamePause` is the single truth, the widget writes the model's result to it (`SetPaused`, `RequestSteps(1, kDefaultStepSeconds)`) and copies the engine's flag into the model at the start of every `Update` (the control API and the manual clock pause too, and the manual clock's pause is never lifted from here). Pause is valid in every state and returns to the state it was pressed from; Step is enabled while paused and repeats while the button is held (`repeat="true"` on its button). Leaving the editor for Game mode (the widget's destructor) resumes the pause, unless the manual clock holds it, so Game mode is never left frozen with no button. The status bar shows the mean FPS and frame ms of the last `kMeterWindow` game frames (`FrameMeter`: a paused, held frame is left out, so the numbers stand while the game is paused; rounded, coloured by `ClassifyFrame` against the fixed 60 fps `kFrameBudgetMs`: `success`, `warning` up to twice over, `error` above; the rule of the Profiler panel's bars, which stays its own code), the allocations of the last frame (only when `AllocTracker::kEnabled`), the GPU's temperature, load and memory or, with no GPU reading, the CPU's load and temperature (`HardwareMonitor` polls on a thread of its own and the frame only `try_lock`s its result; coloured by thresholds, tooltip naming the device, nothing when nothing can be read; `EditorLayout/Hardware/CLAUDE.md`), the control API (`ControlServerStatus` published by `Application`: `off`, or the port and the clients), the active game, the active scene and the engine's git branch (`ReadGitBranch`, read once in `Initialize()`; a `.git` file is followed, nothing found leaves it out). The models (`EditorPlayModel`, `StatusBarModel`, `GitBranch`) have no ImGui and are tested alone. **Zero allocations in a steady frame:** numbers live in fixed `char` buffers and are formatted again only when the meter's `Version()`, the allocation count, the control status or the hardware readings (`HardwareMonitor::Fetch` answers true) moved; a name is copied into a member `String` only when its `PoolString` differs from the last one seen; no `Format(...)` and no heap argument per frame. `EditorBarsTest` holds it with a counter check that bites only with `ENGINE_PROFILER_ALLOC` (the profile preset).
- **Owner's note.** Text is rasterized by stb_truetype and may look soft at 13..15 px. The fix is `imgui_freetype`, which lives in the vendored `src/Modules/imgui/` and needs the owner's yes.

## Scene Editor Conventions

Scene editor code is split across focused layers:

- `SceneEditorWidget`: orchestration (selection flow, scene-level actions, window structure).
- `ComponentInspectors`: per-component editing. `RenderComponentInspector` uses a custom inspector registered with `RegisterComponentInspector` when there is one, and otherwise the generic `ImGuiPropertyVisitor` driven by the component's generated `AcceptPropertyVisitor`.
- `ImGuiPropertyVisitor`: the `IPropertyVisitor` implementation that renders ImGui controls for reflected fields; it draws the `BE_FIELD_ATTRS` of a field (slider, snap, tooltip, disabled), the decisions being `FieldPresentation` (pure, no ImGui), and the container hooks (`+` / `x` per list, the optional's checkbox, the variant's combo), only writing the request the dispatch applies after the list.

Rules:
- Keep selection and scene navigation in `SceneEditorWidget`; keep component field editing in `ComponentInspectors`. Do not duplicate edit logic in the scene widget.
- A new editable field only needs `BE_REFLECT_FIELD`; the generic visitor shows it. Write a custom inspector only when the generic one is not enough.
- Scene editor behavior stays aligned with `config/SceneConfig.xml`. New editable scene/component fields are represented there and then surfaced through inspectors.
- Editor panels build their window in `Update()` (see "ImGui in `Update()`" above).
- **Remote mode** (`RemoteSessionRegistry::GetRemote()` non-null: attached, connecting or lost). **Nothing local may be edited or saved.** The Scene Editor delegates its content to `RemoteSceneView`, drops its selection and announces null (also while closed), ignores `scene.save`, `sceneEditor.addComponent`, select requests and viewport events, and answers its bars as a host: not dirty, name and structure read-only, the layer read-only unless `Attached`. The Viewport runs no scene pass, forwards no input, cancels its drags and shows the link's state; an open Add dialog closes. A panel that learns to change the local scene asks `GetRemote()` first. The local unsaved flag is kept for the return; events that report a change of the local scene made elsewhere still set it. What is remote: `src/Widgets/RemoteEditor/CLAUDE.md`.
- **Component list.** `DrawComponentList` (`SceneEditor/ComponentListView.h`) draws the headers of an `IComponentListSource`, the local node's or the remote one's.
- **UI elements.** For a node with a `UICanvasComponent` the inspector shows a "UI elements" section above the generic fields: the element tree and, for the selected element, `InspectUIRect` (`UIRectInspector`). It edits the authored `style.rect`, live, sets the scene dirty and sends `UIRectEditEvent{scene, node, element, before, after}` in every frame that changed it (`UIEditEvents.h`; the pattern of `NodeTransformEditEvent`, for `editor-undo-redo`). `UINodeFileSession` holds the changed elements; the section's first line says where they go on Save. A node that is an instance of a node file used by no other node of the scene gets the rect attributes of the elements written into `config/<ref>.xml` on Save (`UINodeFileSave`, a text patch: comments and everything else stay); a shared file, or a node written in the scene file, keeps the edit as an `<elements>` override in the scene file. A `.ui.xml` is never edited. The layout math is in `UIRectEdit` / `UIAnchorPresets`, not in the widget. The selected element is an `IntrusivePtr` in `SceneEditorWidget`, dropped when the node changes or the scene is replaced.
  - **The same element in the viewport** (Edit input mode, `ViewportUIGizmos` over `UIElementDrag` and `UIElementEditSession`). `SceneEditorWidget` sends `UIElementSelectedEvent{scene, node, element}` once per change of the pair (null element: none; pointers frame-valid like `SceneNodeSelectedEvent`'s), and `ViewportWidget` keeps them raw and finds them again every frame (`HierarchyModel::FindNode`, `ScenePick::FindElement`), so a deleted node or a replaced tree is never dereferenced. The element must be the primary selection and its node not locked; a `World` canvas is not dragged. When `UIElementDrag::CanDrag` says no (not laid out, hidden, a stack or popup parent, a variant overriding the rect: a drag writes `style.rect` and would seem to do nothing) the viewport draws one line with the reason instead of handles. Otherwise it draws the body outline, eight handles and the anchor widget (four petals; one mark on a point axis; the box faint). **Who takes a press**, before the node gizmo and the box select: a petal, then a handle, of the selected element; its body only when `Ctrl` / `Shift` are not held and `ScenePick::PickAt` answers this same element (a press on another element on top is a normal pick). The node gizmo is disabled while a UI drag is going or the pointer is over a handle. The drag: the pointer goes through `OutputToCanvas` and the wanted rect is always the rect at the press plus the pointer's delta (nothing drifts); `Shift` keeps the aspect on a corner and locks the axis of a move, `Ctrl` turns the snap to the box's edges and centre off, `Esc` cancels; a petal drag changes `anchorMin` / `anchorMax` and keeps the element where it is. The session ends by itself when the scene is not the active one, the node or the element is gone or locked, or the input mode left Edit.
  - **`UIRectDragEvent{phase, scene, node, element, before, after, exact}`** (`ViewportEvents.h`, the pattern of `NodeTransformEditEvent`): `Begin` at the press, `Change` per changed frame (`before` the last frame's spec), `Commit` at the release only if the spec moved (`before` the spec at the press), `Cancel` otherwise (`after` the spec undone to). Pointers are valid for the event only. `SceneEditorWidget` answers `Change` with `UIRectEditEvent` (an undo stack merges the frames as for the inspector), `Commit` with `UINodeFileSession::Note` and the dirty flag, and keeps `exact == false` for the inspector's warning. Not built: pivot drag, arrow-key nudge, several elements, a stack child, a `World` canvas.
  - **Other shapes.** The "Overlays" dropdown of the Viewport's toolbar also lists the devices (`ViewportUIShapes`, session state, never stored): each checked one outlines the selected element's rect as it lays out in that device, over the image, dashed when only approximate (`src/Modules/BECore/UI/CLAUDE.md`, "Editor preview"). The probe lays the live canvas out and gives it back, after the scene pass and only when its key moved.
  - `SceneEditorWidget::Update` announces the selection (`AnnounceSelection`, `AnnounceUIElement`) from inside its window, because the selection itself is made by what the window draws (`HierarchyPanel`, `SyncSelection`): while the window is collapsed or a background tab, nothing is announced and the viewport keeps the last pair, which it re-checks against the tree every frame.
- **Hierarchy panel.** `HierarchyPanel` (ImGui) draws the search box, the component-type filter and the tree of an `IHierarchySource` (`SceneEditor/HierarchySource.h`: `LocalHierarchySource` over a scene, `RemoteHierarchySource` over an attached program, `src/Widgets/RemoteEditor/CLAUDE.md`). A row takes drag and drop, the context menu, the rename field and the eye and lock toggles only when its source gives an `EditableNode`; F2 / Delete / Ctrl+D, Add Node and the pending change belong to the `Draw(Scene&, ...)` overload alone. The keys, and Ctrl+F of both, are local keys while the panel is focused, not rows of the command table. Every decision sits in `HierarchyModel` (no ImGui, tested alone: filters, `CanDrop` / `ResolveDrop`, `ApplyOperation`, `FindNode`, `AncestorsOf`, `SelectionTracker`). `HierarchyState`, owned by `SceneEditorWidget`, holds the selection and what the panel asks for. **One pending operation per frame:** the walk only notes a delete, duplicate or move in `state.pending`, applied after the walk, because it changes the child lists being walked; never change the tree inside the walk. A drag payload holds a raw pointer, used only after `HierarchyModel::ContainsNode` finds it alive. Per-frame text goes to stack buffers.
- **Save row and inspector frame.** The window, `##hierarchy`, `##inspector`, the component list and the UI elements stay C++; the Save row at the top of the window and the inspector's frame (title, empty state, the refusal of a remote edit, the multi-selection and locked lines, Name `##node_name`, Layer `##node_layer`, the instance line, Add Component) are the `Bar` assets `SceneEditorToolbarPanel` and `SceneInspectorPanel` over `SceneEditorPanelModel` (source `scene`), drawn by `SceneEditorWidget` with `PanelBarsRegistry::Draw`. The model reads and edits the inspected node through `ISceneEditorHost` (`SceneEditorHostRegistry`, the `IEditorLayoutHost` pattern), which the widget registers for its lifetime and which says which of name, layer and structure take no edit; a typed name or layer reaches the host before the view is made again, and `SceneNodeSelectedEvent` drops an edit not yet applied. The component list is the slot `sceneComponents` inside the inspector bar. Both lines come before `SceneEditorWidget` in `WidgetsConfig.xml` (their models update first); a game without them keeps the component list (the widget draws the slot itself) and Ctrl+S, without the Save row and the name and layer fields.
- **Add dialogs.** The Add Node and Add Component dialogs are the asset `SceneDialogsPanel` over `SceneDialogsModel` (`SceneEditor/SceneDialogEvents.h`): `SceneEditorWidget` sends `SceneAddNodeRequestEvent{scene, parent}` (the hierarchy's add items) and `SceneAddComponentRequestEvent{scene, node}` (the inspector's button); the model keeps the raw pointers and, while a dialog is open, closes it when the scene is no longer the active one or the node is gone (`HierarchyModel::ContainsNode`); it adds an authored child and answers `SceneNodeAddedEvent{scene, parent, node}` (the widget sets the unsaved flag and reveals the parent) or a component and answers `SceneEditedEvent`. A locked node is offered no component. The inline rename field of a hierarchy row stays in `HierarchyPanel`.
- **Hide and lock** are editor-only flags of `SceneNode` (`EditorFlags`; never saved, copied or serialized). Hidden draws nothing in the viewport; a locked node is not renamed, deleted, moved, dropped into or edited (the inspector is disabled with a line saying so), but it can be selected and duplicated (the copy is unlocked). `SceneEditorWidget`'s destructor calls `SceneManager::ClearEditorFlags()`, so Game mode is never left with a hidden node; a scene switch clears nothing by itself.
- **Selection by events** (`SceneSelectionEvents.h`): `SceneNodeSelectedEvent{scene, node}` is sent by `SceneEditorWidget` once per real change (tracked by `SelectionTracker`; node null = cleared); a subscriber treats the pointers as valid for that frame only. `SceneEditedEvent{scene}` is how another panel says it changed the active scene (the Generate panel's Use on selected): the widget marks it unsaved. `SceneEvents::SceneNodeEditedEvent` (a control client's `scene_set` or `scene_set_node`, `control-scene-api.md`) does the same unless Save leaves the node out. `SelectSceneNodeRequestEvent{scene, node}` asks the widget to select and reveal a node: it acts only on a node found alive in the active scene's tree (`HierarchyPanel::Reveal`), opens its ancestors, scrolls to it and clears a filter that hides it; anything else is ignored (`SelectUIElementRequestEvent{scene, node, element}` is the same request that also selects the canvas element, found by pointer compare); both bring the "Scene Editor" window to the front on the next `Update()` (a flag, never inside the event). **A left click in the viewport in `Edit` mode** (`ViewportEditClickEvent`, other buttons ignored) is answered by `SceneEditorWidget` with `ScenePick::PickAt` (`BECore/Scene/ScenePick.h`, in every build: `scene_pick` picks with it too): the topmost candidate by `Scene::GetDrawRank`, canvas elements (`UICanvasLayout::PickElement`: also an element that only draws) and scene nodes with a `TransformComponent` rect (rotation honoured) alike, a node under a hidden one skipped, a locked one pickable. The node is revealed like a request; a canvas element is also selected in "UI elements" (found again by pointer with `FindElement`). A plain click on nothing clears the selection (with Ctrl or Shift it changes nothing). `ViewportWidget` listens to `SceneSelectionChangedEvent`, keeps the nodes as raw pointers, confirms them alive with one walk per frame (`HierarchyModel::ResolveLive`; the outlines, the framing and the node gizmo take the confirmed list, a drag confirms its own nodes the same way) and outlines `ScenePick::SelectionOutlines` (its rect and a canvas's bounds, not the selected UI element; the primary in the accent colour, the others in `accentMuted`); a node hidden by the editor flag is outlined too.
- **Multi-selection, camera, gizmos** (Edit input mode only). `SceneEditorWidget` owns a `SceneSelection` (ordered, the last is the primary and stays `HierarchyState::selected`, pruned every frame, cleared on a scene change); a click applies `ApplyClick` with the modifiers of `ViewportEditClickEvent` (Ctrl/Cmd toggles, Shift adds), a drag on empty ground sends `ViewportBoxSelectEvent` answered by `ScenePick::PickInRect`, Ctrl+click on a hierarchy row toggles it; `SceneSelectionChangedEvent` carries the list (frame-valid pointers). `ViewportCamera` (pure) is a zoom and centre over the viewport's fit: wheel about the pointer, middle-drag or Space+left-drag, `F`, Reset; every pixel the viewport draws or reads goes through `ViewportFrame`. `ViewportGizmos` (ImGui) over `GizmoGeometry` / `GizmoDrag` (pure) moves, rotates and scales the unlocked selected nodes that have a `TransformComponent`; it writes the component each frame and emits `NodeTransformEditEvent{phase, scene, records}`: `Begin` at the press, `Change` per frame, `Commit` at the release only if something moved (the scene is dirty then), `Cancel` on Esc, a scene change, a dead node, a switch to Play or the widget's death (the nodes get their start values back). A record is `{node, before Item, after Item}`, valid for the event only: an undo stack copies what it keeps and makes one step of a `Commit`. Tool, space and snap are session state of `ViewportToolbarModel` (the toolbar's second row), not in `EditorSettings`; `ViewportGizmos` gets them every frame and a drag takes the snap at its press.
- Save writes the UI rect edits into their node files first (`UINodeFileSession::Save`: a failure is a warning and never stops the scene), then replaces only the `<scene>` of the active scene in `SceneConfig`, matched by its `name` (`SaveSceneToConfig` over `WriteSceneToConfig`, `BECore/Scene/SceneConfigWriter.h`, in every build: `scene_save` saves with it too, and its `SceneSavedEvent` clears the unsaved flag unless canvas edits wait for a node file). The other scenes, their order and the comments around them stay (`XmlDocument` keeps comments and lays the saved text out like the file on disk, `Config/CLAUDE.md`); the comments **inside** the replaced `<scene>` are lost, the element is rebuilt from the live scene; a scene without an element is appended. The scene's attributes come from `Scene::Serialize`, so a new reflected field of `Scene` is saved without a change there; a node is written by `AppendNodeElement` (its fields and its components' through `Serialize`, only those that differ from a fresh object's, `name` always, then `<children>` recursively, so a node added under another survives a Save); a generated node (`SceneNode::IsGenerated()`) is not written, and only authored children make an instance of a node file (`SceneNode::GetSourceRef()`) inline: it becomes its `<node ref>` with only the overrides that differ (`BuildNodeReference`), or, when that cannot be (no loader, the file gone, a component gained, lost or reordered, a node field a reference cannot override, an authored child, the round trip fails), inline with a line in the `notes` of `WriteSceneToConfig(configRoot, scene, loader, notes)` (also for an authored node under a generated parent, which is not written), which `SaveSceneToConfig` logs as warnings, reading the node files through the layered `FileSystem` (`Scene/CLAUDE.md`, "Node files"). Tested without ImGui in `tests/BECore/SceneEditorSaveTest.cpp` on a document of its own and a temporary file; never test it through `ConfigManager::SaveConfig` on a shipped config, that overwrites the file in the repository.
- **Documents for `editor_state`.** The Scene Editor, the Config Editor (its model) and the Sprite Library (its model) register a source in `Initialize` (`CoreManager::GetEditorDocuments().Add`, the handle is a member) that reports their own dirty flags through the rows of `EditorLayout/EditorDocumentRows.h`; a closed panel keeps reporting, a new panel with a Save button adds its own. Shape and kinds: `control-editor-api.md`.
