# Widget System Guidelines

## Overview

Widgets are the engine's per-frame building blocks implementing `IWidget` (a `FACTORY_BASE` that also derives `SubscriptionHolder`). `WidgetManager` creates them from XML (the reflected holder `WidgetList`, filled by `MakeFromConfig`) and drives them every frame. There are two kinds:

- **Editor panels**: `SceneEditorWidget`, `ConfigEditorWidget`, `TextureEditorWidget`, `EditorLayoutWidget`, `ViewportWidget`, `ProfilerWidget` (the Profiler panel: frame bars with budget lines and stage split, counter graphs, zone timeline, zone table, spike capture, heap, allocations per zone, Chrome trace controls and export; switches the zone ring on while open; hidden until Ctrl+Shift+P or `view.profiler`). They build ImGui windows. `EditorLayoutWidget` also hosts the dock space, the menu, the command palette and the preferences window ("Editor commands, hotkeys and settings"). `ViewportWidget` also has a size picker (aspect presets, devices, custom size, rotate), a safe-area simulation and overlays for looking at a UI layout in several shapes (`src/Modules/BECore/UI/CLAUDE.md`, "Editor preview").
- **Frame widgets**: steps of the render frame that are not UI. `ClearScreenWidget` clears the back buffer and opens the swapchain pass, `SceneRenderWidget` draws the scene (Game mode), `ImGuiWidget` begins and renders the ImGui frame (Editor mode), `ProfilerOverlayWidget` (last in `GameWidgetsConfig.xml`) draws the profiler overlay over the scene with the engine's rects and text (no ImGui), shown and hidden by Ctrl+Shift+P, its draws left out of the frame statistics; it is in every build but does nothing in a plain Release (`kProfilerViewsBuilt`, `BECore/Profiler/CLAUDE.md`).

The editor panels exist only in a build with `BE_WITH_EDITOR` (Debug always; Release only when switched on: `cmake/CLAUDE.md`, "The editor option"); without it `src/CMakeLists.txt` leaves the six folders `ConfigEditor`, `EditorLayout`, `Profiler`, `SceneEditor`, `TextureEditor` and `Viewport` out of `RuntimeModule`, and `tests/CMakeLists.txt` leaves out the tests of the panels by a regex (`ConfigEditorSaveTest`, `SceneEditorSaveTest`, `ConfigFieldSchemaTest` the five of the commands section below: `KeyChordTest`, `HotkeyMapTest`, `CommandFilterTest`, `EditorSettingsTest`, `LayoutStoreTest`, and the four of "Bars": `EditorPlayModelTest`, `StatusBarModelTest`, `GitBranchTest`, `EditorBarsTest`); a new editor test goes into that regex. A new editor panel goes into one of these folders (or a new one added to the regex in `src/CMakeLists.txt`); code outside them that needs an editor header is guarded with `#if BE_WITH_EDITOR`. The frame widgets and `ImGuiWidget` are in every build, because a game may list `ImGuiWidget` in its own `GameWidgetsConfig.xml` for a HUD.

A widget is not game UI. In-game UI is a scene feature, canvases of `UICanvasComponent` (`src/Modules/BECore/UI/CLAUDE.md`); do not build it on `IWidget`.

## IWidget Interface

All methods are `BE_FUNCTION`.

| Method | Purpose |
|--------|---------|
| `Initialize(IDeserializer&)` | Called by the loader after the widget's reflected fields are read, inside its own `<widget>` scope (read an attribute or child that is not a field here, subscribe to events); return `false` on failure (the widget is then logged and not registered). Do not call `Deserialize(deserializer)` here: the loader has done it |
| `Update()` | Every frame. An ImGui panel builds its window here (`ImGui::Begin` ... `End`), between `ImGui::NewFrame` and `ImGuiWidget::Draw`. A frame widget issues its render commands here when they must come first (`ClearScreenWidget`) |
| `DrawScreen()` | Optional, default is empty. Draws into the back buffer after every `Update()` (`SceneRenderWidget` draws the scene here) |
| `Draw()` | Every frame, after `DrawScreen()`. Normally empty; `ImGuiWidget::Draw()` runs `ImGui::Render()` and the ImGui draw event |

## Widget Lifecycle

1. `WidgetManager::CreateWidgets()` (from `CoreManager::OnApplicationInit`) reads the run mode (`mode` in `ApplicationConfig.xml`, see `BECore/CLAUDE.md`) and fills a `WidgetList` with `MakeFromConfig<WidgetList>(configName)`: each `<widget type>` is created through `AbstractFactory<IWidget>` with the default constructor and its reflected fields are read. A missing config is logged (`WidgetManager: config '...' not found`) and no widget is created.
2. `Initialize(deserializer)`: subscribe to events, read what is not a field. An unknown `type` or an `Initialize` that returns `false` is logged once as `Config '<name>': widgets[N]...` (`Unknown factory type: 'X'` / `<Type> failed to initialize`) and the widget is skipped. A `<widget>` without `type` is skipped silently, and `enabled="false"` is honored.
3. Every frame, from `CoreManager::OnGameCycle`: `UpdateAll()` → (queued events) → `DrawScreenAll()` → `DrawAll()`, in registration order.
4. Destruction: `SubscriptionHolder` drops the event subscriptions. A widget can die in the middle of the run, not only at program end: in a build with the editor `WidgetManager::ApplyPendingMode()` replaces the widgets of one run mode by those of the other (Ctrl+Shift+E, applied at the end of a frame after `WaitIdle`; the order and what is lost: `BECore/CLAUDE.md`, "Run mode"). At program end `Application::Cleanup` calls `WidgetManager::DestroyAll()` before `ApplicationCleanUpEvent`. Both destroy the widgets **last created first**, with the GPU idle, and the renderer and its device are alive. So a destructor must give back what the widget set globally and release its GPU objects:
   - `ImGuiWidget::~ImGuiWidget()` calls `Destroy()` (idempotent through `_isInitialized`; the `ApplicationCleanUpEvent` subscription goes with the widget): it waits for the GPU, emits `ImGuiShutdownEvent` (the Vulkan backend frees ImGui's descriptor pool and pipeline there) and shuts the ImGui backends down.
   - `ViewportWidget::~ViewportWidget()` clears the safe-area override of `CoreManager::GetUIEnvironment()` (so a canvas does not keep the simulated safe area in Game mode) and releases its render target, whose destructor waits for the GPU and needs the ImGui context, which is why `ImGuiWidget` must come first in `WidgetsConfig.xml` (it dies last).
   - A new widget that sets something on `CoreManager` or in the scene resets it in its destructor. A mouse button pressed in the viewport and not released at a switch is lost (no button-up reaches the scene).

## XML Configuration

File: `config/WidgetsConfig.xml` (Editor mode) or `config/GameWidgetsConfig.xml` (Game mode: `ClearScreenWidget` + `SceneRenderWidget`, no ImGui, so a Game-mode widget must not touch ImGui). Entries `<widget type="..."/>` under `<widgets>`:
- `type`: widget class name (`ImGuiWidget`, `EditorLayoutWidget`, `ViewportWidget`, `SceneRenderWidget`, ...)
- widget-specific settings as `BE_REFLECT_FIELD` fields (for example `<clearColor r g b a/>` of `ClearScreenWidget`), filled by the loader; anything else is read in `Initialize`
- `enabled="false"` skips the entry
- the file order is the creation and update order; there is no `name` or `priority` attribute

The order is a contract, nothing checks it:
- `ImGuiWidget` is first in `WidgetsConfig.xml`: it creates the ImGui context, and every panel after it needs one.
- `ClearScreenWidget` comes before `SceneRenderWidget` in `GameWidgetsConfig.xml`: its `Update()` opens the swapchain pass that `SceneRenderWidget::DrawScreen()` records into.

## Best Practices

- **Single Responsibility**: one widget, one purpose.
- **XML Configuration**: tunable parameters come from the widget's XML node.
- **Event-Driven**: communicate through events, not direct widget-to-widget calls.
- **Lazy Initialization**: set up resources in `Initialize()`, not in the constructor.
- **ImGui in `Update()`**: a panel calls `ImGui::Begin()` / `ImGui::End()` inside `Update()` and leaves `Draw()` empty. `ImGuiWidget::Draw()` renders the ImGui frame first in `DrawAll()`, so a window built in a later widget's `Draw()` would miss the frame.
- A widget that runs in Game mode must not touch ImGui (there is no context).

## Editor commands, hotkeys and settings

Code in `src/Widgets/EditorLayout/`. The logic (`KeyChord`, `HotkeyMap`, `FilterCommands`, `EditorSettings`, `LayoutStore`, the atomic write of `UserFileIo`) needs no ImGui context and is tested without one (`tests/BECore/*Test.cpp` named in the regex above); `CommandPalette`, `PreferencesWindow` and `EditorLayoutWidget` are the ImGui part.

- **Commands.** `GetEditorCommands()` is a static table `{id, title, defaultChord, rebindable}` (ids in `EditorCommandIds`), so it does not depend on which panels are alive (they are re-created at a mode switch). The palette, a menu item and a hotkey all emit `EditorCommandEvent{commandId}`; a panel subscribes in `Initialize` and acts on the ids it owns: `EditorLayoutWidget` (quit, layouts, palette, preferences, `mode.toggle` through `WidgetManager::RequestToggle()`), the Scene, Config and Texture editors (`scene.save`, `config.save`, `texture.save`: the same method as their Save button, so the command does nothing while the button is disabled). A new command is a row of the table and a subscriber.
- **`Ctrl+Shift+E` and `Ctrl+Shift+P` are outside the map.** `Application` reads the first from the raw SDL event before ImGui (`RunMode.h`), `ProfilerWidget` / `ProfilerOverlayWidget` the second (`Profiler/ProfilerToggle.h`), so `mode.toggle` and `view.profiler` are listed (palette, hotkey table) as fixed and `Assign` refuses them.
- **Chord rules.** Text form `Ctrl+Alt+Shift+Key`, case-insensitive on read, canonical on write; `Ctrl` is `ImGuiMod_Ctrl` (Cmd on macOS). A hotkey needs Ctrl or Alt or is an F-key, so typing in a text field never runs a command. Reserved: `Ctrl+Shift+E`, `Ctrl+Shift+P`, the text-editing chords `Ctrl+A/C/V/X/Y/Z` and `Ctrl+Tab`. `Assign` reports `Conflict` with the other command (the window offers `AssignSwapping`) or `NotAllowed` and changes nothing. Dispatch (`ImGui::Shortcut` with `RouteGlobal`) is off while any popup is open (a menu, the palette, the layout name or the chord capture, which are popups).
- **Per-user files**, never in the repository: `EditorUserDirectory()` is `SDL_GetPrefPath` of the engine's organization and `Editor`, or `$BAGI_EDITOR_DIR` when it is set (tests, CI; a test uses `TestTempDirectory`, never the real folder). There: `preferences.json` (font scale 0.75..2, viewport grid and step 4..256, the `viewportPreview` object: the viewport's size, rotation, safe area and overlays, the device by name), `hotkeys.json` (only the bindings that differ from the table, `""` is unbound, so a later change of a default reaches users who never rebound it) and `layouts/<name>.ini`. Both JSON files keep keys this build does not know, including a binding of an unknown command, and write them back. A file that does not parse or a wrong type gives the default for that field and one warning; `Load` never writes, and the first save after an unreadable file moves it to `<name>.json.bad`. A hotkey entry with a bad chord, for a fixed command or in conflict is dropped with a warning. Writes go to `<name>.tmp` and are renamed over the file, so a failure keeps the old one (the window shows the error). Use the checked helpers of `BECore/Control/Json.h`: nlohmann aborts on a wrong type without exceptions.
- **Preferences reach other panels by event.** `EditorLayoutWidget` owns the settings and emits `EditorPreferencesChangedEvent{viewportGrid, viewportGridStep, the preview fields}` on its first `Update` (the panels subscribed in `Initialize`) and on each change; a panel never reads the files. `ViewportWidget` draws the grid and restores its preview choice from it, and tells a change of that choice with `ViewportPreviewChangedEvent` (on a real change only), which `EditorLayoutWidget` stores and saves without announcing it again.
- **Layouts.** The dock layout of the last session is restored by ImGui's own ini (`config/imgui.ini`, `ImGuiWidget`), so nothing of ours restores it. The named layouts (`LayoutStore`, names `[A-Za-z0-9_ -]`, 1..64, not a Windows device name) hold the text of `ImGui::SaveIniSettingsToMemory`. A chosen layout is kept as pending text and loaded in the handler of `RenderEvents::ImGuiNewFrameEvent` (emitted right before `ImGui::NewFrame`); `LoadIniSettingsFromMemory` in the middle of a frame can assert, and it clears the dock tree even for a bad text, so a text without the `[Docking][Data]` section is refused and the current layout stays. A window the loaded layout does not mention floats at its default place; "Reset to Defaults" rebuilds the default tree.

## Editor look

`ImGuiWidget` (every build) sets up the look of the ImGui context; the code is in `src/Widgets/ImGuiFonts.*`.

- **Fonts.** The default font is Inter Regular with Lucide merged into it (a label can hold an icon glyph, `ICON_LC_*` of `Icons/IconsLucide.h`, and a word). Inter has glyphs of its own in the private use area, on Lucide's codepoints, and the first source wins, so the Inter source excludes the Lucide span (`GlyphExcludeRanges`); `ImGuiFontsTest` holds that every Lucide codepoint is drawn from the icon source. The second font is JetBrains Mono, for numbers (`ScopedMonoFont`; null-safe, so a missing file costs the look, not the start). The files are `assets/fonts/` read through the layered file system (a game's file with the same name replaces ours) into `ImGuiFontBuffers`, which `ImGuiWidget` keeps until after `DestroyContext` (ImGui 1.92 reads the bytes while its atlas lives). Sizes are the named `k*FontSize` constants of `ImGuiFonts.h`. No bold or second weight. `IconsLucide.h` is vendored (kept out of clang-format).
- **Scale.** ImGui's backend sets the rasterizer density from the framebuffer scale, so a Retina display needs nothing from us. What is left is `FontScaleFor(displayScale, pixelDensity)` (the display scale the user set over the pixel density; 2/2 is 1, 1.5/1 is 1.5), kept in `style.FontScaleDpi` and re-read every frame, so moving the window to another display needs no rebuild. `FontScaleMain` stays the user's preference (`EditorPreferences::fontScale`); the two multiply.
- **Theme.** One theme only, in `ImGuiTheme.{h,cpp}` (every build): `GetImGuiPalette()` holds the colour roles (window / panel / frame surfaces, border, text, the violet accent with hover, active and muted fill, success, warning, error) and `ApplyImGuiTheme(style, uiScale)` builds the whole style from them and from named sizes, from a fresh `ImGuiStyle` each time (so a scale change never scales twice) and keeping only the font fields. `ImGuiWidget` applies it at start and when the window's scale changes. Panels take a colour from the palette (`GetImGuiPalette().warning` for "(unsaved changes)"), never a literal. There is no theme preference: the `theme` key of an older `preferences.json` is kept as an unknown member and written back; a light theme would be a new entry on top of the palette.
- **Icons.** A class declares its icon with `ICON=<lucide-name>` in `BE_CLASS` (`ClassMeta::icon`, `reflection-module.md`); the editor maps the name to a glyph with `IconTable` (`EditorLayout/IconTable.*`, a sorted `constexpr` array: a new icon is a new row in its place, a `static_assert` holds the order). `IconOfClass` gives the generic `box` for an empty or unknown name and logs an unknown one once; `IconOfNode` takes the icon of the node's main component (the first one, in the node's order, that names an icon). A hierarchy row and the Add Component list show it before the name. Per-frame code builds no string for it: icons are static `const char*`, ImGui formats `"%s %s"` itself.
- **Controls.** `EditorLayout/EditorControls.*`: `IconButton` (icon only, the word in the tooltip; the tooltip shows on a disabled button too) and `IconTextButton` (icon and word) for every button of a panel; a menu item takes the icon as a literal (`ICON_LC_TRASH_2 " Delete"`). No `[+ Add]` brackets. A number field (drag, input) draws in the mono font through `ScopedMonoFont`; ImGui draws a field's label in the field's font, so a drag field whose name should stay in the UI font hides its label (`##id`) and writes the name after it (`DrawNumber` in `ImGuiPropertyVisitor`). Labels are built in a stack buffer, never in an `eastl::string` per frame.
- **Toolbars and empty states.** Every control of a toolbar (the viewport's size, safe-area and view combos, Rotate, Overlays, the custom W / H) has an icon and an `ItemTooltip` that says what it is, so a bare "Free" or "Auto" is never alone. A combo shows its icon and current value from a literal (`ICON_LC_EYE " Auto"`) or, for a name that varies, from a member string made again only when the value changes. A panel with nothing to show calls `EmptyState(icon, text)` (a large icon and one wrapped line, centered; it takes only the room it needs, so it can sit inside a section) instead of a bare `TextDisabled`.
- **Bars.** `EditorLayoutWidget` draws two fixed-height children of its `##EditorRoot` host (not windows, so they are not draggable and not in `imgui.ini`, and the dock layout is unchanged): `MainToolbar` under the menu bar and `StatusBar` at the bottom; the dock space gets the height that is left (`CloseItemGap` pulls the cursor back over ImGui's gap so the three touch). Heights are the frame height plus the theme's padding, never a pixel constant. The toolbar is **state only**: Play / Stop, Pause and Step change `EditorPlayModel` (pure, `Stopped` / `Playing` / `Paused`, owned by the widget) and nothing in the engine reads it yet; the tooltips say so. The status bar shows the mean FPS and frame ms of the last `kMeterWindow` frames (`FrameMeter`, rounded, coloured by `ClassifyFrame` against the fixed 60 fps `kFrameBudgetMs`: `success`, `warning` up to twice over, `error` above; the rule of the Profiler panel's bars, which stays its own code), the allocations of the last frame (only when `AllocTracker::kEnabled`), the control API (`ControlServerStatus` published by `Application`: `off`, or the port and the clients), the active game, the active scene and the engine's git branch (`ReadGitBranch`, read once in `Initialize()`; a `.git` file is followed, nothing found leaves it out). The models (`EditorPlayModel`, `StatusBarModel`, `GitBranch`) have no ImGui and are tested alone. **Zero allocations in a steady frame:** numbers live in fixed `char` buffers and are formatted again only when the meter's `Version()`, the allocation count or the control status moved; a name is copied into a member `eastl::string` only when its `PoolString` differs from the last one seen; no `Format(...)` and no heap argument per frame. `EditorBarsTest` holds it with a counter check that bites only with `ENGINE_PROFILER_ALLOC` (the profile preset).
- **Owner's note.** Text is rasterized by stb_truetype and may look soft at 13..15 px. The fix is `imgui_freetype`, which lives in the vendored `src/Modules/imgui/` and needs the owner's yes.

## Scene Editor Conventions

Scene editor code is split across focused layers:

- `SceneEditorWidget`: orchestration (selection flow, scene-level actions, window structure).
- `ComponentInspectors`: per-component editing. `RenderComponentInspector` uses a custom inspector registered with `RegisterComponentInspector` when there is one, and otherwise the generic `ImGuiPropertyVisitor` driven by the component's generated `AcceptPropertyVisitor`.
- `ImGuiPropertyVisitor`: the `IPropertyVisitor` implementation that renders ImGui controls for reflected fields.

Rules:
- Keep selection and scene navigation in `SceneEditorWidget`; keep component field editing in `ComponentInspectors`. Do not duplicate edit logic in the scene widget.
- A new editable field only needs `BE_REFLECT_FIELD`; the generic visitor shows it. Write a custom inspector only when the generic one is not enough.
- Scene editor behavior stays aligned with `config/SceneConfig.xml`. New editable scene/component fields are represented there and then surfaced through inspectors.
- Editor panels build their window in `Update()` (see "ImGui in `Update()`" above).
- **UI elements.** For a node with a `UICanvasComponent` the inspector shows a "UI elements" section above the generic fields: the element tree and, for the selected element, `InspectUIRect` (`UIRectInspector`). It edits the authored `style.rect`, live, and sets the scene dirty; an edit in an instance of a node file is saved as an `<elements>` override in the scene file, never into the node file or a `.ui.xml`. The layout math is in `UIRectEdit` / `UIAnchorPresets`, not in the widget. The selected element is an `IntrusivePtr` in `SceneEditorWidget`, dropped when the node changes or the scene is replaced.
- Save replaces only the `<scene>` of the active scene in `SceneConfig`, matched by its `name` (`WriteSceneToConfig`, `SceneEditor/SceneConfigWriter.h`, no ImGui). The other scenes, their order and the comments in the DOM around them stay (`XmlDocument` loads with the default pugixml flags, which drop comments, so a comment of the file on disk is already gone from the DOM that `SaveConfig` writes); a scene without an element is appended. The scene's attributes come from `Scene::Serialize`, so a new reflected field of `Scene` is saved without a change there; the nodes are written by hand (`name`, `layer` when not 0, the components through `Serialize`), except an instance of a node file (`SceneNode::GetSourceRef()`): it becomes its `<node ref>` with only the overrides that differ (`BuildNodeReference`), or, when that cannot be (no loader, the file gone, a component gained, lost or reordered, the round trip fails), inline with a line in the `notes` of `WriteSceneToConfig(configRoot, scene, loader, notes)`, which `SaveScene` logs as warnings with the loader of the layered `FileSystem` (`Scene/CLAUDE.md`, "Node files"). Tested without ImGui in `tests/BECore/SceneEditorSaveTest.cpp` on a document of its own and a temporary file; never test it through `ConfigManager::SaveConfig` on a shipped config, that overwrites the file in the repository.

## Config Editor

`ConfigEditorWidget` edits any loaded XML config. Field typing comes from `ConfigFieldSchema` (registered fields per config path, for example `LoggerConfig` → `sink/@type`), the controls from `FieldInspectors`, and edits stay in `StagedChanges` until the user saves. New config attributes with a fixed value set should be registered in the schema, in `ConfigEditorWidget::Initialize`:

- a `type` attribute that the loader resolves through `AbstractFactory<Base>` is registered with `RegisterFactoryTypes<Base>(config, "element/@type")`. The options are the class names the factory has registered (sorted), exactly the strings the loader accepts, so the list cannot drift from the code. Do not mirror them in an enum: the `CORE_ENUM` that the generator emits for a `FACTORY_BASE` has other names and another order;
- an attribute read through `EnumUtils<E>` is registered with `RegisterEnum<E>`; `RegisterFlags` takes the flag names of a `|`-joined value.

An `Enum` combo shows a current value that is not among the options (a typo, or a name the code no longer has) instead of an empty box and marks it `(not a known value)`; choosing an option replaces it. `tests/BECore/ConfigFieldSchemaTest.cpp` (only with `BE_WITH_EDITOR`) checks that the options are creatable by the factory and that the shipped `LoggerConfig.xml` uses only offered values. The save path is tested without ImGui in `tests/BECore/ConfigEditorSaveTest.cpp` (only with `BE_WITH_EDITOR`): the edit goes through `StagedChanges::Set` and `ApplyTo` on a copy of the config, `XmlDocument::SaveToFile` writes a temporary file, and the file is loaded back into the real consumer. Never test it through `ConfigManager::SaveConfig` on a shipped config: that overwrites the file in the repository.
