# Starting the control API (flags, config, status)

The module: `src/Modules/BECore/Control/CLAUDE.md`.

The API is off by default: a game has to be asked for it. `Application::Initialize()` loads the reflected `ApplicationConfig` (`LoadApplicationConfig()`) and calls `ResolveControlSettings(args, load)` right after the core services are up (before the window exists) and, when the API is enabled, starts the `RemoteControl` server after `GameManager::Initialize()`, so the game methods are registered before the first client connects. A panel can ask for it later (`ApplicationEvents::StartControlServerRequestEvent`, the Generate panel): the default port, else a free one; a failure is logged.

| Command line | `ApplicationConfig.xml` root attribute | Meaning |
|--------------|----------------------------------------|---------|
| `--control`, `--control=false` | `control="true"` (or `false`, `1`, `0`) | start the WebSocket server; the value form of any boolean flag below can also switch off what the file turned on |
| `--control-port=N` | `controlPort="N"` | port 0 to 65535; 0 asks the system for a free one; default `kDefaultControlPort` (8765) |
| `--headless` | `headless="true"` (or `false`, `1`, `0`) | no window: the SDL software renderer on the dummy video driver, a screenshot is the way to see the game (`SDL/CLAUDE.md`, "Headless and screenshots"); needs the API; with `--editor` the editor runs in the memory window (`status.runMode` says which mode runs) |
| `--window=WxH`, `--density=D` | none (flags only: `ControlFlags`) | the start size (window units) and pixel density of a headless window, within `WindowLimits`; need `--headless` (`.claude/rules/control-window-api.md`) |
| `--backend=software\|sdl-gpu\|vulkan`, `--hidden-window` | none (flags only: `ControlFlags`) | the renderer backend of one run (`RenderBackendChoice`; absent is the config's `renderer`, software when headless) and a real window created hidden, for a GPU benchmark nobody watches. `--hidden-window` needs the API and refuses `--headless`; `software` needs `--headless`; `sdl-gpu` and `vulkan` refuse it (the dummy driver has no GPU surface). A bad spelling is an error naming `--backend` |
| `--content-overlay=<dir>` | none (a per-run flag read from `CommandLine` like a game's own, not a `ControlSettings` key) | every editor write goes to `<dir>/<mount>/<path>` instead of the layer the file was found in; the checkout is not written (`FileSystem/CLAUDE.md`, "Content overlay") |
| `--manual-clock` | `manualClock="true"` (or `false`, `1`, `0`) | frames run only on `step` (see "Manual clock and `step`"); needs the API |
| `--replay=FILE`, `--replay-exit` | none | plays a replay file once the game is up; exit code 0 or 1, and `--replay-exit` also quits; both need the API and the manual clock (`Games/CLAUDE.md`, "Record and replay") |

`Application::PublishControlStatus()` copies the server's state (`IsRunning()`, `GetPort()`, `WebSocketServer::GetClientCount()`) into `ControlService::SetServerStatus()` every frame, the idle pass of the manual clock included, and `Cleanup` resets it. Main thread only; the editor's status bar reads `GetServerStatus()`. A build without `BE_WITH_REMOTE_CONTROL`, or with the API off, never sets it (`listening == false`).

The file half is the reflected `ApplicationConfig` read with strict values (`reflection-module.md`): an attribute that is not a boolean or not a number of the field's type is an error of the load under the attribute's name, and the error of one of the four control attributes stops the start-up (also when the API is off or a flag would override it). Errors of the other fields (`mode`, `type`) are not control errors: `Application::Initialize()` logs them once after the settings were resolved.

The flag half is **one `CommandLineDeserializer`** (`Application/`) over a copy of the file's config and a `ControlFlags` (`Control/ControlFlags.h`: `--replay`, `--replay-exit`, `--window`, `--density`, `--backend`, `--hidden-window`, which have no attribute), so each flag overrides one field and an absent flag leaves the file's value; the flag of a field is `--` and its name in kebab case. Only the ten names of the table are flags (the `keys` list in `ControlSettings.cpp`): `type`, `renderer`, `path`, `mode` stay names a game may use. The grammar is the strict one of the config (`StrictText`): a boolean flag is bare (true) or `=true|false|1|0`, a flag that needs a value (`--control-port`, `--replay`, `--window`, `--density`, `--backend`) is an error when bare, a number is read whole (a leading `+` and surrounding spaces are fine, `70000` for a port is not), and the error names the flag. A repeated flag takes its first form (`Control/CLAUDE.md`), so a flag appended to a launcher's command (`tools/control/game_process.py`) cannot move its port. The rules between settings stay in `ResolveControlSettings`: a value that cannot be read, `--control-port` / `--manual-clock` / `--headless` while the API stays off, a replay without the manual clock, `--window` / `--density` without `--headless` or outside `WindowLimits`, and the `--backend` / `--hidden-window` combinations of the table are errors: the start-up stops with a line in the log (`Application::Initialize()` flushes it itself, nothing else does before the first frame), so nobody who asked for the API is left waiting. A port that is taken stops it the same way. Other arguments are ignored (a game may have flags of its own), but one that is near to a flag of this table (`--contol-port`) is a warning in `ControlSettings::warnings`, which `Application` logs as `Config 'Command line': ...`; to refuse it, the diagnostics of the reader would be `Error`. What headless, the window size and the density mean for the window reaches the SDL module as `ApplicationOptions` (`ApplicationFabric::Create(config, options)`), not as ControlSettings, which it does not see.
