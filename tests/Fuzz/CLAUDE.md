# tests/Fuzz: fuzz targets for input nobody trusts

Library `BagiFuzzTargets`: one plain function per kind of untrusted input, `void Fuzz<Name>(const uint8_t* data, size_t size)` in `BECore::Fuzz` (`FuzzTargets.h`), the deterministic mutator (`FuzzMutator.h`) and the writer of the generated seeds (`FuzzSeeds.h`). Two ways run the same functions:

- **`FuzzCorpusTest`** (`tests/BECore`, part of `BagiEngineTests`, so of every `ctest`): replays every file of `corpus/<folder>/` through its target, then `BAGI_FUZZ_ITERATIONS` (default 50000, about 2 s in Debug) mutations of the seeds taken in turn, with the generator of `FuzzMutator` (xorshift64*, fixed seed per target): the same bytes on every platform and every run. `BAGI_FUZZ_ITERATIONS=2000000 ctest --preset macos-debug -R FuzzCorpus` is a longer run with no libFuzzer. An engine `ASSERT` reached by input is a gtest failure (`AssertBridge`), a `FUZZ_CHECK` or a sanitizer report kills the process.
- **libFuzzer**, for long runs: preset `macos-fuzz` (Homebrew LLVM, ASan + UBSan on all code, asserts and expects ON; `cmake/CLAUDE.md`, "Fuzzing") and `macos-fuzz-shipped` (the same with Release and asserts and expects OFF), one executable `BagiFuzz<Name>` per target, made by `be_add_fuzz_executable(<Name> <Function>)` in `CMakeLists.txt` over the same function. `InstallAssertAbort()` (`FuzzAssertAbort.h`) makes an engine assertion that an input reaches abort the run, because a libFuzzer process has no gtest. `tools/fuzz/run_fuzzers.py` runs every executable for N seconds over a copy of its corpus and keeps the findings in `build/<preset>/fuzz-artifacts/` (the commands: `.claude/rules/build-project.md`, "Fuzzing"). The corpus test also runs under the sanitizers: `ctest --preset macos-fuzz -R Fuzz`.
- **Why the corpus also runs with asserts off** (`macos-release`, `macos-fuzz-shipped`): an `ASSERT` or `EXPECT` that compiles out leaves the code after it to run on the bad input, so a check that only an assertion held is a hole in a shipped build. The properties of a target are `FUZZ_CHECK`s for that reason, and the hook of `InstallAssertAbort()` never fires there. Running all of `BagiEngineTests` there is the entry `sanitizers`.

## The targets

| Target (`Fuzz<Name>`) | Corpus folder | Guards |
|-----------------------|---------------|--------|
| `BinaryDeserializer` | `binary` | `BinaryDeserializer::LoadFromBuffer` (`BECore/Reflection`) |
| `XmlDeserializer` | `xml` | `XmlDeserializer::LoadFromString`, lenient and strict (`BECore/Reflection`) |
| `SaveEnvelope` | `save` | `SaveGameService::Peek` / `Load` (`BECore/Save`) |
| `SceneNode` | `scene` | node references and component deserialization (`BECore/Scene`) |
| `WebSocketFrame` | `ws_frame` | `WebSocketFrameParser`, both peers (`RemoteControl`) |
| `Handshake` | `ws_handshake` | the opening handshake, request, response and URL (`RemoteControl`) |
| `RoomProtocol` | `room_protocol` | `ParseClientMessage`, `ParseServerMessage`, `SanitizePlayerName` (`Rooms`) |
| `RoomHub` | `room_hub` | `RoomHub` fed with operations over the demo game (`Rooms`, `RoomServer`) |
| `ControlRequest` | `control_request` | `ControlService::Post` with the builtins and the game methods (`BECore/Control`) |

Not covered yet: the sockets and threads of the transports (`WebSocketListener`, `RoomWebSocketServer`: the next slice, `hostile.py`), `LoadFromFile` of both readers, the rest of the control methods (`ui_*`, `screenshot`, the profiler: they need a scene, a renderer or a profiler), and the content and saves as consumers see them in a release build.

## A target

- Feeds the bytes to the real code and checks properties inside (`FUZZ_CHECK(cond)`: prints and `std::abort()`s in every build; not the engine `ASSERT`, which compiles out in Release). It is exception free like the engine: a malformed input is a refusal or undefined behaviour, and the second is the finding.
- Reads no file and no clock, uses no service that needs the repository directory, and never sizes an allocation by a number read from the input unless the code under test checked it. State is local to the call: the same input twice gives the same result.
- Bounded work: the cost of one input is limited by a budget in the target (`FuzzBinaryDeserializer`: 48 entries per document, four array elements), because a reader that finds a name by scanning its scope costs scope-size per read.
- To add one: `Fuzz<Name>.cpp` (picked up by the glob), the declaration and a row in `FuzzTargetList()` (`FuzzTargets.h/.cpp`; the last field is the cost weight: the corpus test runs `BAGI_FUZZ_ITERATIONS` default divided by it, so a target that touches the disk gets a big one), a folder `corpus/<folder>/` with seeds, and a `be_add_fuzz_executable` line in `CMakeLists.txt`. `run_fuzzers.py` reads the rows of `FuzzTargets.cpp` with a regex: keep one row per line in the shape `{"Name", &FuzzName, "folder", weight}`.
- `FuzzBinaryDeserializer` also feeds the input again under a header that is true (magic, version, payload size), because any change of length breaks the payload size and the load stops before the validation of the entries. It walks the loaded document by parsing the bytes itself (`BinaryFormat::ParseEntry`) and reads every name with all 26 overloads: only the overload of the entry's own type may succeed and it returns the bytes of the entry. It then loads the same buffer into a fresh reader and again into the walked one: equal digests. It does not cover `LoadFromFile`.
- **Reflected probe** (`tests/BECore/FuzzProbe.h`, a scan dir of `BECoreModule`): `ProbeState` has a field of every kind a content file or a save has. The generated code is included in `FuzzProbeAccess.cpp` only (the `.gen.hpp` holds non-inline definitions), every other file uses `ProbeState::Deserialize` through `FuzzProbeAccess.h` (`MakeFilledProbe`, `DigestProbe`).
- `FuzzXmlDeserializer`: reads the text lenient and strict. A second parse by pugixml alone gives the walk its names; every attribute and element is read with all 13 overloads. Strict refusals are checked against a grammar of integers and booleans written in the target (not the reader's code): same verdict, same value, one error per refusal, the target untouched; a float that is accepted is finite. The probe type (it holds a list of its own kind, as a UI tree does) is read from the same document by a fresh reader, by the same one again and from a copy of the text one byte into its buffer: equal digests. A document that does not parse loaded on top of a good one leaves nothing readable.
- `FuzzSaveEnvelope`: the bytes (and the same under a true header) are a slot of a `SaveGameService` in a folder of the process (removed at exit); `Peek` and `Load` with the probe state. A refusal on game or version never calls the reader and leaves the state as it was, every refusal has a `detail`, a `Load` that succeeds agrees with `Peek` on game and version. The disk makes one input slow (cost weight 10).
- `FuzzSceneNode`: the input is `scene text, NUL, node file` (no NUL: the whole input is the node file under a scene with one reference). Every reference is expanded or reported, none is left, a second expansion does nothing; then `LoadSceneManager` deserializes the whole scene, components included. No window, renderer or `CoreManager` is needed: the component classes are registered by the engine core that the target links whole. The texts are copied into buffers of their own because pugixml reads a text that looks like UTF-16 or UTF-32 as words (misaligned in the middle of a buffer). It does not instantiate nodes into a live scene (`Scene::InstantiateNode` needs a scene with services).
- `FuzzWebSocketFrame`: the first byte of the input is `[chunk pattern: 4 bits | message limit: 3 bits | sender: 1 bit]` (`FuzzWebSocketInput.h`, which the seed writer shares), the rest is the byte stream of a `WebSocketFrameParser`. **Differential:** the whole stream at once is the reference, any chunking must give the same messages and the same first error; after an error `Pop` keeps returning that error whatever is fed (and the parser holds nothing). A text or binary message is at most the limit, a control message at most 125 bytes, and the messages re-encoded in the form of the other role (masked or not) are read back equal. Pattern 0 reads in one piece, so the chunked run of the same input uses pattern 1 (a byte at a time).
- `FuzzHandshake`: the first byte picks one of five policies (loopback, public with an origin list, with `*`, with `allowMissingOrigin = false`, with a health path), the rest is read as a request head (`ParseHandshakeRequest`, `IsHealthCheckRequest`), as a response head (`CheckServerHandshakeResponse` against the key of RFC 6455 section 1.3) and as a URL (`ParseWebSocketUrl`). Ties between them: an accepted request gets an accept response that a client of that key accepts and a client of another key does not; a health check is never a handshake; a refusal has a known status and is no accepted response; every refusal message, of the request, the response and the URL, is printable ASCII and short, whatever the peer sent (it reaches a log and a reject body); a parsed URL gives a `Host` header that parses back to the same host and port, and the request built for it is accepted by a public policy with its key. Both targets need the sockets of `RemoteControlModule`, like `BagiEngineTests` itself (the web build has no tests).

- `FuzzRoomProtocol`: the first byte is `[limit: 2 bits | side: 1 bit]` (`FuzzRoomInput.h`), the rest is one message read by `ParseClientMessage` or `ParseServerMessage` under the real size limit or a small one. A refusal carries one of the documented codes and a tidy message, and is `message_too_large` exactly when the text is over the limit. A client message read back through `SerializeClientMessage` is the same message; a server message rebuilt by the `Make*Message` builders reads back and builds the same text. The same bytes also go through `SanitizePlayerName`: idempotent, strictly valid UTF-8 (checked against the Unicode ranges, not the reader's code) with no control character, trimmed, 1 to 24 bytes, a piece of the input.
- `FuzzRoomHub`: a `RoomHub` over the demo card game (the leaky one is not registered) fed with a stream of operations `[op: 2 bits | connection: 6 bits][length: u16 LE]` (+ `length` bytes of text for a message; op 0 message, 1 connect, 2 disconnect, 3 tick by `length` ms), at most 200 per input. Small limits (3 rooms, 6 connections, 2048-byte messages) so the refusals of a full hub are in reach; the clock and the random function are injected and fixed (`RoomHubInput::MakeRandom`), so the codes and tokens of a recorded session replay. Judged on every text the hub sends: valid JSON with `v` and `type`; a token appears only in `joined`, to a connection that sent it or got it first; the seat of a member stays what `joined` said unless it asked for another and never changes after the first `view`; a card that is not in the connection's seat, nor in the table of its own view, nor in the text it sent itself, is a leak (`WireJudge.h`, the judge of the socket scenarios, on the text alone: the hub keeps its rooms private, so the live game is out of reach). After every operation the hub's connection count is the one the transport was told, within the limits, and a connection that was in a room still has it; at the end everyone leaves and the rooms and connections are gone after a long tick. The seeds are sessions recorded against a real hub by `FuzzRoomSeeds.cpp` (`Recorder`).
- `FuzzControlRequest`: `ControlService` with the builtins and the game methods registered (no game is active, so the game methods answer their `no_active_game`; the handlers that need a window, a renderer or the profiler are not registered): `Post`, `Drain`, a few `EndFrame`s, `Shutdown`; exactly one answer, an object with the request's `id` (null when there is none), `ok` with a `result` or an `error` with a code and a message. A first byte of `0xFF` (not JSON) pads the input to over `kMaxRequestBytes`, which must be `request_too_large`.

- **What the targets cannot show.** `PoolString` interns the text of an input (a `PoolString` field, an error message) and never frees it, so a long run grows its memory without bound (`rss_limit_mb` of `run_fuzzers.py` ends it): the reader limits keep one load small, the pool itself is a known gap. An array of more than `kMaxArrayElements` needs a seed of 256 KiB, over `kMaxFuzzInputSize`: its test is in `ReaderLimitsTest`, not in the corpus. `LoadFromFile` of both readers is not fuzzed (a path is not a byte input): `ReaderLimitsTest`.

## The corpus

- `corpus/<folder>/`, small files (a corpus file over 64 KiB, `kMaxFuzzInputSize`, fails the replay), real inputs where a real one exists (a file copied from `config/`, a message made by the real builders), no hand-typed hex.
- Generated seeds come from `MakeGeneratedSeeds()` (`FuzzSeeds.cpp`), made with the engine's own writers. After a format changes, `FuzzCorpusTest.GeneratedSeedsAreTheCommittedFiles` fails: write them again with `BAGI_FUZZ_WRITE_SEEDS=<repo>/tests/Fuzz/corpus build/<preset>/bin/BagiEngineTests --gtest_filter=FuzzCorpusTest.WriteSeeds` and commit the files.
- `.gitattributes` marks `corpus/**` binary: a seed is raw bytes (a request head has CRLF in it), and `text=auto eol=lf` would rewrite it in the repository and break `GeneratedSeedsAreTheCommittedFiles` on a fresh checkout.
- A finding becomes a regression seed `fix-<what>` in the folder of its target, committed with the fix and a test next to the fixed code. Seeds are never deleted to make a run pass.

## The mutator

`Mutate` / `ApplyMutation` (`FuzzMutation`): flip a bit, set a byte to 0 / 0x7F / 0x80 / 0xFF, set four bytes to `0xFFFFFFFF` / `0x7FFFFFFF` / `0x80000000` / 0 (length and count fields), insert, delete and duplicate a block, truncate, splice from another seed; at most 64 KiB. A kind the input cannot take (an empty input, three bytes for a word, no other seed) does the nearest one that fits and says which. Own generator only: the `<random>` distributions and `std::random_device` differ between platforms. A change of the generator or of a mutation changes every corpus run: `FuzzMutatorTest.SameSeedGivesTheSameBytes` pins a hash, update it on purpose.
