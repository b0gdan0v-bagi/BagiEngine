# tests/Fuzz: fuzz targets for input nobody trusts

Library `BagiFuzzTargets`: one plain function per kind of untrusted input, `void Fuzz<Name>(const uint8_t* data, size_t size)` in `BECore::Fuzz` (`FuzzTargets.h`), the deterministic mutator (`FuzzMutator.h`) and the writer of the generated seeds (`FuzzSeeds.h`). Two ways run the same functions:

- **`FuzzCorpusTest`** (`tests/BECore`, part of `BagiEngineTests`, so of every `ctest`): replays every file of `corpus/<folder>/` through its target, then `BAGI_FUZZ_ITERATIONS` / cost weight mutations of the seeds taken in turn, with the generator of `FuzzMutator` (xorshift64*, fixed seed per target): the same bytes on every platform and every run. Unset, it only replays; the `extended` ctest entry `BagiFuzzMutations` sets it, and `BAGI_FUZZ_ITERATIONS=2000000 bin/BagiEngineTests --gtest_filter='FuzzCorpus/*'` from `build/<p>` is a longer run with no libFuzzer. An engine `ASSERT` reached by input is a gtest failure (`AssertBridge`), a `FUZZ_CHECK` or a sanitizer report kills the process.
- **libFuzzer**, for long runs: preset `macos-fuzz` (Homebrew LLVM, ASan + UBSan on all code, asserts and expects ON; `cmake/CLAUDE.md`, "Sanitizers and fuzzing") and `macos-fuzz-shipped` (the same with Release and asserts and expects OFF), one executable `BagiFuzz<Name>` per target, made by `be_add_fuzz_executable(<Name> <Function>)` in `CMakeLists.txt` over the same function. `InstallAssertAbort()` (`FuzzAssertAbort.h`) makes an engine assertion that an input reaches abort the run, because a libFuzzer process has no gtest. `tools/fuzz/run_fuzzers.py` runs every executable for N seconds over a copy of its corpus (the commands: `.claude/rules/build-project.md`, "Fuzzing"). The corpus test also runs under the sanitizers: `ctest --preset macos-fuzz-all -R Fuzz`.
- **Why the corpus also runs with asserts off** (`macos-release`, `macos-fuzz-shipped`): an `ASSERT` or `EXPECT` that compiles out leaves the code after it to run on the bad input, so a check that only an assertion held is a hole in a shipped build. The properties of a target are `FUZZ_CHECK`s for that reason, and the hook of `InstallAssertAbort()` never fires there.

Not covered: the sockets and threads of the transports (`WebSocketListener`, `RoomWebSocketServer`: `tools/rooms/hostile.py` over real sockets), `LoadFromFile` of both readers (a path is not a byte input), image and Ogg assets (vendored decoders), the editor's user files (`WriteFileAtomically`), the other control methods (`ui_*`, `screenshot`, the profiler: they need a scene, renderer or profiler), and the pool of interned strings, which never frees. Cost weights (the last field of a row) follow the time of one input: 1 for a plain parser, 2 to 8 for tables and geometry, 10 to 15 for a target on the disk, a hub or the web compiler; a new target keeps its share of `BAGI_FUZZ_ITERATIONS` near 2 s in Debug.

## A target

- Feeds the bytes to the real code and checks properties inside (`FUZZ_CHECK(cond)`: prints and `std::abort()`s in every build; not the engine `ASSERT`, which compiles out in Release). It is exception free like the engine: a malformed input is a refusal or undefined behaviour, and the second is the finding.
- Reads no file and no clock, uses no service that needs the repository directory, and never sizes an allocation by a number read from the input unless the code under test checked it. State is local to the call: the same input twice gives the same result.
- Bounded work: the cost of one input is limited by a budget in the target (`FuzzBinaryDeserializer`: 48 entries per document, four array elements), because a reader that finds a name by scanning its scope costs scope-size per read.
- To add one: `Fuzz<Name>.cpp` (picked up by the glob), the declaration and a row in `FuzzTargetList()` (`FuzzTargets.h/.cpp`; the last field is the cost weight, which divides `BAGI_FUZZ_ITERATIONS`), a folder `corpus/<folder>/` with seeds, and a `be_add_fuzz_executable` line in `CMakeLists.txt`. `run_fuzzers.py` reads the rows of `FuzzTargets.cpp` with a regex: keep one row per line in the shape `{"Name", &FuzzName, "folder", weight}`.
- `FuzzBinaryDeserializer` feeds the input again under a true header (versions 1 to 3 stay as they are, anything else becomes the current one), since a changed length breaks the payload size first. It walks the loaded document by parsing the bytes itself (`ParseEntry`; version 2: `ParseStringTable`, `ParseEntryV2`; version 3: also `ParsePoolSection`, `ParseEntryV3`, its texts by index: an accepted document that does not parse is a finding) and reads every name with all 26 overloads: only the overload of the entry's own type may succeed (`String` and `PoolString` take tag 12 and 15) and it returns the entry's bytes or section text. The same bytes through a fresh reader, `LoadFromView` and the walked reader: equal digests.
- `FuzzBinaryContent`: each input as it is, under a true header and with the checksum of its pool section made true (a mutated section stops at the checksum otherwise), through `LoadContentBytes` with `verifyHashes` on and off. Checking more never accepts more; with it on every adopted string has the hash of its text, and every string has the text of its entry in the stream and, when its hash is right, is the pool's `Find`. **Differential** against `LoadFromView` of the whole stream: the content is accepted exactly when the stream is and its pool section's checksum is right (an empty section has none to check), `LoadFromContent` has the same verdict, and the shared walk of `FuzzBinaryWalk.h` reads equal digests through both. This is the only corpus of `PoolString::AdoptBlock`: its seeds are small because every accepted input adds a block to the pool.
- **Reflected probe** (`tests/BECore/FuzzProbe.h`, a scan dir of `BECoreModule`): `ProbeState` has a field of every kind a content file or a save has. The generated code is included in `FuzzProbeAccess.cpp` only (the `.gen.hpp` holds non-inline definitions), every other file uses `ProbeState::Deserialize` through `FuzzProbeAccess.h` (`MakeFilledProbe`, `DigestProbe`).
- `FuzzXmlDeserializer`: reads the text lenient and strict. A second parse by pugixml alone gives the walk its names; every attribute and element is read with all 13 overloads. Strict refusals are checked against a grammar of integers and booleans written in the target (not the reader's code): same verdict, same value, one error per refusal, the target untouched; a float that is accepted is finite. The probe type (it holds a list of its own kind, as a UI tree does) is read from the same document by a fresh reader, by the same one again and from a copy of the text one byte into its buffer: equal digests. Diagnostics `Warn` and `Off` give the same digest and error count.
- `FuzzJsonDeserializer`: the text goes to `JsonTape::Parse` and `JsonDeserializer::Load` as it is (a refusal is one `Invalid JSON` error; every read then fails). No second parser is the oracle: the invariants are the ones the tape has alone. **Write back:** a text the tape takes is written by `WriteJson(JsonWriter&, JsonView)` into a text the tape takes and `WriteJson` writes again unchanged, and by `WriteJsonSorted` into one that `JsonEquals` itself and `WriteJsonSorted` writes again unchanged. `ProbeState`, `ProbeNode` and `ProbeShapes` are read from the text under `Off`, `Warn` and `Error`: the same digest in all three, the same error count under `Off` and `Warn`, and a fresh object and a reader that loads twice read it alike. **Round trip:** the loaded state saved by `JsonStreamSerializer` reads again under `Error` with no error and the same digest, and saves to the same text. **Calls:** the document is the argument object of every method of `ProbeCalls`, read from text and from a `JsonView` of a tape (the way `call_method` reads) with one outcome: `bad_arguments` leaves the object as it was, a call that ran counted itself once, an unknown name is `unknown_method`, the result is one object with at most `result`.
- `FuzzSaveEnvelope`: the bytes (and the same under a true header) are a slot of a `SaveGameService` in a folder of the process (removed at exit); `Peek` and `Load` with the probe state. A refusal on game or version never calls the reader and leaves the state as it was, every refusal has a `detail`, a `Load` that succeeds agrees with `Peek` on game and version.
- `FuzzSceneNode`: the input is `scene text, NUL, node file` (no NUL: the whole input is the node file under a scene with one reference). Every reference is expanded or reported, none is left, a second expansion does nothing; then `LoadSceneManager` deserializes the whole scene, components included. No window, renderer or started `CoreManager` service is needed (the loader reads the command line for the diagnostics mode): the component classes are registered by the engine core that the target links whole. The texts are copied into buffers of their own because pugixml reads a text that looks like UTF-16 or UTF-32 as words.
- `FuzzWebSocketFrame`: the first byte of the input is `[chunk pattern: 4 bits | message limit: 3 bits | sender: 1 bit]` (`FuzzWebSocketInput.h`, which the seed writer shares), the rest is the byte stream of a `WebSocketFrameParser`. **Differential:** the whole stream at once is the reference, any chunking must give the same messages and the same first error; after an error `Pop` keeps returning that error whatever is fed (and the parser holds nothing). A text or binary message is at most the limit, a control message at most 125 bytes, and the messages re-encoded in the form of the other role (masked or not) are read back equal. Pattern 0 reads in one piece, so the chunked run of the same input uses pattern 1 (a byte at a time).
- `FuzzHandshake`: the first byte picks one of five policies (loopback, public with an origin list, with `*`, with `allowMissingOrigin = false`, with a health path), the rest is read as a request head (`ParseHandshakeRequest`, `IsHealthCheckRequest`), as a response head (`CheckServerHandshakeResponse` against the key of RFC 6455 section 1.3) and as a URL (`ParseWebSocketUrl`). Ties between them: an accepted request gets an accept response that a client of that key accepts and a client of another key does not; a health check is never a handshake; a refusal has a known status and is no accepted response; a refusal message is short printable ASCII; a parsed URL gives a `Host` header that parses back to the same host and port, and the request built for it is accepted by a public policy with its key.

- `FuzzRoomProtocol`: the first byte is `[limit: 2 bits | side: 1 bit]` (`FuzzRoomInput.h`), the rest is one message read by `ParseClientMessage` or `ParseServerMessage` under the real size limit or a small one. A refusal carries one of the documented codes and a tidy message, and is `message_too_large` exactly when the text is over the limit. A client message (`public` and `list_rooms` included) read back through `SerializeClientMessage` is the same message; a server message rebuilt by the `Make*Message` builders reads back and builds the same text; a `rooms` message that was read has at most the cap of entries, well-formed codes, `taken <= seats <= 64` and plain options. The same bytes also go through `SanitizePlayerName`: idempotent, strictly valid UTF-8 with no control character, trimmed, 1 to 24 bytes, a piece of the input.
- `FuzzRoomHub`: a `RoomHub` over the demo card game (the leaky one is not registered) fed with a stream of operations `[op: 2 bits | connection: 6 bits][length: u16 LE]` (+ `length` bytes of text for a message; op 0 message, 1 connect, 2 disconnect, 3 tick by `length` ms), at most 200 per input. Small limits so the refusals of a full hub are in reach; the clock and the random function are fixed (`RoomHubInput::MakeRandom`), so a session replays. Judged on every text the hub sends: valid JSON with `v` and `type`; a token appears only in `joined`, to a connection that sent it or got it first; the seat of a member stays what `joined` said unless it asked for another and never changes after the first `view`; a card outside the connection's seat, its own view's table and the text it sent is a leak (`WireJudge.h` on the text alone); a `rooms` text goes to a connection in no room and names only codes that were answered to a `create_room` with `"public":true` (so a private code is on no list), each existing, once, with a free seat and `started` false. After every operation the hub's connection count is the one the transport was told, within the limits, and a connection that was in a room still has it.
- `FuzzControlRequest`: `ControlService` with the builtins, the game methods (no game active) and the scene methods over a scene local to the call (none that needs a window, a renderer or the profiler) and the roots `state` and `probe` over a filled `ProbeState` and a `ProbeCalls`, so the by-name methods see real data: `Post`, `Drain`, a few `EndFrame`s, `Shutdown`; one answer, an object with the request's `id` (null when there is none), `ok` with a `result` or an `error` with a code and a message. A first byte of `0xFF` pads the input over `kMaxRequestBytes`: `request_too_large`.
- `FuzzWebUi`: the input is `html, NUL, css` (no NUL: all of it is the html); the loader of linked style sheets gives the css part for any `href`. `Compile` twice gives the same text and the same report; the report holds at most `kMaxIssues` entries (+ the one that says more follow), each with a known source (`html`, `css`, `css:<href>`), a line inside the input, a message of at most `kMaxMessageBytes` and no control character; the text of a document the report calls clean is well-formed XML; the text goes through `XmlDeserializer` and `UIScreenContent::Deserialize` as `UIDocument` reads it.
- `FuzzUiTables`: the input is an XML text, and a root named `UIStrings` or `UIThemes` picks the table (anything else goes to both, so the loaders' answer to a file of the wrong kind is covered). Local `UIStrings` and `UIThemes` instances (pure data). The problems a load returns are short lines with no control character. The expected content is read from the document by pugixml alone (the first occurrence of a good key or token wins); the table has it, has no empty key, token, theme or language and no duplicate, resolves `{#key}` to the text of the key, and loading the same file again or into a fresh table changes nothing.

- `FuzzPanelAsset`: the input is the XML text of a panel file. `LoadPanelAsset` twice gives the same issues, at most `kMaxIssues`, each short with no control character. **Oracle:** `AssetJudge` walks the returned tree and decides from the format alone (limits, well-formed unique ids, required fields, binding and path syntax): there is no issue exactly when the tree has no violation and the deserializer alone, under the loader's strict diagnostics, has no finding. A valid asset written by `XmlSerializer` loads again with no issue and writes the same text.

- `FuzzUiGeometry`: the input is rounds of fields (`FuzzUiGeometryInput.h`: one `Transfer` description that the target reads and the seed maker writes), floats as raw bits so NaN, infinity, denormals and the largest floats appear. A round runs the box builders, `UINineSlice::Compute`, `UILayout` over every field of a `UIRectSpec`, `LayoutStack`, `UICanvasScaler::Resolve` and a `UICanvasLayout` with a tree of up to seven elements (`HitTest`, `PickElement`, `Validate`). Properties: a call appends at most `kMaxVerticesPerCall` vertices and `kMaxIndicesPerCall` indices (whole triangles, indices inside the list, finite vertices); a rect from a layout, a stack, a canvas or its tree has numbers within `UIBounds::kMaxExtent` and no negative size; the scale is in its range; a nine-slice piece is finite with area on both sides or neither; a corner radius is finite and not negative.

- **What the targets cannot show.** `PoolString` interns the text of an input (a `PoolString` field) and never frees it, so a long run grows its memory without bound, and `FuzzBinaryContent` adopts every accepted input as a block. An array of more than `kMaxArrayElements` needs a seed of 256 KiB, over `kMaxFuzzInputSize`: its test is in `ReaderLimitsTest`, not in the corpus. `LoadFromFile` of both readers is not fuzzed (a path is not a byte input): `ReaderLimitsTest`.

## The corpus

- `corpus/<folder>/`, small files (a corpus file over 64 KiB, `kMaxFuzzInputSize`, fails the replay), real inputs where a real one exists, no hand-typed hex.
- Generated seeds come from `MakeGeneratedSeeds()` (`FuzzSeeds.cpp`), made with the engine's own writers. After a format changes, `FuzzCorpusTest.GeneratedSeedsAreTheCommittedFiles` fails: write them again with `BAGI_FUZZ_WRITE_SEEDS=<repo>/tests/Fuzz/corpus build/<preset>/bin/BagiEngineTests --gtest_filter=FuzzCorpusTest.WriteSeeds` and commit the files.
- `.gitattributes` marks `corpus/**` binary: a seed is raw bytes, and `text=auto eol=lf` would rewrite it in the repository and break `GeneratedSeedsAreTheCommittedFiles` on a fresh checkout.
- A finding becomes a regression seed `fix-<what>` in the folder of its target, committed with the fix and a test next to the fixed code. Seeds are never deleted to make a run pass.

## The mutator

`Mutate` / `ApplyMutation` (`FuzzMutation`): flip a bit, set a byte to 0 / 0x7F / 0x80 / 0xFF, set four bytes to `0xFFFFFFFF` / `0x7FFFFFFF` / `0x80000000` / 0 (length and count fields), insert, delete and duplicate a block, truncate, splice from another seed; at most 64 KiB. Own generator only: the `<random>` distributions and `std::random_device` differ between platforms. A change of the generator or of a mutation changes every corpus run: `FuzzMutatorTest.SameSeedGivesTheSameBytes` pins a hash, update it on purpose.
