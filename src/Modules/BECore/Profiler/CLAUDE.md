# Profiler — zones, frame marks, counters, allocations

How to use it (flags, Perfetto, sampling profilers, measured costs): `HowToProfile.md`. The build options `ENGINE_PROFILER`, `ENGINE_PROFILER_ALLOC`, `ENGINE_PROFILER_TRACY` and the preset `macos-profile`: `cmake/CLAUDE.md`.

## The stats build (`ENGINE_PROFILER_STATS`)

The light profiler for a shipped build, also the web page: `ENGINE_PROFILER_STATS=ON` sets `ENGINE_PROFILER` and `BE_PROFILER_STATS=1` in a Release build (presets `*-release-stats`, `HowToProfile.md`). The desktop presets count allocations; the web ones do not (`AllocPlatform` is not checked under wasm yet; the overlay says "Allocations not counted"). **In it:** the zones, the frame ring, `ProfilerOverlayWidget` with its top zones and the trace export (Ctrl+Shift+P, Ctrl+Shift+T). **Not in it:** Tracy, `--trace` (the web has no command line; the ring export is the way out). With the ring off a zone costs the allocation snapshot and one atomic load (`HowToProfile.md`, "What a zone costs"). `Application` logs `Profiler: stats build ...` once at start; the web smoke waits for it.

## The contract

- **Code is marked only with the macros of `Profile.h`** (`BE_PROFILE_SCOPE`, `_FUNCTION`, `_FRAME`, `_COUNTER`, `_THREAD`, `_NO_ALLOC`; included by the PCH). No backend name appears outside `Backends/`. With `BE_PROFILER=0` a macro is `static_cast<void>(0)`: its arguments are not evaluated, so they must have no side effect the program needs.
- **What compiles in every build:** the recorder (`ChromeTraceBackend`), `Profiler`, `ProfileZone`, `ScopedTrace`, the flags. Only the macros compile out, so the everyday Debug tests cover the logic and a test can drive a recorder directly.
- **A zone name is a string literal** (the macro keeps a `static constexpr ProfileSite` whose address is the zone's identity); a thread name may be built at run time (`BE_PROFILE_THREAD` copies it). Counters are named by literals too.
- **Zones are coarse**: a frame stage, a system, a task, one rollout of a search. A zone costs a clock read and a store when recording and an atomic load with no backend (`HowToProfile.md`); a function called millions of times a second gets no zone, the sampling profiler sees it.

## Why not a CoreManager service

`Profiler` and the allocation counters are static classes over `constinit` globals, not a `Singleton` or a `CoreManager` getter (the one place the "no globals" rule is broken on purpose): zones run on every thread, the global `operator new` runs before `main` and after `CoreManager` is gone, and window-less tools (the bot arena of a game, a benchmark) have no `CoreManager` at all. Nothing in them is destroyed: a backend that was ever installed stays alive, because a zone ends on the backend it began on.

## Pieces

| Piece | Does |
|-------|------|
| `ProfileSite` | `{name, function, file, line, color}`, laid out like Tracy's source location (checked only in the Tracy backend) |
| `IProfilerBackend` | `Start` / `Stop`, `BeginZone` → token, `EndZone(token, site, allocs)`, `RecordZone(site, beginTicks, endTicks)`, `FrameMark`, `Counter`, `SetThreadName`, `OnAlloc` / `OnFree`, and the lock events of a backend that `WantsLockEvents()` (Tracy). Called from any thread |
| `Profiler` | the primary backend (`SetBackend`; `GetPrimaryBackend()` is what the application chose) and the effective one that zones read (`GetBackend()`: the primary, or with the ring on the ring itself or a `FanOutBackend`), thread ids (1, 2, ... in the order threads first ask), names and sort indexes (kept here, so a backend installed later still names the threads), `Start(settings)` / `Finish()` of an application run, the process's `ChromeTraceBackend` |
| `ProfilerClock` | `mach_absolute_time` on macOS (measurably cheaper than `steady_clock`), `steady_clock` elsewhere; ticks converted only when written |
| `ChromeTraceBackend` | per-thread chunked buffers, no lock on the recording path; writes Chrome trace JSON (below) |
| `FrameRingBackend`, `FanOutBackend` | the ring of recent zones (below) and the immutable (primary, ring) pair that runs it beside any other backend |
| `Ring/` analysis | pure, in every build: `RingSnapshot` (plain copy of the ring), `ZoneStats` (per site: calls, total, self, p95, allocations; `ComputeZoneStats(..., rows)` refills in place from the scratch arena, allocation-free once grown; `ExclusiveStageMs`: segments without double counting, `Other` the rest of `cpuMs`, `WaitStage` last so "work only" is all but the last; `FrameWorkMs`, `SummarizeWorkWait`), `SpikeCapture` (frozen slow frames), `FrozenTrace` / `RingTraceExport` (frozen frames and the last seconds of the ring as a Chrome trace), `TimelineView` (zoom, lanes, hit test) |
| `ProfilerSettings` | `ResolveProfilerSettings(args)`: `--trace=<file>`, `--profiler=none\|chrome\|tracy` (table in the header) |
| `ScopedTrace` | RAII trace of one scope for tools: installs the recorder, marks the start, writes the file and restores the old backend at the end |

**The application run:** `Application::Initialize` resolves the flags first (an error stops the start-up, as a bad control flag does) and calls `Profiler::Start`; `Application::Cleanup` calls `Profiler::Finish` after `OnApplicationDeinit`, when the worker threads have been joined, so every zone is complete in the file.

## The Chrome trace

- Each thread records into a buffer of its own (chunks of `std::malloc`, never `new`, so recording does not enter the operator new it may count). The number of finished events is published with a release store; a writer reads the published part with an acquire load. A buffer is registered once under a mutex and freed only with its recorder, so a thread may end at any time.
- Writing (`WriteJson`, `WriteFile`) is safe at any moment from the main thread: zones still open are closed at their thread's last event, so the file always nests. `MarkTraceStart` starts a session: what each buffer held before is left out and its time is 0.
- The recorder and the frozen-frame writer share `Backends/ChromeTraceJson.h` (`TraceFileWriter`, `WriteTextFile`, the event formatters, all through `AppendFormat`: no temporary `String` per event), so the two files keep one format.
- `WriteFile` formats into one `String` it reserves once and writes it out and clears it between two events when it holds a chunk (`kWriteChunkBytes`), so a large trace costs no more allocations than a small one; `WriteJson` is the same writer keeping the whole text. `WriteFile` runs in the zone `Trace write` and holds the registry mutex; `WriteJson` has no zone.
- A full thread buffer (`kMaxEventsPerThread`) or too many threads drop events; the count is `otherData.dropped` of the file.
- Events: `B` / `E` per zone (`args`: `file`, `line`; with `ENGINE_PROFILER_ALLOC` the `E` carries `allocs` and `bytes`, inclusive of inner zones), `C` counters, `i` frame marks (global scope), `M` thread names. Time in microseconds.
- With `ENGINE_PROFILER_ALLOC` `otherData.allocNames` holds the allocations per zone x name (`[{zone, name, allocs, bytes}]`, at most 100, most bytes first); `Alloc/CLAUDE.md`, "Names". `otherData.allocSizes` holds the size histogram of each innermost zone (`[{zone, allocs, buckets: [{upTo, allocs}]}]`, at most 100, most allocations first; the shape of `zone_allocs` `sizes`); "Sizes".

## The ring (editor panel)

`FrameRingBackend` keeps per thread the last finished zones (written at `EndZone`, so overwriting the oldest never leaves an orphaned begin) and the last frame marks; it holds only what happened since the last `Start()` (`Profiler::SetRingEnabled(true)`): `Start()` begins an epoch, `Snapshot()` drops the frames and zones from before it, and the first frame of the epoch begins at the epoch's tick, so the time the ring was off is in no frame. A frame is the interval between two `FrameMark` ticks and a zone belongs to the frame its begin tick falls in. A reader never blocks a writer: the writer publishes a monotonic count with a release store and slot words are relaxed atomics; `Snapshot()` copies the window without any lock (thread buffers are published by a release store and never freed), re-reads the count and drops what was overwritten meanwhile; `Snapshot(into)` refills a snapshot in place and keeps the capacity of its vectors and names (so a steady frame allocates nothing for the copy); `FrameMark` reads the clock inside its mutex, so mark ticks never go backwards. Memory is bounded and malloc'd; the ring is never destroyed. A `FanOutBackend` is never mutated or destroyed (one per distinct primary while the ring is on) because a zone ends on the backend it began on; with the ring off `GetBackend()` is the primary. `ScopedTrace` and `profiler_dump` use `GetPrimaryBackend()`.

**Ring pause** (`Ring/RingPause.h`): while a `ScopedRingPause` is alive on a thread, the ring records nothing from it (`BeginZone` pushes no open zone, `EndZone` and `RecordZone` write no slot); `FrameMark` is not paused, and the other backends of a `FanOutBackend` still get every zone. No state is kept per zone because scopes nest: a zone begun before the pause ends after it and is recorded whole, a zone begun under it ends under it and was never pushed. A profiler view holds one zone of its own outside the pause and the pause around the rest, so its cost is one block in the timeline and not many small zones in the numbers it shows.

Frame-window export: `WriteFramesTraceJson` (`Ring/FrozenTrace`) writes cut frames (`FreezeFrame`) in the file format above, once for two callers. `WriteFrozenTraceJson` marks each frame `Frozen frame`, not `Frame`, so `trace_summary.py` does not take the gap between two spikes for a frame time; `WriteRingTraceJson(snapshot, seconds)` (`Ring/RingTraceExport`) takes the frames that end within `seconds` of the newest frame's end (the newest always) and marks them `Frame`, since they are consecutive, so the summary reads it like a recorded trace.

## Lock waits

`Mutex` / `SharedMutex` (`Threading/`) call `LockHooks::WaitBegin` / `WaitEnd` around the blocking lock that follows a failed `try_lock`. `WaitBegin` reads `ProfilerClock` only when a backend is installed; `WaitEnd` calls `backend->RecordZone(site.wait, begin, end)` when the wait was at least `Profiler::GetLockWaitThresholdUs()` (default `kDefaultLockWaitThresholdUs`, 50 microseconds). The zone is made after the fact, so it needs no token and never leaves a begin open: `ChromeTraceBackend` writes the `B` / `E` pair together with the given ticks (both or neither when the buffer is full; the thread was blocked between them, so the pair nests inside what the thread has open), `FrameRingBackend` writes a slot at the thread's current depth without touching its open stack, `FanOutBackend` forwards to both sides.

**Raw on purpose:** the recording path takes no engine `Mutex`: a wait inside it would record itself without end. `Profiler.cpp` (`g_backendMutex`), `ChromeTraceBackend` (the registry mutex, `std::thread::id`) and `FrameRingBackend` (its mutexes) keep `std::mutex`, each with a `//-NoStd:` marker (the list of allowed raw uses: `Threading/CLAUDE.md`); no `Mutex` is taken in `RecordZone`, `SetThreadName`, `GetThreadBuffer` or `ProfilerClock`. Both recorders find a thread's buffer by `std::thread::id`, which the OS may give to a later thread: such a thread writes into the buffer (and under the thread id) of the earlier one.

## Frame statistics (always on)

`FrameStatsCollector` (`CoreManager::GetFrameStats()`, a normal main-thread service, unlike the rest of this folder) keeps the last `kFrameHistory` frames: `frameMs` (end to end), `cpuMs`, the stages (`FrameStage`: `Update` and inside it `SceneUpdate`, `Render` and inside it `SceneDraw`, `Present`, `Wait`, a sibling inside `cpuMs` that the Vulkan backend times around the fence and the swapchain acquire (SDL and web have none, their vsync wait stays in `Present`), and `Submit`, the `SubmitBatch()` calls of `IRenderer::Flush()` outside a counters pause, nested in whichever stage flushed, so a sum of stages leaves it out), `gpuMs` (the one source of GPU time: the backend's `SetGpuTime()`, the newest frame the GPU finished, so some frames old; 0: no value; a trace counter `GPU ms` only with a value), the renderer's `RenderCounters` (`drawCalls` submissions, `primitives` what callers asked for: they differ when the renderer batches), the allocations of the frame, also per `MemTag` (zero without `ENGINE_PROFILER_ALLOC`; `Alloc/CLAUDE.md`, "Tags") and up to `kMaxFrameCounters` named counters (`SetCounter`; ImGui's draws come this way). `Application::RunFrame` opens the frame after the clock and closes it after the present; `OnGameCycle` and `Scene::Draw` time their stages with `StageScope`. `FrameStats::paused` marks a held frame of a paused game (`BeginFrame(held)`): not a game frame, so averages leave it out.

**Control methods** (`ProfilerControl.cpp`, registered by `CoreManager::InitializeCoreServices`): `frame_stats`, `profiler_dump`, `zone_allocs` (per zone and, as `names` and `sizes`, per zone x allocation name and per zone x size bucket), MCP tools of the same names (`tools/control/bagi_mcp.py`). The answers of `profiler_dump` and `zone_allocs` and the rows of `arenas`, `pools`, `tags` are reflected structs (`ProfilerAnswers.h`); `frame_stats` is streamed by hand (its frames hold objects keyed by names a module chooses, which a reflected map cannot write).

## The views

- **Ctrl+Shift+P** (`ProfilerToggle.h`, `IsProfilerToggle`: the modifiers of Ctrl+Shift+E on `SDLK_P`) is read from the raw `SDLEventWrapper` by the Profiler panel's model and the overlay widget themselves, so it works over an ImGui text field. Ctrl+P is the editor's command palette; Ctrl+Shift+P is reserved in the hotkey map and listed as the fixed command `view.profiler`.
- **Game mode:** `ProfilerOverlayWidget` (`src/Widgets/`, last in `config/GameWidgetsConfig.xml`): a translucent rect, the lines of `FormatOverlayLines` (`FrameStats/FrameStatsText.h`, pure) and the top zones, one bar per recent frame against the frame budget. Output pixels (the scene's view transform is put aside), its draws under `ScopedRenderCountersPause` and its allocations under `ScopedAllocCountersPause` (`Alloc/CLAUDE.md`, "Pause"). **Zones:** in a build with `BE_PROFILER` the overlay runs the ring only while it is visible (`SetRingEnabled` on show, off on hide and in the destructor, so a mode switch leaves it off); every `kZoneRefreshFrames` frames it takes one `Snapshot(into)` and `ComputeZoneStats(..., rows)` over the last `kZoneWindowFrames` ring frames, and the frames between draw the kept rows: `FormatTopZoneLinesTo` gives the six zones with the largest self time per frame. **Its own cost is out of those numbers:** the draw is one zone `Profiler overlay` with a `ScopedRingPause` held inside it, and the list skips that name. **Export:** Ctrl+Shift+T (`IsProfilerExportChord`, same rules as the toggle) or a left click on the line `Save trace` saves the last `kExportSeconds` of a fresh `Snapshot()` through `WriteRingTraceJson`: a file `profiler-trace.json` in the working folder on the desktop, a download in the browser (`WebDownloadStart`, `SDL/CLAUDE.md`), then a status line under the text. The click goes through `UIInput` (a top-order handler while visible, its rect from the last draw: the press does not reach the game); the export runs under the same zone and ring pause, into a replaceable sink. It is compiled in every build so a config that lists it never fails, but in a plain Release (`kProfilerViewsBuilt`: no editor, no profiler) it ignores the chord and draws nothing; without `BE_PROFILER` it shows the frame lines and bars and no zones. A game with its own `GameWidgetsConfig.xml` adds the entry itself.
- **Editor:** the panel asset `ProfilerPanel` over `ProfilerPanelModel` and its slots (`src/Widgets/Profiler/CLAUDE.md`; editor only; the ring runs only while it is open): the frame bars with budget lines or the stage split ("Work only" drops `Wait` from bar and scale, a line gives `SummarizeWorkWait`), counter graphs, the timeline of the opened frame, the zone table, the spikes, the heap, the allocations per zone and the Chrome trace. While open, the model holds a `ScopedAllocCountersPause` from `Update` to `EndUpdate`, so the panel's allocations are not in the counts it shows.

## Tracy (`ENGINE_PROFILER_TRACY`)

`Backends/TracyProfilerBackend.cpp` is the only file that sees Tracy's headers (the C API, `tracy/TracyC.h`); it and the vendored `TracyClient.cpp` get the Tracy definitions and no PCH (`BECore/CMakeLists.txt`), so `TRACY_ENABLE` never reaches another file. The client runs `TRACY_ON_DEMAND`, `TRACY_MANUAL_LIFETIME` and `TRACY_DELAYED_INIT` (its threads start when the backend is first installed and end in `Profiler::Finish`; it cannot start twice in a process). In a Tracy build Tracy is the default backend; `--trace=` picks the Chrome trace instead. Version and viewer: `src/Modules/tracy/README.md`. **Lockables:** `TracyProfilerBackend` answers `WantsLockEvents()` true, so `Profiler` hands it every lock operation of a `Mutex` / `SharedMutex` (`BeforeLock` / `AfterLock` / `BeforeUnlock` / `AfterTryLock`, over Tracy's lockable C API; the lock's name is the `function` of its `BE_LOCK_SITE`, also sent as the custom name). Chrome and the ring answer false, so their locks pay one relaxed load (`LockHooks::g_eventBackend`, null) and no virtual call; a `FanOutBackend` forwards the events to its primary. The lock's context is made on its first event (`LockEvents`, `Threading/LockHooks.h`) and ended in the lock's destructor through the backend that made it; every Tracy call is a no-op once Tracy has shut down, so a lock may outlive it.

## Where the engine's zones are

Zones sit in `Application::RunFrame` (`Frame`, `Idle` for a manual-clock pass, `Present`, the frame mark), the stages of `CoreManager::OnGameCycle` (`Game cycle` around `Input`, `Tasks`, `Tweens`, `Scene update`, `Widgets update`, `Queued events`, `Draw screen`, `Draw widgets`) and in the systems, renderer backends, control calls, saves, the thread pool (`Task`, `Main thread task`), the room server (`Room *`, `WS *`) and `RoomClient` (`Client poll`, `Client send`); `grep BE_PROFILE_SCOPE` finds the rest. Named threads: `Main`, `Worker <n>`, `Control accept` / `reader` / `writer`, `Room hub` / `reader` / `writer`.

**The task system in a trace.** A job on a pool thread is a `Task` zone; a worker that waits for a job is in an `Idle` zone, so its row shows busy and idle at a glance. A task named with `BE_TASK_LABEL` (`TaskSystem/TaskLabel.h`) adds a zone of that name inside `Task` (inside `Main thread task` on the main thread). Counter tracks: `Worker n: busy` and `Pool: busy workers`, sent on every change under one lock (the points keep their order) and only while a backend records; the queue depths are sampled once per frame by `TaskManager::Update`. A counter name is a literal, so there is one per worker up to `ThreadPool::kMaxGraphedWorkers`. **Thread order:** `BE_PROFILE_THREAD_ORDER(name, n)` also sets `thread_sort_index` of the Chrome trace (lower is higher): `Main` 0, `Worker n` 100 + n, the control threads 200 to 202; Tracy has no such field. A worker's `Idle` zone began on the backend that was installed then, so a test backend that a pool thread can still see must never be destroyed.

## Tests

Tests are in `tests/BECore/`. Traps: `AllocTrackerTest` calls `::operator new` explicitly so the optimizer keeps the calls; `EastlAlignedAllocTest` runs under the Debug CRT's heap checks on Windows (a report ends the process) and is skipped under ASan; `ProfilerCostTest` is disabled and `HowToProfile.md` quotes it.
