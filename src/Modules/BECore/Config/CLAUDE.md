# Config Module Guidelines

## Overview

XML configuration: every file under `config/` (the engine's and the game's, see layering below) is loaded once at startup and read through `ConfigManager`. Parsing is pugixml behind thin wrappers; reflected objects are filled from a config with the serialization layer (`.claude/rules/reflection-module.md`).

## Components

| Class | Role |
|-------|------|
| `ConfigManager` | Loads and caches all configs; reached via `CoreManager::GetConfigManager()` |
| `XmlDocument` | `RefCountedAtomic` owner of a `pugi::xml_document`: load/save file or string. It keeps the comments and the declaration of a file (nodes of the DOM, written back; a declaration the file lacked is not added; a UTF-8 BOM is kept) and writes every attribute of an element on one line. `GetRoot()` is the **root element**, not the first child. `SaveToFile` lays the text out like the file that is on disk (`XmlLayoutMerge`), writes nothing when the text is the one the file holds, and falls back to the canonical text (two-space indent) when the file cannot carry the layout; the DOM always wins over the file. Files go through the file layer (`File/CLAUDE.md`): `LoadFromFile` reads the bytes once and parses them (`encoding_auto`; the byte-order mark is read from those bytes), so a missing file, a folder, an empty file and a file over `kMaxXmlDocumentBytes` do not load; `SaveToFile` makes the folder and truncates the file in place (no `<file>.tmp`: the `FileWatcher` watches these folders). It reads the old text with `ReadFileBytesScratch` in a `ScratchScope` that ends before the file is opened for writing (a file over `kMaxScratchSaveBytes`, 256 KiB, goes to a heap block of the helper, so the thread's arena keeps no big chunk); the new text, the two pugixml documents and the canonical texts stay on the heap |
| `StringXmlWriter` (`StringXmlWriter.h`) | The one `pugi::xml_writer` into a `String`: `document.save(writer, ...)` / `node.print(writer, ...)`, then `writer.text`. Every save to text goes through it; no `ostringstream`, no local writer struct |
| `XmlLayoutMerge` (`MergeXmlLayout`) | The pure line merge under `SaveToFile`: the canonical text of the edited DOM laid out like the old file (its blank lines, indentation and hand layout of every line the edit did not touch). `nullopt` when the old text does not match its own canonical form line for line (quote style, `<a/>` forms, wrapped attributes, a `\r`) or is past a size limit; `SaveToFile` then writes the canonical text, and it verifies a merge by parsing it. Its working lists and the Myers trace live in a function-local `LinearArena` whose first chunk is on the stack (a config of a few hundred lines allocates only the result): the thread's scratch arena would keep the chunks of a big file or of a diff whose trace grows with the square of the edit count, this arena frees them on return |
| `XmlConfig` | Handle over an `IntrusivePtr<XmlDocument>`: `LoadFromVirtualPath`, `LoadFromFile`, `LoadFromString`, `SaveToFile` |
| `XmlNode` | Lightweight pugi node wrapper: `GetChild(name)`, `Children()` (the element children only), `Name()`, `ParseAttribute<T>(name)` → `Optional<T>`; `if (node)` is the validity check |
| `XmlTextPatch` | Edits the attributes of named start tags in the text of a file and leaves every other byte alone (comments, quote style, `<a />` forms, line wrapping, BOM). A `pugixml` re-save loses those, and the files of a person (`config/nodes/*.xml`) are read in a diff. `Parse` (UTF-8 only) gives the document whose `offset_debug()` locates the tags; `Apply` refuses a tag that no longer matches the document |
| `ConfigManager::CreateDeserializer(name)` | An `IDeserializer` (`UniquePtr`) over the root of a named config, or `nullptr` when the config is unknown. The one way for a caller to read a named config through the reflection; it must not outlive a `ReloadConfig` of that config |
| `OpenDeserializer(virtualPath)` (`Reflection/OpenDeserializer.h`) | An `IDeserializer` for a file, picked by extension (`.xml` gives `XmlDeserializer`, `.bin` gives `BinaryDeserializer`); `std::expected` with a message when the extension is unsupported or the file does not load. The header does not pull `CoreManager.h`. `ResourceManager::LoadSerialized` and `SDLMainWindow` use it |
| `MakeFromConfig<T>(name)` (`ConfigFactory.h`) | `New<T>()` + `Deserialize` through `CreateDeserializer`, under a `ValueLinkScope` named after the config (so a `<context>` and the `from` of `Value` fields of the document work, `Values/CLAUDE.md`); returns defaults when the config is missing. Errors the deserializer reports (an unknown factory `type`, a malformed value) are written to the log, one `LOG_ERROR` each (and one `LOG_WARNING` per finding), by `LogDeserializeErrors(configName, deserializer)` (declared in `OpenDeserializer.h`, included by `ConfigFactory.h`; `Config 'LoggerConfig': sinks[0].type: Unknown factory type: 'Console'`); the object keeps what could be read. Include from `.cpp` files only (pulls in `CoreManager.h`) |

## ConfigManager

**DO**: read configs through the manager.
```cpp
auto rootNode = CoreManager::GetConfigManager().GetConfig(ConfigNames::logger);
```

**DON'T**: create loaders by hand or call `LoadFromVirtualPath()` directly for engine configs.

- `Initialize()` scans every layer of the `config` mount point (engine first, game on top) recursively, loads every `.xml` and `.bin` ("Binary configs") in parallel through `TaskManager` and blocks until done. A second call is a no-op. A layer folder that cannot be listed is one `LOG_ERROR` and adds no file.
- The key is the **file stem** (without `.xml` or `.bin`). Two files with the same stem in different layers do not collide: the upper layer wins and the log says `Config 'X' from <path> overrides <path>`. A game's `SceneConfig.xml` therefore replaces the engine's entire file, it is not merged. Two files of one extension with the same stem inside one layer still collide (the one that loads first wins, the order is not defined). The scan is recursive, so the node files of a scene (`config/nodes/X.xml`, referenced by `<node ref="nodes/X"/>`, see `Scene/CLAUDE.md`, "Node files") are loaded as configs named by their stem too: prefix them with the game name so that no stem equals a real config.
- `SaveConfig` writes to the file the config was loaded from, i.e. into the layer that won; with a content overlay (`FileSystem/CLAUDE.md`) into `FileSystem::WriteTarget` of it, the original copied there first so the layout is kept, and the entry's `filePath` and `fileHash` follow the copy.
- `GetConfig` takes a `PoolString` or a `StringView` (the latter avoids interning) and returns an invalid `XmlNode` when the name is unknown, so check it.
- Documents live in `UnorderedPoolMap<ConfigEntry>`; writes are serialized by a mutex.
- Editor support: `GetAllConfigNames()`, `GetConfigFilePath(name)`, `SaveConfig(name)`, `ReloadConfig(name)` (replaces the cached document; both are `false` for a binary config). Code that holds an `XmlNode` from before a reload must fetch it again, whatever caused the reload: `ReloadConfig`, or a file changed on disk (below).

## Binary configs

A `config/` folder may hold cooked files: `Name.bin`, a binary document (`.claude/rules/reflection-module.md`, "Binary Format", content mode) that (format version 2 or 3; a file cooked by this engine is 3) starts with the content stamp (`$content`: root type and layout hash). The key is the stem and the layers work as for XML: the upper layer wins whatever the extension. A `.xml` and a `.bin` of one stem **in one layer** is one `LOG_ERROR` naming both and the stem is absent from every layer (a lower layer's file under an error would be a stale config read unseen).

- **Load:** `LoadContentFile` (`Reflection/BinaryContent.h`) reads the file's pool section straight into a pool block and the rest into a `BinaryContent` the entry owns; it is validated (`LoadFromContent`) and stamp-checked (`CheckContentStamp`) in the same parallel step as an XML parse. A version 2 `.bin` (no pool section) loads whole and interns as a save does; a version 3 one takes the straight adoption after the cook is run again. A refusal (no stamp, another layout hash, damage, a bad checksum: cook again) is one `LOG_ERROR` and the config is absent; the stamp is checked after the adoption, so a refused file leaves its type and field names in the pool. `CreateDeserializer` gives a `BinaryDeserializer` over that content, valid while the manager lives; `IsBinaryConfig(name)` tells the kinds apart. The caller's `SetDiagnostics` has no effect: a binary read reports no findings, so `--strict-config` does not reach a `.bin`; the XML is where a typo is found, and the cook (`Cook/CLAUDE.md`) fails on every such finding, so a release is built from clean files.
- **XML-only, by design:** `GetConfig` (an invalid `XmlNode` for a binary config), and with it every reader that parses by hand (`UIConfig`, `TextConfig`, `UIStrings`, `UIThemes`; entry `config-xmlnode-by-hand`: such a file stays XML until its reader is reflected); `SaveConfig` and `ReloadConfig` (`false`, one `LOG_ERROR`, nothing changes); the hot reload (a changed `.bin` is ignored with a `LOG_DEBUG`, no `ConfigChangedEvent`); `TextureLibrary::Save`, the config and scene editors, and `BuildNodeReference` with the node files the editor reads. A cooked file is read-only: replacing it is a patch story, not a reload.
- **Scenes:** a `SceneConfig.bin` and the node files `.bin` are read by the scene loader (`Scene/CLAUDE.md`, "Node files"); no `kContentVersion` check, the stamp stands for it (the cook checked the XML). The node files are read by `LoadFromFile`, hashed: an adopted block is never freed and a node file is read at every instantiation.

## Hot reload and `ConfigChangedEvent`

`ConfigManager::StartWatching(FileWatcher&)` (called by `CoreManager::StartFileWatching` when the `fileWatch` setting says so; `FileSystem/CLAUDE.md`, "FileWatcher") watches the `config` mount point. A change of the file a loaded config came from reads it again; the manager keeps a **hash of the file text each document reflects** (set at load, at `SaveConfig` after the write, at `ReloadConfig`) and acts only when the text differs. That is what stops the echo of the manager's own `SaveConfig` (its write reaches the watcher as a change) and the duplicate posts of one save, and a rewrite with the same text costs one read. A different text is `ReloadConfig`'s work and ends in `ConfigEvents::ConfigChangedEvent{name}`.

- **Failure is quiet:** a file that does not parse leaves the old document and logs one `LOG_ERROR`, no event (when the change came from `FileWatcher::Apply` the watch's callback also sets `FileChange::ok = false` and the reason, so the Editor panel and `files_apply` report it; the watch is named `ConfigManager` in a rescan); the hash stays the one of the document, so restoring the old text later changes nothing. A new file, a removed file, a file of a lower layer and a file no loaded config owns are ignored with a `LOG_DEBUG` (picking up new files is the `hot-reload` entry).
- **The event** (`Events/ConfigEvents.h`) is also emitted by `SaveConfig` and `ReloadConfig`, and by `NotifyConfigChanged(name)` for a caller that changed the cached document in place. Always on the main thread, after `_writeMutex` is released, so a subscriber may call the manager. Every `XmlNode` and `CreateDeserializer` result taken before it is stale: a subscriber reads again.
- `ConfigManager(const FileSystem&)` makes a manager over a file system of its own (tests: a `config` folder in a temp directory, `ConfigHotReloadTest`); the default one uses `CoreManager`'s.

## Reading values

```cpp
if (auto title = node.ParseAttribute<StringView>("title")) { /* use *title */ }
```

**A config DOM holds comments** (and the declaration), so a reader of one walks elements only: `XmlNode::Children()` does, a loop over a pugi node tests `node_element`, and the array reader of `XmlDeserializer` counts elements. Prefer a reflected struct plus `MakeFromConfig<T>` / `Deserialize` over hand-written attribute loops. A caller that needs an `IDeserializer` asks the engine (`CreateDeserializer`, `OpenDeserializer`); it does not construct `XmlDeserializer` for a named config. A caller of `CreateDeserializer` or `OpenDeserializer` whose document holds `Value` fields opens its own `ValueLinkScope(name)` around the read. Hand-parsing with `XmlNode` is for small, fixed shapes that no reflected struct has replaced yet. A reflected struct per config is the shape: `ApplicationConfig` (`BECore/Application/`, loaded by `LoadApplicationConfig()`) and `GamesConfig` (`Games/`, read by `GameManager::Initialize`) are the examples. The strict-values mode (`IDeserializer::SetStrictValues(true)`, `reflection-module.md`, "Serialization") is opt-in for a config whose bad boolean or number must be an error and not a zero; `ApplicationConfig` uses it, the default stays lenient. The command line is its second source: `ResolveControlSettings` reads the flags of the four control fields over a copy of the loaded config with a `CommandLineDeserializer`, field by field (`.claude/rules/control-startup.md`).

**Findings of a config load:** every reader that comes through `CreateDeserializer` (and `SDLMainWindow`, `LoadSceneManager`, which set the mode themselves) has `ConfigManager::GetDiagnostics()`: `Warn`, or `Error` when the command line has `--strict-config` (read at each call, so the order of start-up does not matter; the process still starts, the findings are errors in the log). An unknown key, a missing `required` field and a value outside `range` are logged by `LogDeserializeErrors` as `LOG_WARNING` (`LOG_ERROR` under `--strict-config`) in the form `Config 'X': path: message`, so a typo in a config shows in the log instead of silently doing nothing. A caller ends its read with `FinishLoad()` before it logs (`MakeFromConfig` does); `ApplicationConfigLoad` carries the `warnings` beside `errors`. When another reader takes keys of the same file (the reflected struct is not the only one), that reader calls `NoteKnownKey` for them; never switch the mode off to silence a config. A game checks its own `config/` with `ExpectConfigFilesClean(folder, readers, byHand)` (`tests/Common/ConfigFilesCheck.h`): each file is read through its reflected type under `Error`, a file with no reader needs an entry with the reason, and a `SceneManager` file has its node references expanded from the folder first (call it again on a subfolder it does not reach). The engine's `WidgetsConfig` and `GameWidgetsConfig` are on that list because their widget classes are registered by the application executable and not by the test one.

A reflected entry in a list whose element name the file fixes is read and written by a hand-written array: `TextureLibrary` (`BECore/Resource/`, `Resource/CLAUDE.md`, "TextureLibrary") has `SpriteEntry` as `<sprite>` elements of `<sprites>` (a generic `Vector` would write `<item>`), `Load(IDeserializer&)` / `Write(ISerializer&)` as the pure halves and `Initialize` / `Save` as the glue over `CreateDeserializer` and `SaveConfig`.

A list of factory objects (widgets, runtime tests, log sinks, assert handlers) is a reflected holder with one `Vector<IntrusivePtr<Base>>` field, filled by `MakeFromConfig<Holder>(name)`; do not write a `<x type>` loop with your own `AbstractFactory` call. `WidgetList` (`BECore/Widgets/`, field `widgets`) and `Tests::TestList` (`BECore/Tests/`, field `tests`) are the shape, `LoggerManager` and its sinks another. The loader reports an unknown `type` (`Config 'GameWidgetsConfig': widgets[1].type: Unknown factory type: 'X'`), skips `enabled="false"` and an element without `type` (no message), and calls the element's `bool Initialize(IDeserializer&)` in its own element scope when the base declares it (`IWidget`): `false` drops the element with `<Type> failed to initialize`.

## Adding a config

1. Drop `config/<Name>.xml`; it is picked up by name at the next start.
2. Consume it with `GetConfig("<Name>"_intern)` or `MakeFromConfig<T>("<Name>")`; the names the engine reads from more than one place are `ConfigNames` (`ConfigNames.h`).
3. If users should edit it in the Config Editor, register enum or flag hints in `ConfigEditorWidget::Initialize` (`src/Widgets/ConfigEditor/`): `RegisterEnum<E>` for an enum, `RegisterFactoryTypes<Base>` for a `type` attribute resolved by `AbstractFactory<Base>`. The options must be the strings the loader accepts (for a factory, the class names), so take them from the factory or the enum, never from a copy.

## Content version

A **content file** is a file of a `config/` folder whose root element is `SceneManager` (a `SceneConfig.xml`) or `node` (a node file): `IsContentRoot` (`ContentVersion.h`). Its root may carry `contentVersion="N"`; **no attribute is version 1**, the format before versions (an explicit `0` is older than anything). The engine reads exactly one number, `kContentVersion`: a format change that old files cannot satisfy adds a step to `tools/migrate/steps/` and bumps it (`tools/migrate/CLAUDE.md`). Other files (`UIConfig.xml`, `TextureLibrary.xml`, ...) are not content files and carry no version; the first step that rewrites one adds its root to `IsContentRoot`.

- **One number for the engine, one stamp per file:** a game's files are migrated together with the engine's, never read through an in-memory upgrade, so a loader only compares and refuses. A file is stamped by the tool, not by hand.
- **Who checks:** `LoadSceneManagerFromConfig()` (the root of the game's `SceneConfig`; an older, newer or malformed root is one `LOG_ERROR` and an empty `SceneManager`) and `MakeFileSystemNodeLoader` (the node file of a reference is dropped like one that does not parse). **Who does not:** `LoadSceneManager(XmlNode, ...)` (a parsed root of tests and tools) and `MakeDirectoryNodeLoader`, so inline XML in tests needs no stamp; `CheckContentVersion` is the pure check a test of a content file calls. The message names the file, its version and the engine's, and says `python3 engine/tools/migrate/migrate.py <your game folder>` (older) or "update the engine" (newer).
- **The stamp is not part of the scene:** `ExpandNodeReferences` removes it from the copy of a node it inserts; the deserializer ignores it on the `SceneConfig` root; the scene editor's save keeps that root as it is.
- **A game's own steps** use the attribute `contentVersion.<track>`, which no engine loader reads: the game's test runs the tool with `--check`.
- A test of a game's own content: `ExpectContentFilesAtCurrentVersion(configFolder)` (`tests/Common/ContentFilesCheck.h`).
