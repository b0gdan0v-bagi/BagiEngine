# PanelAssets: an editor panel described as data

A panel asset is a file `config/panels/<Name>Panel.xml` that says what a simple tool panel shows (text, fields, buttons, a table of a list) and which editor command each button runs, so changing a panel is a file edit and a hot reload, not C++ and a rebuild. This folder is the pure half: the classes of the asset, the loader and validator, the registry of named sources, the reads of a bound value and the one-field visitor. It has no ImGui and is compiled in every build, because a reader of untrusted XML must be testable and fuzzable everywhere (`FuzzPanelAsset`). **What is not here:** the interpreter that draws an asset, the widget that hosts it, the model interface and the hand-written drawers (`PanelInterpreter`, `AssetPanelWidget`, `IPanelModel`, `PanelSlots`) are the editor's, in `src/Widgets/PanelAssets/` (its `CLAUDE.md`).

A model (C++) owns the logic and the data: it registers a reflected object under a name and handles the commands. The asset says how it looks and what it is bound to. A button never calls code: it emits `EditorCommandEvent{command, argument}`, and the model that owns that command subscribes (`EditorCommandEvent::argument` is a `String`, empty for a button with no argument).

## The asset format

```xml
<PanelAsset id="FileChanges" title="File changes" command="view.fileChanges" open="false" width="640" height="320">
  <sources>
    <source name="files" model="FileChangesPanelModel"/>
  </sources>
  <elements>
    <element type="PanelEmptyState" id="notRunning" icon="file-diff" text="The file watcher is not running" visible="!files.running"/>
    <element type="PanelRow" id="toolbar" visible="files.running">
      <elements>
        <element type="PanelButton" id="applyAll" text="Apply all" command="fileChanges.applyAll" enableWhen="files.hasPending"/>
      </elements>
    </element>
    <element type="PanelTable" id="pending" source="files.pending" visible="files.hasPending">
      <columns>
        <column type="Text" id="path" field="path"/>
        <column type="Button" id="apply" icon="check" command="fileChanges.apply" argument="path"/>
      </columns>
    </element>
  </elements>
</PanelAsset>
```

- **The root** (`PanelAsset`): `id`, `title`, `titleBind` (a binding to a text: the window title is that text with `###<id>` after it, so the window keeps its saved layout; an unreadable text leaves `title`), `command` (the editor command that shows and hides the panel), `open` (its state at start), `width` / `height` (0: the editor's default), `sources`, `elements`. The loader does not check the name of the root element; the schema tool finds the type of a file by it, and the `Panel` suffix of the file stem keeps a panel from colliding with a real config (`ConfigManager` keys configs by the stem).
- **Sources:** `source` has a `name` (`[A-Za-z_][A-Za-z0-9_]*`, unique in the asset) and a `model` (the name of the model class the editor resolves; here it is only a text, checked through `PanelValidationContext::isKnownModel` when the editor passes one). A binding may also name a source registered in `PanelDataSources` that the asset does not list. The writer of the reflection names the items of `sources` and `columns` `<item>`, and the reader takes any tag name, so a hand-written `<source>` / `<column>` loads and the schema says `item`.
- **Elements** all derive from `PanelElement` (`id`, `visible`, `tooltip`, `elements`; the factory element name is `element`, its attribute `type` the class name): `PanelSection` (collapsing header: `title`, `defaultOpen`, children), `PanelRow` (children on one line), `PanelText` (`text` literal or `bind`, `style` `Normal|Disabled|Success|Warning|Error`, `wrap`, `mono`, `maxLines`: N > 0 shows N lines and scrolls, also sideways), `PanelField` (one top-level field of the object `bind` names, drawn as the inspector draws it: `bind`, `label`), `PanelFields` (every field of that object; `bind` may be a source alone, `game`, for the whole object: `ParseObjectBinding`), `PanelInput` (a text field bound to a `String` field: `bind`, `hint`, `icon`, `width` in em), `PanelCheckbox` (`bind` a bool field, `text`, `labelBind` a text binding that replaces `text`, `look` `Check|Toggle` (a toggle is a button filled while on), `style` the label colour; one of `text` and `labelBind` is required), `PanelCombo` (`bind` an enum, an integer index or a `String`; `items` a binding to a list whose rows are the choices, `itemField` the path of the text in a row, empty for a list of scalars, only with `items`; an enum with no `items` lists its names; `width` em), `PanelNumber` (`bind` any number field, `text` the label after the control, `min` / `max` (equal, the default: unbounded), `step` the drag speed, `slider` (needs `min` < `max`), `width` em; there is no `format`: a printf format chosen by an untrusted file is a hole). These three write the field themselves (`PanelBindingWriter`) and emit no command: the model reads its object again in its next `Update`. `PanelButton` (`text`, `icon`, `command`, `argument`, `enableWhen`), `PanelTable` (`source` a list, `columns`, `header`, `borders`, `maxRows`, `scrollRows`: N > 0 shows N rows in a scroll region; a `PanelColumn` has `type` `Text|Button|Selectable|Input`, `title`, `field`, `styleField`, `enableField`, `hint`, `command`, `argument`, `icon`, `tooltip`; an `Input` cell edits the `String` at `field` of the row, a `Button` with a `field` is labelled with the cell's text, `enableField` is a bool path relative to the row that disables a `Button` or `Input` cell while false; `selectedField` is one that draws a `Selectable` cell selected while true (only that type may name it); `styleField` is a path relative to the row to a `PanelTextStyle` field, the colour of a `Text` cell per row), `PanelSeparator` (`title`), `PanelEmptyState` (`icon`, `text`), `PanelSlot` (`name`: a hand-written drawer registered under it), `PanelChild` (a region with its own scroll beside others in a `PanelRow`: `width`, `height` in em, 0 fills what is left, `border`), `PanelPopup` (a modal window: `title`, `open` a condition that is required, since a popup with none could never open; one modal at a time, so a popup is not nested in a popup). Only `PanelSection`, `PanelRow`, `PanelChild` and `PanelPopup` hold `elements`. A button's condition is `enableWhen`, not `enabled`: the factory writes and reads `enabled` itself on every element of a factory list, so a binding text there would make the element vanish at load.
- **A binding** is `source.path`: the part before the first `.` names a source, the rest is a `PropertyPath` (`Reflection/PropertyPath.h`) of the source's object: `files.pending`, `game.fields`, `files.status.text`. A **condition** (`visible`, `enableWhen`, a popup's `open`) is `term ( and term )* ( or ... )*`: `and` binds tighter than `or`, no parentheses, tokens separated by blanks (a quoted key of a path may hold them; an attribute writes `<` as `&lt;`). A term is `[!]source.path` (a bool field) or `source.path <op> literal` with `<op>` one of `== != < <= > >=` and the literal a number (compared through `ReadNumber`) or a bare word (an enum name, `true`, `false`; compared as text through `ReadText`, `==` and `!=` only, so an order compare on a word is a load issue); `!` does not combine with a compare. At most `kMaxConditionTerms` terms; a literal is parsed once at load (`ParsePanelCondition`, `EvaluatePanelCondition` in `PanelCondition.h`). A term that cannot be read counts as the caller's `whenUnreadable` (true for `visible` / `enableWhen`, false for `open`). Empty is always true. A table column's `field` and `argument` are property paths **relative to the row** (the list's element; empty for a list of scalars). `ParseBinding` / `ParseCondition` (one `[!]source.path` term) check the syntax only (`ParseObjectBinding` also takes a source alone, the whole object); whether the source and the field exist is found when the panel reads, and a miss is shown as `?`, never an error. A bound field is a top-level field of a source object (`PanelField`); a nested object is reached by the model exposing it as a source of its own.
- **Limits** (`PanelAssetLimits.h`, the loader reports anything beyond them as an issue): nesting depth, elements, `maxLines` and `scrollRows`, the extent of a child region or a combo or number `width`, `kMaxNumberExtent` for `min`, `max` and `step` of a number, popups, columns in all, sources, bytes of a text field, an `id` of 1 to 64 bytes of `[A-Za-z0-9_.-]` that is unique in the asset (column ids are unique per table), issues per load. The size of the file is the reader's (`ReaderLimits`).
- **Strings are `String`, never `PoolString`**, in every class here, in the registry and in the compiled-path cache keys: an asset is untrusted and read again at every hot reload, and the pool never frees (`Reflection/CLAUDE.md`, "Rules").

## The loader

`LoadPanelAsset(text)` / `LoadPanelAsset(IDeserializer&)` returns the asset and the `PanelIssue`s (`{where, message}`: an element id, or a path such as `elements[2].columns[0]` when the id is bad). **`issues.empty()` is the only meaning of "valid".** An asset with issues is still safe to hold and to walk, so a panel can keep drawing the last good one under a banner; `asset` is null only for a text that does not parse. No input asserts or crashes, the same text gives the same issues, issues are short with no control character and the list is bounded (the last one says that more were dropped). The deserializer runs in `DiagnosticsMode::Error` with strict values, so an unknown attribute, a bad number, a wrong enum name and an unknown `type` (with `did you mean`) are issues too. The names a file cannot verify itself (commands, models) are checked only when the caller passes `PanelValidationContext` predicates; this folder includes no editor header.

A failed hot reload of the file is `ConfigEvents::ConfigReloadFailedEvent` (`Config/CLAUDE.md`, "Hot reload"): the panel that shows the asset subscribes to it and to `ConfigChangedEvent`. `PanelAssetHolder` is the rule a host applies to both: `Load` reads the config through its deserializer under a `ValueLinkScope`, `Current()` is the last asset read with no issue and a later bad file only sets `Issues()` (the host draws a banner and the last good asset below it), a first read that failed leaves `Current()` null, and `Failure()` is the reason of an unreadable reload until the next read replaces it. It is here, not in the editor folder, so the rule is tested in every build.

## Reading a bound value

`PanelDataSources` (a `Singleton`, main thread only) maps a name to a provider that gives the source's `TypedRef` **now**, so an object that appears or dies (the active game) is found again at every read. A model registers with `Register`; the returned `PanelSourceHandle` unregisters when destroyed, and a name registered again replaces the provider and orphans the older handle. A registry may have a parent (`SetParent`): a name the own sources do not hold is looked up in the parent, so a widget keeps its models in a registry of its own (two panels may both name a source `files`) with the global one behind it.

`PanelBindingReader` reads a bool, a number (and, when asked, whether the field is an integer or a float, which picks a drag over `int64_t` or `float`), a text, an enum's index and names (a combo's items), a list's row count and a row's cell through a `PanelReadStatus`; any status but `Ok` is a `?` in the panel, never an assert or a crash (a gone source, a wrong path, a field of another kind, a row past the end). A path is compiled against the object's type once and cached (keyed by `TypeInfo*` and the text, bad paths too, bounded by `kMaxCompiledPaths`), so a steady frame allocates nothing: a field held by value (a bool, a number, an enum, a `String`, a `PoolString`, also inside embedded objects and list rows) is read in place. A path through an optional, a pointer or a list position, and a `FixedString` text, go through `GetProperty` and allocate: bind those rarely. (`TypeDesc::isEngineString` exists so a `String` cell can be told from an overflowing `FixedString`, which cannot be read in place.) A list sits at a fixed path of the source. `PanelBindingWriter` is the other direction, for the controls: a call per kind (`WriteText`, `WriteBool`, `WriteNumber`, `WriteEnumIndex`, each also as `WriteRow...` for a cell of a list) sets one field held by value (top level, embedded, list row) through the reader's own compiled paths (one cache, `friend`), so a steady write allocates nothing. A number is rounded for an integer field and clamped to the field's own type (a write never wraps; NaN and infinity are `BadValue`), an enum is set by the index of its name (past the names: `BadValue`); every other kind, a `PoolString` (never interned: an asset is untrusted) and a const source object are `WrongType`, and a refused write changes nothing. A write emits no command: the model sees the new value when it reads its own object in its next `Update`, so a model that derives state from a bound field must re-read it there, never cache it.

`SingleFieldVisitor` is a decorator over an `IPropertyVisitor`: it lets one top-level field (and everything inside it) through to the inner visitor and nothing else, so the inspector's own drawing (`ImGuiPropertyVisitor`) draws one bound field. A name that is no field gives no call. Keep one per widget so its text scratch keeps its capacity.

## Tests and fuzzing

`PanelAssetTest` (classes, round trip), `PanelAssetLoadTest` (issues), `PanelAssetHolderTest`, `PanelBindingTest` (reader, writer and the binding parsers), `PanelConditionTest` (the condition grammar and its evaluation), `SingleFieldVisitorTest` in `tests/BECore`; the reflected probe types of the binding tests are `PanelBindingProbe.h` and `SingleFieldProbe.h`. `FuzzPanelAsset` (`tests/Fuzz/CLAUDE.md`) holds the reader's contract against a walk of the returned tree and replays `tests/Fuzz/corpus/panel_asset/`; a new kind or field needs the walk of the target extended in the same change. The generated reflection code of the classes is in the build folder (`BE_CLASS`, `.claude/rules/reflection-module.md`); a change of a field of a class that a shipped file names needs a step in `tools/migrate/steps/` and a `kContentVersion` bump (`tools/migrate/CLAUDE.md`).
