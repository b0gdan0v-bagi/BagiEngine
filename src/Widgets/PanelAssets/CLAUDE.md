# Panel assets in the editor

The editor half of "panels as data": it draws a `PanelAsset` (`config/panels/<Name>Panel.xml`) on ImGui and hosts it as a widget. The format, the loader, the sources and the reads of a bound value are the pure half, `src/Modules/BECore/Widgets/PanelAssets/CLAUDE.md` (read it first). Editor only: the folder is in the `BE_WITH_EDITOR` regex of `src/CMakeLists.txt` (`.claude/rules/widgets-module.md`). The first asset is the File changes panel (`config/panels/FileChangesPanel.xml`, `FileChangesPanelModel` in `Widgets/FileChanges/`).

## The interpreter

`PanelInterpreter::Prepare(asset)` once per asset change parses every binding text of the tree into a `PreparedElement` tree (parsing allocates, so no frame does it); `Draw(sources, result, slots)` walks it inside the window the caller has begun and allocates nothing in a steady frame (its reader, text scratches and visitors are members whose capacity stays). `CanDraw(element)` says whether a kind is really drawn, which the test of the shipped panels uses; keep it in step with `KindOf` when a kind is added.

- **A click is noted, then emitted.** `Draw` only puts the command and the argument of the clicked button or cell into `PanelDrawResult`; the host emits `EditorCommandEvent` after the walk, because a command may change the list that is being walked. One click per frame is kept (the last). A button has no row, so its argument is empty; a table's `Button` / `Selectable` cell reads `argument` from its row.
- **Ids are the asset's.** `PushID` of the element `id` around every element, and inside a table the row index and the column `id` around every cell, so the control API's lookup by name finds a control by the ids of the file (a button's own label is the last link). The window is `<title>###<asset id>`. Ids in a file are unique per asset, which the loader checks.
- **A read that fails is a `?`**, never an error: a gone source, a wrong path and a field of another kind are what a hot-reloaded asset shows while it is edited. A condition that cannot be read counts as true (`visible`, `enableWhen`), so a broken binding is seen and not hidden. `PanelField` draws the one top-level field of the bound object as the inspector does (`SingleFieldVisitor` over `ImGuiPropertyVisitor`; the visitor is reset before each field because it numbers its widgets from a counter); `PanelFields` is a `PanelField` whose object node starts open. `PanelField::label` is not drawn.
- **Not drawn yet** (stage 3 of the entry): `PanelInput` (it needs a write path into a bound `String`) is a muted `?`, and a table draws every row (no clipper; `maxRows` limits it).
- **Slots.** A `PanelSlot` calls the drawer registered under its name in `PanelSlots` (the global one unless the caller passes its own); an unknown name draws `?`. Nothing registers a slot yet.

## The widget and the models

`AssetPanelWidget` (`<widget type="AssetPanelWidget" asset="FileChangesPanel"/>`) reads the asset through `PanelAssetHolder` with the real predicates (`FindEditorCommand`, `IsKnownPanelModel`), so a file that names an unknown command or model is an issue. It subscribes to `ConfigChangedEvent` and `ConfigReloadFailedEvent` of its asset: a file with issues shows a banner (error colour, three issues as `where: message`, then `and N more`, and `Could not reload: <reason>` for an unreadable file) and the **last good asset keeps being drawn below it**; a first load that failed shows the banner alone and opens the window at once.

- **Models.** A `<source>` with a `model` is one `IPanelModel` (`CreatePanelModel` by class name, a `FACTORY_BASE`) registered in the widget's own `PanelDataSources` (the global one is its parent). A reload keeps the instance whose source name and model class did not change, so its state (such as "scanned") survives an edit of the file. A model keeps `GetObject()` current; a `TypedRef` it gives is never kept past the frame.
- **Commands.** The asset's `command` toggles the panel; any other `EditorCommandEvent` reaches the models' `RunCommand` **only while the panel is open** (the first that returns true takes it). A command a button names must be a row of the command table (`EditorCommands.cpp`), so the palette lists it; a command with an argument does nothing without one.
- **Tests.** `AssetPanelWidget::SetConfigManager` and `SetAsset` are the seams of `PanelAssetHotReloadTest`, which runs the widget over a config folder of its own; `PanelInterpreterTest` draws in an ImGui context with no backend and finds a control by its hash chain; `PanelAssetShippedTest` loads every file of `config/panels/` under the real predicates; the stress smoke validates the folder against the XSD.

A new panel is a file `config/panels/<Name>Panel.xml`, a model class when it needs data or commands, its commands in the table, and one `<widget>` line in `config/WidgetsConfig.xml`.
