# Panel assets in the editor

The editor half of "panels as data": it draws a `PanelAsset` (`config/panels/<Name>Panel.xml`) on ImGui and hosts it as a widget. The format, the loader, the sources and the reads of a bound value are the pure half, `src/Modules/BECore/Widgets/PanelAssets/CLAUDE.md` (read it first). Editor only: the folder is in the `BE_WITH_EDITOR` regex of `src/CMakeLists.txt` (`.claude/rules/widgets-module.md`). The assets are the Config Editor (`config/panels/ConfigEditorPanel.xml`, `ConfigEditorPanelModel` in `Widgets/ConfigEditor/`, `Widgets/ConfigEditor/CLAUDE.md`), the File changes panel (`config/panels/FileChangesPanel.xml`, `FileChangesPanelModel` in `Widgets/FileChanges/`) and the Game panel (`GamePanel.xml`, `GamePanelAssetModel` in `Widgets/GamePanel/`, `Widgets/GamePanel/CLAUDE.md`).

## The interpreter

`PanelInterpreter::Prepare(asset)` once per asset change parses every binding text of the tree into a `PreparedElement` tree (parsing allocates, so no frame does it); `Draw(sources, result, slots)` walks it inside the window the caller has begun and allocates nothing in a steady frame (its reader, text scratches and visitors are members whose capacity stays). `CanDraw(element)` says whether a kind is really drawn, which the test of the shipped panels uses; keep it in step with `KindOf` when a kind is added.

- **A click is noted, then emitted.** `Draw` only puts the command and the argument of the clicked button or cell into `PanelDrawResult`; the host emits `EditorCommandEvent` after the walk, because a command may change the list that is being walked. One click per frame is kept (the last). A button has no row, so its argument is empty; a table's `Button` / `Selectable` cell reads `argument` from its row.
- **Ids are the asset's.** `PushID` of the element `id` around every element, and inside a table the row index and the column `id` around every cell, so the control API's lookup by name finds a control by the ids of the file (a button's own label is the last link). The window is `<title>###<asset id>`. Ids in a file are unique per asset, which the loader checks.
- **A read that fails is a `?`**, never an error: a gone source, a wrong path and a field of another kind are what a hot-reloaded asset shows while it is edited. A condition (`visible`, `enableWhen`, a popup's `open`) is a `PanelCondition` parsed once at `Prepare`; a term that cannot be read, or a text that does not parse, counts as true (`visible`, `enableWhen`), so a broken binding is seen and not hidden; an empty one is true too. Evaluating allocates nothing. `PanelField` draws the one top-level field of the bound object as the inspector does (`SingleFieldVisitor` over `ImGuiPropertyVisitor`; the visitor is reset before each field because it numbers its widgets from a counter); `PanelFields` is a `PanelField` whose object node starts open. `PanelField::label` is not drawn.
- **Child and popup.** `PanelChild` is `BeginChild` with the asset's id (`width` / `height` in em, 0 fills the rest, optional border); a child and a popup are their own ImGui windows, so the control ids chain from them. `PanelPopup` is a modal that opens on the rising edge of its condition (true), is drawn auto-resizing while it reads true and is closed with `CloseCurrentPopup` when it reads false, so a button that clears the bool closes it one frame later (a click is emitted after the walk). An `open` that cannot be read, does not parse or is empty leaves a popup closed, against the rule above: a broken binding must not open a modal that blocks the editor. One modal at a time.
- **Controls.** `PanelCheckbox`, `PanelCombo` and `PanelNumber` (`PanelInterpreterControls.cpp`) write the bound field through `PanelBindingWriter` the moment ImGui reports a change and emit **no command**: the model sees the new value in its next `Update`, so a model that keeps a copy of the field must read it there. A read that fails is a `?`, a write that fails is ignored. A checkbox's label is `<text>###<id>`, so a `labelBind` text that changes keeps the ImGui id (the control API finds it by the `###<id>` link); `Toggle` is a button filled with the accent while on, its label in the `style` colour (disabled while off). A combo's label is `##<id>`; with no `items` it lists the names of the enum, with `items` the value is an index when it is a number and the text of a row otherwise; an index out of range shows `?`. A number is a drag or, with `slider` and `min` < `max`, a slider, over a 64-bit integer or a float by the field's own kind; bounds are always clamped; the control is in the mono font with its label `##<id>` and `text` drawn after it; there is no `format`. These kinds have no `enableWhen`: the surrounding row or `visible` hides them.
- **Selected row.** A `Selectable` cell whose column names `selectedField` is drawn selected while the row's bool reads true; the label is `<text>##select`.
- **Input.** `PanelInput` and a table's `Input` cell draw `InputTextWithHint` on a member char buffer (the bound text is copied in, cut at a UTF-8 boundary when longer than the buffer, and written back through `PanelBindingWriter` on a change; a field that is not a `String` reads fine and ignores the edit). The label is `##<element or column id>`, `icon` is a prefix of the hint, `width` is in em (0 fills the line). An `Input` cell is disabled while its `enableField` reads false.
- **Tables.** `scrollRows` N shows N rows in a scroll region (`ImGuiTableFlags_ScrollY`, rows through `ImGuiListClipper`, so a clipped row is not drawn and not found by the control API); a list that fits is a plain table. A `Button` column with a `field` is labelled with the cell's text (`<icon> <text>##<column id>`, found by its visible part). `maxLines` on a text is a child region of that many lines with a horizontal scrollbar, drawn without copying the text. `PanelFields` with a source alone draws the whole object.
- **Slots.** A `PanelSlot` calls the drawer registered under its name in `PanelSlots` (the global one unless the caller passes its own); an unknown name draws `?`. The Config Editor registers `configTree` (its tree of typed inspectors); a slot takes no arguments and draws inside the element's own id scope.

## The widget and the models

`AssetPanelWidget` (`<widget type="AssetPanelWidget" asset="FileChangesPanel"/>`) reads the asset through `PanelAssetHolder` with the real predicates (`FindEditorCommand`, `IsKnownPanelModel`), so a file that names an unknown command or model is an issue. It subscribes to `ConfigChangedEvent` and `ConfigReloadFailedEvent` of its asset: a file with issues shows a banner (error colour, three issues as `where: message`, then `and N more`, and `Could not reload: <reason>` for an unreadable file) and the **last good asset keeps being drawn below it**; a first load that failed shows the banner alone and opens the window at once.

- **Models.** A `<source>` with a `model` is one `IPanelModel` (`CreatePanelModel` by class name, a `FACTORY_BASE`) registered in the widget's own `PanelDataSources` (the global one is its parent). A reload keeps the instance whose source name and model class did not change, so its state (such as "scanned") survives an edit of the file. **The reload is deferred**: the config event only notes it, and `Update` (or the end of the command being run) applies it, because applying the panel's own file inside a model's command (`ApplyAll` -> `ConfigChangedEvent`) could drop the model that is running. `IPanelModel::Initialize()` is an empty virtual called once after the model is registered: the place for its subscriptions, document source and slots. A model keeps `GetObject()` current; a `TypedRef` it gives is never kept past the frame.
- **Commands.** The asset's `command` toggles the panel; any other `EditorCommandEvent` reaches the models' `RunCommand` **only while the panel is open** (the first that returns true takes it). A command a button names must be a row of the command table (`EditorCommands.cpp`), so the palette lists it; a command with an argument does nothing without one.
- **Tests.** `AssetPanelWidget::SetConfigManager` and `SetAsset` are the seams of `PanelAssetHotReloadTest`, which runs the widget over a config folder of its own; `PanelInterpreterTest` draws in an ImGui context with no backend and finds a control by its hash chain, `GamePanelAssetTest` draws a shipped asset and finds it by label; `ConfigEditorAssetTest` draws the Config Editor asset through a real widget; `PanelAssetShippedTest` loads every file of `config/panels/` under the real predicates; the stress smoke validates the folder against the XSD.

A new panel is a file `config/panels/<Name>Panel.xml`, a model class when it needs data or commands, its commands in the table, and one `<widget>` line in `config/WidgetsConfig.xml`.
