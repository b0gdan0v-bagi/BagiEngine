# Hardware readout of the editor's status bar

What the status bar shows besides the frame time: the GPU's temperature, load and memory (`GPU 64°C 87% 9.1/12 GB`) or, when no GPU reading exists, the CPU's load and temperature (`CPU 45% 58°C`), coloured by thresholds, with a tooltip naming the device. Nothing at all when nothing can be read. The folder is editor-only: `src/CMakeLists.txt` leaves `Widgets/EditorLayout/` out of `RuntimeModule` without `BE_WITH_EDITOR`, and the tests are in the regex of `tests/CMakeLists.txt`.

| `HardwareMonitor.*` | `SampleHardware` (which reader wins) and `HardwareMonitor` (the worker thread, the hand-over to the frame) |
| `CpuLoad.*` | `CpuLoadTracker` (ticks to a percent) and the pure parsers of the Linux files: `/proc/stat`, `/proc/cpuinfo`, a hwmon temperature and name; every platform |
| `NvmlReader.*` | `NvmlApi` (the NVML functions as a table), `LoadNvmlApi` and `NvmlReader` (device 0); built everywhere, used on Windows and Linux |

| `MacMapping.*` | `MacGpuStats` and `MapMacGpu` (what the IORegistry numbers mean), `PickAppleSiliconTemperature` (which IOHID sensors, how they combine), `DecodeSmcTemperature` (`sp78`, `flt `, `fpe2`) and the sensor names and SMC keys as constants; pure, every platform |

No ImGui and no platform code in the first two: they are tested alone (`HardwareTextTest`).

## The readings and the reader contract

- `HardwareReadings` holds integers only (°C, percent, MiB), so "changed" is exact equality and the bar never formats again for noise. A value that could not be read is empty, never 0. The name is zero-filled after its terminator (`SetHardwareName`, `NormalizeReadings`), because equality compares the bytes.
- `NormalizeReadings` is the one place that decides what is absurd: load above 100 is 100, a temperature outside -20..150 °C is missing. The sampler and `FormatHardware` both apply it.
- `IHardwareReader::Read` is called by one thread only (the monitor's worker), may take milliseconds, allocates nothing in a steady call, fills everything but `kind` and returns false (or a result without a value) for "nothing to show". A reader needs no lock for its own state.

## The monitor thread

- **Why a thread:** the art pipeline runs on the same GPU, and exactly then a driver call can stall (NVML starts in hundreds of milliseconds, a query on a saturated or sleeping GPU takes tens, an IOHID read on a Mac takes milliseconds). Polled on the frame, one stall is one visible hitch. The worker (`Thread` "Hardware stats", about once a second, `kHardwarePollPeriod`) reads at once on `Start` and then waits on a `ConditionVariable` with the stop flag as the predicate, so `Stop()` does not wait for the period.
- **The frame never waits:** `Fetch()` is one atomic load when the version did not move, otherwise a `try_lock`; a failed `try_lock` is a false answer and the frame asks again next time. The worker reads **outside** the lock and holds it only to compare and store, and moves the version only when the readings differ from the published ones, so an unchanged hardware costs the frame nothing and the bar formats nothing. A test that races a fast worker must expect a false `Fetch` now and then and ask again.
- **Readers belong to the worker.** They are touched by that one thread (or by `PollOnce`, the test hook, which asserts that no worker runs), so a reader needs no lock and may keep handles from its first `Read`.
- **Shutdown:** `Stop()` (also in the destructor) sets the flag under the lock, notifies and joins; it is idempotent, and the monitor can be started again. `Start` and `Stop` are the main thread's. Where `Thread::kAvailable` is false (the single-thread build) nothing starts and the bar shows nothing.
- `SampleHardware` is the policy: the GPU reader wins when it answers true with at least one value, else the CPU reader, else `None`; the sampler sets `kind` and normalizes.

## What the bar shows

- Segment order: GPU temperature, load, memory; CPU load, temperature (the CPU's memory is never shown). A missing value leaves its segment out, and the tooltip says so (`temperature not available`).
- Memory is MiB shown as GB with one decimal for the used amount; the total is whole when within 0.05 GB of a whole number. The unit follows the total (below 1 GiB: whole MB), without a total the used amount. A zero total is an unknown one. Memory of a `unifiedMemory` reading ends the tooltip with `unified memory, shared with the system`.
- Thresholds (named constants in `HardwareText.h`): GPU 80 / 90 °C, CPU 85 / 95 °C, memory 90 / 97 % used. Load is never coloured: a saturated GPU is the normal state while the art pipeline works.
- Everything is formatted into fixed `char` buffers and cut at their size, so a steady frame allocates nothing.

## The bar

- `StatusBar` owns the monitor. `StartHardwareMonitor()` (once, from `EditorLayoutWidget::Initialize`) builds the platform's readers and starts the worker only when at least one exists, so a platform with none costs no thread and shows nothing; `SetHardwareMonitor()` is the tests' way in (not started, driven by `PollOnce`). The monitor is joined when the bar dies: a mode switch or the end of the program.
- `Refresh()` calls `Fetch()` every frame and formats (`FormatHardware`) only when it answered true. The group sits in the left half after the allocations: the device's icon (`ICON_LC_MICROCHIP` GPU, `ICON_LC_CPU` CPU) and label in the disabled colour, then each segment in the mono font in its level's colour (`Normal` the text colour, `Warning` and `Error` the palette's), every piece with the device's tooltip. Without a visible text nothing is drawn, not even a gap.

## NVML (the GPU of Windows and Linux)

- **No SDK at build time.** `NvmlApi` declares the signatures of `nvml.h` itself and `LoadNvmlApi` resolves them with `SDL_LoadObject` / `SDL_LoadFunction` (`nvml.dll`, then the `NVSMI` folder, on Windows; `libnvidia-ml.so.1` on Linux). A machine with no NVIDIA driver loads nothing and the reader says false. A test drives `NvmlReader` through a table of fake functions and loads only a bogus library name, so it passes with and without a driver.
- **The reader loads on the worker.** `NvmlReader()` loads the library and calls `nvmlInit_v2` inside its first `Read`, never in the constructor, because both take hundreds of milliseconds. A failed load, init, device count, handle or name is final: the reader remembers it and answers false at once, and nothing is loaded again (a driver installed while the editor runs is seen after a restart).
- Device 0 only. Temperature, utilization and memory are three queries, and one that fails leaves only its field missing. Memory is rounded to MiB; the memory is the card's own (`unifiedMemory` false). The destructor shuts NVML down (only after a successful init) and unloads the library.
- `CpuLoadTracker` takes cumulative ticks: the first call, an unchanged total and counters that went back give no value and make the new sample the baseline.

## The CPU readers and where each is compiled

- **Windows:** `GetSystemTimes` into `CpuLoadTracker` (kernel time contains idle time), load only, name empty (the tooltip says `CPU`). **No CPU temperature, on purpose:** Windows gives a normal user no die temperature (WMI `MSAcpi_ThermalZoneTemperature` needs admin and is often a constant, the ACPI thermal-zone counters are empty on many desktops), so nothing is guessed. The first `Read` has no load (a delta needs two samples) and answers false.
- **Linux:** `/proc/stat`, `/proc/cpuinfo` and `/sys/class/hwmon/hwmon0..15/{name,temp1_input}` read with POSIX `open` / `read` into stack buffers (no stream and no `String` in a steady read; the file layer is for content, not `/proc`). On the first `Read` the first hwmon device named `coretemp`, `k10temp`, `zenpower` or `cpu_thermal` is picked and its `temp1_input` path kept; an ARM board with another sensor name shows load only. Everything that decides (the lines, the numbers, the names) is a pure function of `CpuLoad.h`.
- **Compiled where:** Windows (`windows-clang-debug`) builds and tests everything, and runs the Windows reader and the real NVML (the tests never load the real library). `CpuReaderLinux.cpp` was written with no Linux machine and has been **compiled nowhere** (only syntax-checked on Windows against a stand-in `unistd.h`): whoever builds on Linux first runs `cmake --preset`, builds `BagiEngineTests` and `ctest -R "Hardware|EditorBars"`, then looks at the bar with a hwmon CPU device. A platform with no reader makes the monitor read nothing and the bar show nothing.

## macOS

- **Compiled where:** `MacGpuReader.cpp`, `MacCpuReader.cpp`, `MacSensors.cpp` and the Mac headers have **never been built or run on a Mac**. They were syntax-checked on Windows (`clang -fsyntax-only -DPLATFORM_MACOS -Wall -Wextra`) against stand-in `CoreFoundation`, `IOKit`, `mach` and `sysctl` headers written from memory of the real declarations: that proves the code parses and the calls match the declared signatures, nothing about the real SDK, the registry or the reference counts at run time. The one layout it can prove is `static_assert(sizeof(SmcKeyData) == 80)`, which holds on Windows with the same alignment rules. What decides (`MapMacGpu`, the sensor picker, the SMC decoder) is pure and built and tested everywhere (`HardwareMacMappingTest`). `src/CMakeLists.txt` links `-framework IOKit -framework CoreFoundation` into `RuntimeModule` when `APPLE` and the editor are on (in the form of `RemoteControl/CMakeLists.txt`); untried too.
- **To verify on a Mac:** `cmake --preset macos-debug`, `cmake --build --preset macos-debug --target BagiEngineTests`, `ctest --preset macos-debug -R "Hardware|EditorBars"`, then start an editor build and look at the bar.
- **The GPU:** `IOServiceMatching("IOAccelerator")` and `IOServiceGetMatchingServices` list the accelerators; per service `IORegistryEntryCreateCFProperty` gives `PerformanceStatistics` (a dictionary, skipped when it is another type) and `model`. With several accelerators the one with the highest utilization is taken (the first on a tie). Memory is `MapMacGpu`'s: a card with `vramUsedBytes` and `vramFreeBytes` shows its own memory; otherwise `In use system memory` is the used part of the unified memory, whose total is `hw.memsize` (read once), and the tooltip says it is shared with the system. `Alloc system memory` is not read.
- **The CPU:** `host_statistics(HOST_CPU_LOAD_INFO)` gives cumulative ticks (user + system + nice busy, plus idle) for `CpuLoadTracker`; the name is `machdep.cpu.brand_string`. A failing call leaves the load missing and the temperature is still read.
- **Reference rules.** `CfOwned` (`MacCoreFoundation.h`) releases with `CFRelease`; a function with `Create` or `Copy` in its name returns +1 and goes into a `CfOwned` at once, a `Get` result (`CFDictionaryGetValue`) is borrowed. Every CF value is checked with `CFGetTypeID` before it is cast, and a missing or mistyped key is a missing value. `IOServiceMatching` is +1 and consumed by `IOServiceGetMatchingServices` on every outcome; the iterator and each service are `IOObjectRelease`d by the file's `IoObject` on every path (a `continue` included). `mach_host_self()` adds a send right once, in the constructor, and the destructor gives it back with `mach_port_deallocate`; `host_statistics` fills a plain struct, which is why it is used instead of `host_processor_info`.
- **Unverified registry keys** (a wrong one is a missing field in the bar, never a crash). Check with `ioreg -r -c IOAccelerator -w0`: `PerformanceStatistics` with `Device Utilization %` (a number) and `In use system memory` (bytes) on Apple Silicon and Intel; `vramUsedBytes` and `vramFreeBytes` (bytes, AMD cards) are a guess; the accelerator's `model` (a string or data). `sysctl hw.memsize machdep.cpu.brand_string` for the rest.

### Temperatures

One `MacSensors` (reference counted, `MakePlatformHardwareMonitor` hands it to both readers; used by the worker only) opens on its first read, on the worker.

- **IOHID (Apple Silicon).** `IOHIDEventSystemClientCreate`, `...SetMatching`, `...CopyServices`, `IOHIDServiceClientCopyProperty`, `...CopyEvent` and `IOHIDEventGetFloatValue` are private: they are resolved from the IOKit library with `SDL_LoadFunction` and never linked, and one missing symbol turns the path off. The filter is `PrimaryUsagePage 0xff00`, `PrimaryUsage 5`; per service the `Product` name and the event of type 15 (temperature, field `15 << 16`) become a `MacSensorSample` in a fixed array. `PickAppleSiliconTemperature` decides: GPU the mean of `GPU MTR Temp Sensor*`, CPU the highest of `pACC MTR Temp Sensor*`, `eACC MTR Temp Sensor*` and `PMU tdie*`; a value outside 0..150 or a NaN is skipped. Every +1 object (the client, the matching dictionary and its numbers and keys, the service array, a product, an event) is in a `CfOwned`, an array element is borrowed.
- **SMC (Intel, used when IOHID found no sensor).** `IOServiceMatching("AppleSMC")`, `IOServiceOpen` and, per key, two `IOConnectCallStructMethod(2)` calls with the 80-byte `SMCKeyData` of the open-source readers (selector 9 for size and type, 5 for the bytes). The connection is closed with `IOServiceClose` in the destructor and the service and iterator are `IoObject`s. A failing return, a short answer, a non-zero `result`, a zero or too large size or a value outside 1..150 is no value (an absent key reads 0). Keys tried in order, the first that decodes wins: CPU `TC0P`, `TC0D`, `TC0E`, `TCXC`; GPU `TG0P`, `TG0D`, `TGXC`.
- **All of it is unverified on a real Mac.** A wrong name, key or layout shows as a missing temperature in the bar, never a crash (every path checks its return). To check: `ioreg -r -c AppleSMC -w0` (the SMC exists), the output of the open-source `smctemp` (Intel keys) and `macmon` (Apple Silicon sensor names) against the constants of `MacMapping.h`; no temperature on an Apple Silicon Mac means the `Product` names differ on that chip, and the fix is a prefix in `MacMapping.h`, tested by `HardwareMacMappingTest`.
