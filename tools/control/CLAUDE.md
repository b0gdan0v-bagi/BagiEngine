# Control Tools Guidelines

## Overview

Python tools that drive a game through the control API (`src/Modules/RemoteControl/CLAUDE.md`, protocol in `src/Modules/BECore/Control/CLAUDE.md`). They are separate processes: the engine has no MCP or Python dependency. Python 3.10+. Nothing here names a game apart from the engine's `BagiStress` in examples; a game with its own tools (the Stockfish bridge of BagiEngine-Chess) keeps them in its own repository and imports the client from here.

| File | Purpose |
|------|---------|
| `bagi_control_client.py` | WebSocket (RFC 6455) client with the standard library only: `BagiControlClient.call(method, params)`, pushed events in `events`, `ControlError` for an error response |
| `game_process.py` | `GameProcess`: starts a game executable with `--control`, retries until it listens, keeps its log; `build_game_command`, `free_port`, `preset_executable`, `log_problems` (the Warning, Error and Fatal lines of its log), `PORT_TAKEN_MARKER` |
| `scenario.py` | The scenario file ("Scenario files"): `load` / `dump`, the expectations (`evaluate`), what a recording writes (`minimal_expect`, `full_expect`) and `--update` writes (`updated_expect`). Standard library only, no I/O besides the two |
| `bagi_session.py` | `GameSession`: one game, started (`launch`) or reached (`connect`), as plain Python calls. No MCP code, so it is tested without the `mcp` package. `SessionError` for what the session refuses; a refusal of the game stays a `ControlError`. Records the calls as a scenario ("Scenario files") and keeps the pushed events (`take_event`) |
| `scenario_shrink.py` | `shrink(items, fails, max_probes)`: delta debugging, the 1-minimal sublist that still fails. Pure, no I/O, knows no session |
| `bagi_play.py` | The scenario player ("Playing a scenario"): `play(exe, header, steps, update, lenient)` and the command line |
| `bagi_reference.py` | `check_reference`: the `reference` expectation of a screenshot line (reads the PNG next to the scenario, compares, writes the failure pictures, updates the reference); `default_failures_dir`. Puts `tools/shots` on `sys.path` |
| `bagi_backends.py` | The backend comparison command ("Comparing backends"): `capture_profile`, the profile table `PROFILES` and the command line |
| `bagi_image.py` | `run_image_diff`: the tool `image_diff` without MCP code (operands, `screen`, the map file, the preview); `ImageError`. The comparison is `tools/shots/png_diff.py`, which it puts on `sys.path` |
| `bagi_mcp.py` | The MCP server (stdio). Each tool is one line over `GameSession` (or `bagi_image`); the only file that needs `mcp` |
| `requirements.txt` | `mcp` (2.x) and `pytest`; nothing else is needed |
| `tests/` | pytest, plus `smoke.py` (the ctest entries `Bagi<Game>ControlSmoke`, `.claude/rules/cmake-rules.md`). `smoke.py` is a game-neutral default (the common methods, a screenshot, the UI tree: no game rules), so any game that implements the control API gets a smoke test from `be_add_game_control_tests` alone; a game with rules brings its own `SCRIPT` that imports the helpers and calls `run_smoke()` (BagiEngine-Chess `tests/control_smoke.py`). `BagiStress` has one (`tools/stress/tests/stress_smoke.py`, which also checks the game's log) |

## Running

Use the repository venv (`CI/setup_venv.*` makes `.venv`; on Windows `.venv\Scripts\python`, made by `CI\setup_venv.bat`, which needs `uv`), then once `.venv/bin/pip install -r tools/control/requirements.txt` (Windows: `uv pip install --python .venv\Scripts\python.exe -r tools/control/requirements.txt`).

```bash
.venv/bin/python -m pytest tools/control/tests                # the tests
```

## Scenario files

A session recorded as JSON lines (UTF-8, one object per line, no comments, blank lines skipped) that a player replays as a test. `scenario.py` holds the format; a file that breaks it is a `ScenarioError` naming file and line.

- **Line 1, the header:** `{"scenario": 1, "game": "Stress", "flags": ["--headless", "--manual-clock"], "title": "..."}`. `scenario` is the format version (a tool refuses a number it does not know and says so); `game` is the active game's name (`list_games.active`, checked after the start); `flags` are the start flags besides `--control` / `--control-port` (`--headless` and `--manual-clock` map onto the launch options, any other goes to the game as it is, so a flag of a later entry fits); `title` is free text.
- **Every other line is one control call:** `{"method": "perform_action", "params": {...}, "expect": {...}}`, sent in order on one connection. `params` and `expect` are optional, `note` (free text) is ignored.
- **`expect`**, every member optional, all must hold, checked in this order:
  - `error`: the error code the call must answer. An error without this member fails the line (the shrinker's `lenient` mode tolerates it); an `error` that does not happen fails too.
  - `result`: the whole answer equals the value. `equal`: each member of the answer (top level) equals the value. `pointers`: JSON pointer (RFC 6901, `/state/score`, `/a/0/b`) to value; a missing path is its own "absent", not `null`. Equality is JSON's: `true` is not `1`.
  - `reference`: only on a `screenshot` call: `{"png": "references/x.png", "threshold": 2, "maxShare": 0.0005, "region": [x0, y0, x1, y1]}`. The picture is compared with the PNG at `png` (relative to the scenario file, required); `threshold`, `maxShare` and `region` are the line's own tolerance (`tools/shots/CLAUDE.md`, "Comparing two pictures"; defaults 0, 0 and the whole picture): it fails when more than `maxShare` of the compared pixels differ by more than `threshold`. A reference of another size fails (nothing is scaled silently). `bagi_reference.py` judges the picture; `scenario.py` holds only its shape and verdict.
  - `versionStep`: `answer.version` minus the last `version` seen in an earlier answer of the run (any object result with an integer `version`). Relative on purpose: a scenario does not break when a counter starts elsewhere. Not checked when no version was seen before.
  - `event`: `{"name": "state_changed", "equal": {"version": 5}, "timeout": 5}`: a push of that name whose `data` has these members arrives (already received, or within `timeout` seconds, default 5); the matching push is consumed.
  - `logClean`: `true`: no line of the game's log since its start has the level Warning, Error or Fatal.
- **What is written.** A recording (mode `minimal`, the default) writes `error` and `versionStep` only, so a scenario survives a change of the game's data and fails on what the API promises. Mode `full` adds `result`; the picture of a `screenshot` is never written, its `width` and `height` go to `equal` instead. `equal`, `pointers`, `reference`, `event` and `logClean` are added by hand, never by default. `--update` of the player rewrites the values of `error`, `result`, `equal`, `pointers` and `versionStep` that a line has, drops what no longer applies, adds the minimal ones to a line with none of the five, writes `error` for a call that now answers one (whatever the line had), and keeps `reference`, `event` and `logClean`.
- **Recording** (`launch(record=)`, `connect(record=)`, `start_recording` / `stop_recording`, mode `minimal` or `full`) hooks `GameSession.call` alone: a call the game answered, or refused with a `ControlError`, becomes a line. Not recorded: a `SessionError`, the `list_games` / `status` the session asks for itself, a trailing `quit` (the player stops the game itself). The header is built at the start: `game` from `list_games.active`, `flags` from the launch options (`connect`: `--manual-clock` from `status` only, never `--headless`, which a person's window is not). The file is written by `stop_recording`, and by `quit` / `close` when a recording is still on, so a crashed game keeps it. A scenario replays from a fresh start, so a recording that begins after calls or on a game that was only connected to says so in its answer.
- **Pushes** are kept in a bounded deque (every action pushes, and nobody has to read them; the oldest are dropped) for `take_event(match, timeout)`; `log_problems()` reads the log of a game the session started.
- `dump` writes the stable form (members in a fixed order, `ensure_ascii=False`), so a loaded and dumped file does not change and a diff shows the real change.

### Playing a scenario

`python3 tools/control/bagi_play.py <exe> <scenario.jsonl>` (or `--preset P --game G <scenario>`; `--timeout` is the start-up wait, `DEFAULT_STARTUP_TIMEOUT` of `game_process.py`) starts the game with the header's flags (`--headless` / `--manual-clock` map onto the launch options, the rest go to the game), checks `game` of the header against `list_games.active`, sends the calls in order and stops at the first line whose expectation fails. It prints `FAILED <file>:<line>  <method> <params>` (params cut at `PARAMS_SHOWN` characters), then `expected <name>: ...` and `actual: ...`; a pass prints `PASSED <file>: N calls`. Exit codes: 0 passed, 1 failed (also a game that did not start, was lost, or exited non-zero after `quit`), 2 a bad file or arguments (a `ScenarioError`, an unknown format version), 77 the executable does not exist (ctest: skipped; a bad file is judged first, so a broken scenario fails even where the game is not built). A launch that finds its port taken is retried once on another port, announced on stdout, as in the smoke test.

- `play` is the function the shrinker reuses: it answers a `PlayResult` (the failing step and its `Failure`, or an `error`), `lenient=True` tolerates an error a line did not expect (but not at `strict_step`). A `step` gets the timeout of its frames in `GameSession.call` itself, so a scenario's long step does not hit the default.
- **`logClean` is judged after `quit`**, not at its line: the game's stdout is block-buffered into the log file when redirected (only Error and Fatal go to the unbuffered stderr), so a Warning logged before the line may not be in the file yet. The failure is still reported at the line that asked for it, and what the game logs while shutting down counts too; put it on the last line. `GameSession.log_problems()` reads the log of a game that has quit.
- **`--update`** plays every call without stopping at an expectation, rewrites the expectations with `scenario.updated_expect` and writes the file only when the run completed (a lost connection or a bad exit writes nothing); it prints the lines that changed. `event` is not waited for in this mode. It also writes the reference pictures (the game's own PNG bytes, folders made) that are missing or differ at threshold 0, prints `created reference <path>` / `updated reference <path> (<share> changed)` and leaves an equal file alone; the `reference` member itself stays as written. A reference it cannot write, or a screenshot without a picture, fails the run (exit 1, the file untouched); a PNG is written when its line is played, so a failed run keeps those already written.
- **Reference pictures** live in `references/` next to the scenario (committed, small: take them with a fixed `maxSize`, long side about 400, on the manual clock after a `step`, so the same build gives the same pixels). A failed comparison writes `<name>.actual.png` and `<name>.diff.png` (A grey, changes red) into `<temp>/bagi-reference/<scenario name>/`, never the repository (`--failures DIR` changes it; a folder inside a git work tree is refused, exit 2) and names both in the failure. A change on purpose is `--update`; the reference is then reviewed like code. The engine's own example: `tools/stress/tests/scenarios/ui_reference.jsonl` (`BagiStressScenario.ui_reference`, no tolerance: the software renderer is exact).

`be_add_game_scenario_tests(<ExeTarget> DIR <folder>)` (`cmake/BagiEngine.cmake`) turns every `*.jsonl` of a folder into the ctest entry `<ExeTarget>Scenario.<file>`, which runs this player on the built executable (the engine's own: `tools/stress/tests/scenarios/`). A game in its own repository adds its folder and the call in its CMakeLists; a new file needs no CMake edit.

### Shrinking

`bagi_play.py <exe> <scenario> --shrink OUT` cuts a failing scenario down to the calls the failure needs, for the QA loop: record a long session, play it, and shrink the one that fails into a small regression file. The scenario has to fail (else exit 2, nothing written). A probe starts the game and plays a candidate list of the calls with **every `expect` stripped except that of the originally failing line**, in `lenient` mode: a dropped call moves the versions and answers of the calls after it, so the other expectations would only add noise, and an error they did not expect must not end the probe. The target line itself is not lenient (`strict_step`): when the dropped calls were its setup it answers an error, which is another failure and not the one being shrunk. A probe fails when that line fails again with the same expectation name. The written file keeps the header and the surviving calls with their original `expect`. `--max-probes` (default `DEFAULT_MAX_PROBES`) bounds the game launches; at the limit the best list so far is written and the output says so. `shrink` itself keeps the list in order and tries chunks of halving size, then single calls.

## Comparing backends

`python3 tools/control/bagi_backends.py <exe> <scenario.jsonl> --out DIR [--backends software,window] [--threshold N] [--max-share X]` (or `--preset P --game G <scenario>`) plays the calls of a scenario on each profile **without their expectations** (`reference` too), keeps the PNG of every `screenshot` call in `DIR/<profile>/<n>-<scenario name>.png`, then diffs each profile with the first available one (A; B is scaled when the size differs) and writes `DIR/diff-<profile>-<n>.png`. `--out` is refused inside a git work tree. The profiles are data in `PROFILES`: `software` (`--headless`: the SDL software renderer, always runs) and `window` (a real window with the renderer of the game's `ApplicationConfig.xml`: with `VulkanRendererBackend` the `screenshot` is refused and the profile is "not available"). A profile that does not start, loses the game or cannot take a picture is `not available: <reason>` and skipped. `vulkan` and `browser` are listed as "cannot capture" and never started: `VulkanRendererBackend` has no capture and the browser build cannot be reached by these tools (`src/Modules/SDL/CLAUDE.md`, "Headless and screenshots"). The tool informs (two renderers differ in anti-aliasing): exit 0 whatever the pictures show, also with fewer than two available profiles; 1 only when `--max-share` (0..1) is exceeded by a picture, 2 a bad file or argument (also a scenario with no `screenshot`), 77 the executable is missing.

## The by-name methods

`get_property`, `set_property`, `call_method`, `list_types`, `describe_type` and `schema` (`Reflection/CLAUDE.md`, "Reflection methods") are plain `client.call(...)` for a script; no MCP tool wraps them yet. `tools/schema` exports `schema` and makes an XSD of it (`tools/schema/CLAUDE.md`).

## Naming the game

A caller gives the executable as a path, or as a preset and a game name: `preset_executable(preset, game, root)` is `<root>/build/<preset>/bin/<game>[.exe]` (a multi-config preset: the newest `bin/<Config>/`; `root` defaults to the repository holding these tools, so a game that carries the engine passes its own). `GameSession.launch` and `launch_game` take `exe` or `preset` + `game`, exactly one of the two; `smoke.py` takes `--exe` or `--preset` + `--game` (the ctest entries pass `--exe $<TARGET_FILE:...>`). The tools never hard-code a build folder: the layout belongs to `cmake/BagiEngine.cmake`.

## The smoke test and the free port

`tests/smoke.py` (`run_smoke`, `play`) starts the game on a port from `free_port()`, which binds port 0, closes the probe and hands the number over, so another process may take the port before the game binds it. `play_with_retry` covers that window: when the game fails to bring the API up and its log tail holds `cannot listen on 127.0.0.1:` (what `Application::StartControlServer` logs; `PortTaken`), the scenario is played once more on a new port and the retry is announced on stdout. Any other failure is not retried, and neither is a port given with `--port`. A port held by a live listener costs about 30 s (the startup timeout) before the retry. In ctest the entry takes the `bagi_control_smoke` lock, so two smoke tests of one run do not start together (`.claude/rules/cmake-rules.md`).

## The MCP server

`claude mcp add bagi -- .venv/bin/python tools/control/bagi_mcp.py` (Windows: `.venv\Scripts\python`). The repository has no `.mcp.json`: the interpreter path differs per machine. Tools: `launch_game`, `connect`, `status`, `get_state`, `list_actions`, `perform_action`, `set_state`, `reset`, `step`, `screenshot` (an image), `image_diff`, `ui_tree`, `ui_click`, `click_at` (a click at a point), `frame_stats`, `profiler_dump`, `zone_allocs` (the profiler's methods, `src/Modules/BECore/Profiler/CLAUDE.md`), `game_log`, `record_start`, `record_stop` (a recording of the session as a scenario, "Scenario files"; `launch_game` and `connect` take `record=` too), `quit`. `launch_game` starts the game `--headless --manual-clock`, so a screenshot works and nothing moves until `step`. What `ui_tree` reports and what `ui_click` emits (`at` sets a slider, a dropdown opens in two clicks, a click changes nothing until `step`): `.claude/rules/ui-control-api.md`.

- **`image_diff(a, b, out?, threshold?, region?)`** compares two pictures (`tools/shots/CLAUDE.md`, "Comparing two pictures": region, threshold, scaling and the stats). An operand is a PNG file (`~` expanded, relative to where the server runs) or `screen`: the connected game's picture now at full size (`maxSize` 4096; `step` first), so two files need no game. It answers `[stats as JSON text, image]`: the image is the difference map (A grey, changes red) shrunk to at most `PREVIEW_SIZE` pixels; `out` also writes the full-size map (folder must exist, outside every git work tree, then `out` is in the stats). An unreadable file, a bad region or threshold is an `ImageError`, shown to the model like a refusal. Uses: a before and an after of a change, a render against its Figma mockup (the mockup as B, so it is scaled to the render), the same scene on two backends.
- Written for `mcp` 2.x (`MCPServer`, `ToolError`); 1.x had `FastMCP` and is not supported.
- **Every tool is wrapped in `reports_errors`.** The server shows the model only the message of a `ToolError`; any other exception becomes "Error executing tool X" and the model would never see `illegal_action` or `promotion_required`. A new tool needs the decorator; `test_dispatch.py` checks this over a real stdio connection.
- The game's stdout goes to a log file, never to the server's: stdout is the MCP protocol.
- `GameSession.call` drops the connection on a timeout, because the late answer would be taken for the answer of the next call.

## Tests without the real things

`tests/fake_control_server.py` (a WebSocket server answering from a Python function), `fake_game.py` (a game executable that serves it: a growing state version, a `state_changed` push behind each action, `warn` writes a log line of a level; `FAKE_GAME_PICTURE` names the PNG that `screenshot` serves). `FakeControlServer.push` sends a push before or after the answer. The `fake_game_exe` fixture of `conftest.py` makes the executable: a script with a shebang, and on Windows a `FakeGame.bat` that runs `fake_game.py` with `%*`, so no test is skipped there. Killing the `.bat` ends `cmd.exe` and not the Python process, so `fake_game.py` ends by itself after `WATCHDOG_SECONDS` if nobody sent `quit`. A gone game can show as a reset connection (`WinError 10053` / `10054`) or a close frame; `GameSession.call` reports both as "the game closed the connection". New tool code gets a test against these before it is tried on the real game.
