# Web Tools Guidelines

## Overview

Python tools for the browser build (entry `web-build` of the todo store; the CMake side is `cmake/BagiWeb.cmake` and the presets `web-release` / `web-debug` (threaded, the default) and `web-release-single-thread` / `web-debug-single-thread`, `.claude/rules/cmake-rules.md`; the page is `web/shell.html`). They are separate processes with the standard library only (Python 3.10+; `brotli` is used when it can be imported). Nothing here names a concrete game apart from `BagiMatch3` as the default. The unit tests build a fake build output; the real build is checked by the browser smoke (below).

| File | Purpose |
|------|---------|
| `package.py` | `package.py <build-dir> <out-dir> [--game NAME] [--single-thread] [--app FILE]`: a web build's `<game>.html` / `.js` / `.wasm` / `.data` into a folder to serve. The page becomes `index.html`, the rest keep their names (they load each other by name); each of the four gets `name.gz`, and `name.br` when `import brotli` works; `manifest.json` is `{game, threads, files: {name: {size, sha256, gzip, brotli}}}`, `threads: false` with `--single-thread` (`serve.py` decides the isolation headers on it). Files of an earlier run that the new manifest does not list (and a stale `.br`) are deleted; files of other kinds are left alone. It also writes `manifest.webmanifest` (never `manifest.json`: that is the package manifest) and `icons/` (cleaned each run), listed in `manifest.json` with no `.gz` / `.br`: "The web app file". Several pages need `--game`; a missing `.js` / `.wasm`, or a `.data` the script names, is an error; the output folder must not be, hold or sit in the build folder (`PackageError`: the cleaning would delete the page) |
| `serve.py` | The static server of the Railway service. **One file that imports nothing of this repository** (the Docker image copies only it; a test checks it). `serve.py --root dist [--host H] [--port P] [--cross-origin-isolation \| --no-cross-origin-isolation] [--quiet]`; `PORT` (default 8080), `COOP_COEP=1/0`, `BASIC_AUTH_USER` and `BASIC_AUTH_PASSWORD` from the environment. The headers and the isolation decision: "The headers of `serve.py`, and why" |
| `build_and_deploy.py` | The one command: configure and build the preset, `package.py` (with `--app <source>/web/app.json` when that file exists; its own `--app` wins), and with `--deploy` the staging and `railway up <staging> --path-as-root --service <name> --detach`. `--single-thread` adds the suffix `-single-thread` to the preset, packages `build/<preset>/bin` of that preset (`--build-dir` wins) and packages with `--single-thread`. `--dry-run` prints the commands. Programs are started by the path `shutil.which` found. Exit 2 with `run: python CI/scripts/setup_emsdk.py` when the SDK in `external/emsdk` is missing (also with `--dry-run`), when `--deploy` finds no `railway` on PATH, or when a program cannot start or the staging fails |
| `Dockerfile`, `railway.json` | `python:3.12-slim`, `COPY serve.py` and `dist/`, `CMD ["python", "serve.py", "--root", "dist"]` with no isolation switch (the default does it), user `nobody`; Railway: builder Dockerfile, health check `/healthz` |
| `tests/web_smoke.py` | The browser smoke: serves a `dist/` with `serve.py` (the real isolation decision, `serve.decide_cross_origin_isolation(None, None, root)`), opens it headless in Chromium or Edge through Playwright and checks (1) the page loads, (2) a first frame that is not one flat color, (3) a click or tap changes the picture, (4) the console, (5) the backing store, (6) the web app manifest and its icons. The checks, the options and the exit codes (0 / 1 / 77 skipped / 2) are in its docstring; `--selftest[-fault]` runs it on a generated page |
| `tests/` | `unittest` (`python -m unittest discover tools/web/tests` from the engine root; pytest also runs them): `test_package.py`, `test_serve.py`, `test_deploy.py`, `test_setup_emsdk.py` (`CI/scripts/setup_emsdk.py`, fake runner, no SDK, no network), `test_cmake_web.py` (+ `check_bagi_web.cmake` under `cmake -P`; skipped without cmake), `test_shell.py`, `test_web_smoke.py` (the browser-free parts; its `RealBrowserTest` cases skip without Playwright or the browser), `web_fixtures.py` (a fake build output in a temp folder; no binary is committed) |

## The package

- **The four files are the same for both configurations:** emcc 4.0.23 writes no `<game>.worker.js`; a Worker starts from `<game>.js`.
- **The `.data` package** holds the `config/` and `assets/` of the engine, the game and the web overlay (`be_web_preload_args`); nothing unneeded is packed. SDL_image is built without TIFF and WebP on the web (`cmake/BagiEngine.cmake`).
- **`-O2` stays the default** (`BE_WEB_OPTIMIZATION`): `-Oz` saves a fraction of the download and costs run time. `-Wno-pthreads-mem-growth` is a link option on purpose (`cmake/BagiWeb.cmake`).
- **Debug** gives a `.wasm` of tens of MB; brotli at quality 11 takes minutes on it, so package it with a Python that has no `brotli`.

## The headers of `serve.py`, and why

| Rule | Why |
|------|-----|
| `Content-Type` from a table in the file (`application/wasm`, `application/octet-stream` for `.data`, `text/javascript`, `text/html; charset=utf-8`, `application/json`, `application/manifest+json` for `.webmanifest`), the file's type also for a compressed copy | A wasm compiles by streaming only as `application/wasm`. Not `mimetypes`: on Windows it reads the registry and has answered `text/plain` for `.js` |
| `name.br`, then `name.gz`, by `Accept-Encoding` (q-values, `q=0` refuses, `*` allows both); `Content-Encoding`, `Vary: Accept-Encoding`, the encoded `Content-Length` | The wasm and the package are the large downloads. `name.gz` / `name.br` are never served as files (404); a file with no variant gets no `Vary` |
| `index.html`, `manifest.json` and `manifest.webmanifest` in the root: `Cache-Control: no-cache` plus `ETag`; everything else `public, max-age=3600` plus `ETag`; `If-None-Match` (a list, `*`, weak tags) gives 304 | A new deploy must show at once, and the other names are **not hashed** (`BagiMatch3.wasm` in every build), so a long cache or `immutable` would keep an old wasm beside a new page. The tag is `mtime-size-encoding` |
| `GET /healthz` -> 200 `ok` (`no-store`) | The health check of `railway.json` |
| **Access:** with `BASIC_AUTH_USER` and `BASIC_AUTH_PASSWORD` both set, every request except `GET /healthz` needs them: 401 with `WWW-Authenticate: Basic` (the isolation headers too; a 401 to a method other than GET / HEAD closes the connection). Neither set: open. One of them, an empty one, or a user with a colon: the server does not start. The comparison is `hmac.compare_digest`; the start line never prints the password | Railway puts no password on a service, and a game for testers must not be public. The secret is a variable of the service (`railway variables`), not a file of the image or of git, so the Dockerfile and the staging are the same for every service. It is a gate for testers, not accounts (no log-out, no per-person rights) |
| `..`, `%2e%2e`, `%2f`, backslash, NUL, a link out of the folder -> 404 | The path is cut into segments before the file system is touched, and the resolved path must stay below the root |
| `HEAD` works; any other method is 405 with `Allow: GET, HEAD` and `Connection: close` (the body is not read); `Server: BagiWebServe` | No Python version on the wire |
| `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` on every answer (304 and errors too). First match wins: the switch, then `COOP_COEP`, then the boolean `threads` of `manifest.json` in the root, then **on**. The start line prints the decision and its reason | A pthread wasm needs `SharedArrayBuffer`, which only a cross-origin isolated page gets: the threaded build (the default) does not start without both headers. The single-thread build needs neither and is served without them, so it works on a host that cannot send them. The headers break a page that embeds another origin without CORP. Unknown means on: a needless header costs a page that embeds nothing, a missing one a game that does not start |

## The web app file

`<source>/web/app.json` belongs to the game (the root of the project that runs `build_and_deploy.py`; the engine itself has none and needs none). All keys optional: `name`, `short_name`, `orientation` (`any` default, `landscape`, `portrait`), `background_color`, `theme_color` (`#rrggbb`; default `#101114`), `icons` (`[{"src": PNG path relative to app.json, "sizes", "purpose"}]`). Defaults: the name is the game stem; with no icons `package.py` generates flat `theme_color` PNGs of 192 and 512, because Chrome treats a page without icons as not installable (it would open a tab with the bars). A bad file, a missing or non-PNG icon, or one outside the folder of the file (`..`) is a `PackageError`. The manifest says `display: fullscreen` (fallback `standalone`), `start_url`, `scope` and `id` `./`. The page links it with `crossorigin="use-credentials"`: a closed service uses Basic auth, and a manifest request without credentials would get 401.

## The page and the isolation

**Decided (slice 2 of `web-build`): threaded is the default, and the headers follow it.** The signal is `threads` in `manifest.json`, written by `package.py`, not a guess from the file names; the deployed image needs no switch.

The shell cannot know whether its build is threaded, so `be_web_configure_target` writes a copy of `web/shell.html` into the build folder (`be_web_generate_shell`: `configure_file(@ONLY)`, `@BAGI_WEB_THREADS@` = `1` or `0`) and `--shell-file` points at the copy. The threaded copy first tests `window.crossOriginIsolated` and `SharedArrayBuffer`; when either is missing it shows "This page needs cross-origin isolation" with the two headers named (plus a secure-context sentence when `window.isSecureContext` is false: plain `http://` from a host that is not `localhost`) and does **not** start the module (a pthread wasm without `SharedArrayBuffer` fails with a cryptic error). The HTML minifier folds the comparison, so the single-thread page has no test at all. `check_bagi_web.cmake` checks both generated copies.

The other messages of the shell: "WebGL is not available" (the module is not started), "The game could not be loaded" / "The game stopped" (`Module.onAbort`, a page error, and an `unhandledrejection` handler, because emcc's package loader is an async function nobody awaits, so a `.data` that fails to download is only a rejected promise), "The game has ended" after Quit (`-sEXIT_RUNTIME=1`, `emscripten_cancel_main_loop()` then `Finish()`; emsdk 4.0.23 calls `Module.onExit` with **no status**).

**Fullscreen and the home-screen app.** The page names nothing of a game. It links `manifest.webmanifest` and `icons/apple-touch-icon.png` (both relative: the only references the page has), the apple / `mobile-web-app-capable` meta tags and `theme-color`. A toggle button (top right, off the safe area, takes its own touches) is shown when `document.fullscreenEnabled` (or the `webkit` form) is true and the page is not an installed app (`navigator.standalone`, `display-mode` read once at start: it also matches after the page itself went fullscreen). On a coarse pointer the first touch `pointerup` asks for fullscreen once per load; `?fullscreen=0` turns that request off. After fullscreen starts the shell calls `screen.orientation.lock` with the `orientation` it read from the manifest (unless `any`), errors ignored. Three degradations, none stops the game: no API (iOS Safari: no button, the home-screen app is the way), refused (a plain page), installed (the manifest does it). The code runs in a `try` after the WebGL test, and every promise has a rejection handler, or `unhandledrejection` would show "could not be loaded". The download bar counts decoded bytes against the compressed `Content-Length`, so a total that the count has passed stops driving the bar.

## Deploying

`build_and_deploy.py` works from the root of a project that has the web presets (the engine, or a game that carries it as `engine/`; `--source-dir` names another). It needs the Emscripten SDK (`python CI/scripts/setup_emsdk.py` installs it into `external/emsdk` once per checkout, about 2 GB; the presets find it), and for `--deploy` the Railway CLI logged in (`railway login`, `railway link`), or `RAILWAY_TOKEN`; the script reads and writes no secret. Defaults: the page in `<source>/build/<preset>/bin` (the single-thread presets have a binary dir of their own, because their libraries are built without `-pthread` and must not meet the threaded ones), the package in `<source>/dist` (in the engine's `.gitignore`; a game adds it to its own), the staging in `<source>/build/web-deploy`. The staging holds `Dockerfile`, `railway.json`, `serve.py` and a fresh copy of `dist/`, and `railway up` gets it explicitly with `--path-as-root`, so it never uploads a linked parent such as the engine root.

By hand: `cmake --preset web-release`, `cmake --build --preset web-release --target BagiMatch3`, `package.py build/web-release/bin dist`, `serve.py --root dist` (http://localhost:8080). The single-thread page: the preset `web-release-single-thread`, `package.py build/web-release-single-thread/bin dist-single --single-thread`, `serve.py --root dist-single`. A threaded page from a host that is not `localhost` over plain `http://` is not a secure context and never isolated, whatever the server sends: use `localhost` or https. The Railway service is made once (`railway add --service bagi-web`, a domain, `railway link`). To close it: `railway variables --service <name> --set BASIC_AUTH_USER=<user> --set BASIC_AUTH_PASSWORD=<password>` and redeploy (the server reads them at start). Nothing is deployed by the tests or by the loop; how `link` and a path interact is not checked against a real Railway CLI.

**The `.data` package and relinks.** The content is packed into `<game>.data` at **link time**. `be_web_configure_target` lists every content file in `LINK_DEPENDS` (globbed with `CONFIGURE_DEPENDS`) and, per folder, a stamp `web-content/<target>_bagi_<layer>_<folder>.txt` with the sorted list of the files (`be_web_content_inputs`, written with `file(CONFIGURE)`, so only when the list changes). An edit relinks because the file is newer than the package; an added or deleted file because the stamp changes (a deleted file alone leaves no trace in the inputs, and the `--preload-file` line does not change). The relink is the price of editing content, and the globs run at the start of every build.

## The browser smoke

Playwright is not a dependency of the repository and the tests never install it. Keep it in a venv inside the git-ignored `build/` (the browser cases of `test_web_smoke.py` skip without it):

```bash
python -m venv build/web-venv
build/web-venv/Scripts/python -m pip install playwright            # bin/python on macOS and Linux
build/web-venv/Scripts/python -m playwright install chromium       # about 170 MB, a cache outside the repository
build/web-venv/Scripts/python -m pip install brotli                # optional: package.py then writes .br copies
build/web-venv/Scripts/python tools/web/tests/web_smoke.py --selftest                 # the script itself, on its generated page
python tools/web/package.py build/web-release/bin dist
build/web-venv/Scripts/python tools/web/tests/web_smoke.py --dist dist                # --click 320,240 aims the click, --viewport 800x600 sizes the window
build/web-venv/Scripts/python tools/web/tests/web_smoke.py --dist dist --touch --device-scale-factor 2
build/web-venv/Scripts/python tools/web/tests/web_smoke.py --dist dist --expect-console "Initialized with \d+ worker threads"
python tools/web/package.py build/web-release-single-thread/bin dist-single --single-thread
build/web-venv/Scripts/python tools/web/tests/web_smoke.py --dist dist-single --expect-console "single-thread mode"
# a Debug build prints one error-level line (TaskSystem/CLAUDE.md, "Browser"):
build/web-venv/Scripts/python tools/web/tests/web_smoke.py --dist <debug dist> --allow-console "Blocking on the main thread is very dangerous"
build/web-venv/Scripts/python -m unittest discover tools/web/tests -p test_web_smoke.py   # also runs the RealBrowserTest cases
```

- If `playwright install chromium` cannot download, use an installed browser: `--browser-channel msedge` (or `chrome`) or `--executable-path FILE`; they exit 77 only when it is absent.
- Run `--selftest` first: if it fails, the browser setup or the script is at fault, not the build. Each `--selftest-fault` has to exit 1 (`flat --timeout 5` with `(2)`, `console-error` with `(4)`, `page-error` with `(1)`, `deaf` with `(3)`, `moving` with `(3) cannot judge`). No Playwright: `SKIP` and 77; a browser that is installed but does not start is a `FAIL`.
- **`DEFAULT_CHROMIUM_ARGS`** force SwiftShader: headless Edge would otherwise draw on the machine's GPU, and with the flags every run uses the same software renderer, independent of the driver. Its WebGL notices (`GPU stall due to ReadPixels`) are warnings and do not trip check (4).
- **The console allow-list holds only `favicon.ico`.** The engine's log goes through `printErr` to `console.error` for `Error` and above (`ConsoleSink`; warnings go to stdout), so anything a healthy run writes to stderr fails check (4): a game that logs errors on purpose needs `--allow-console`. The Debug line above is not on the default list on purpose, so a Release build that starts to print it fails.

**What each check proves.** (1) the page was served and no script threw, not that the game started; (2) the renderer, the shaders and the first present work, not that the picture is right; (3) an input reaches the game and changes what is drawn (a tap is judged like a click: SDL turns a touch into a mouse event); (4) no unexpected `console.error`, and with `--expect-console "Initialized with \d+ worker threads"` that the task system's workers started; (5) the backing store is the CSS size times the pixel ratio, so the picture is neither blurred nor half-sized; (6) `manifest.webmanifest` is served as `application/manifest+json`, parses, says `display: fullscreen`, and every icon it lists is served as `image/png` (plain HTTP, no browser; the selftest site has a manifest too). The page is opened with `?fullscreen=0`: the first tap of `--touch` would otherwise request fullscreen and resize the canvas under (3) and (5). The report's `crossOriginIsolated` and `typeof SharedArrayBuffer` show whether the headers reached the page.

**What it does not check:** the first-tap request, the toggle button and the orientation lock (a phone does); that the game is right; sound; a real device's touch and pixel ratio (emulated); a real GPU; the shell's error messages; Firefox and Safari. The window is small (`--viewport`, 640x480) because the shots are decoded in plain Python by `tools/control/tests/png_reader.py` (imported from there, not copied). Check (3) needs a canvas that stands still, with the pointer on the click point, for `--settle` + `CLICK_TIMEOUT_SECONDS` before the click: an idle animation, a blinking cursor or a long fade-in fails with `(3) cannot judge`, on purpose; a change slower than the window can pass for the click's. For a slow start raise `--settle`; a game that animates while idle has no way out yet (no target needs a `--click-region` switch).

## Tests

`python -m unittest discover tools/web/tests` from the engine root (in a game: from `engine/`). `test_serve.py` starts the server on port 0 of 127.0.0.1 in a thread and one test starts `serve.py` as a program with `PORT=0`, the way the Dockerfile's `CMD` does. `test_deploy.py` hands a fake runner to `build_and_deploy.run`: no `railway`, `docker`, `cmake` or emsdk. The real `brotli` is tested only when installed (a stand-in otherwise). `docker build` of the staged folder is a manual check.
