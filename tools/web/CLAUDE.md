# Web Tools Guidelines

## Overview

Python tools for the browser build (entry `web-build` of the todo store; the CMake side is `cmake/BagiWeb.cmake` and the presets `web-release` / `web-debug` (threaded, the default) and `web-release-single-thread` / `web-debug-single-thread`, `.claude/rules/cmake-rules.md`; the page is `web/shell.html`). They are separate processes with the standard library only (Python 3.10+; `brotli` is used when it can be imported). Nothing here names a concrete game apart from `BagiMatch3` as the default. `package.py` has run on the real output of `BagiMatch3` built with emsdk 4.0.23 (sizes below), and `web_smoke.py` has run for real, in headless Chromium and Edge, on its own `--selftest` page and on the threaded and the single-thread release pages of `BagiMatch3` ("The browser smoke"); the unit tests build a fake build output.

| File | Purpose |
|------|---------|
| `package.py` | `python tools/web/package.py <build-dir> <out-dir> [--game NAME]`: the output of a web build (`<game>.html`, `.js`, `.wasm`, `.data`) into a folder to serve. The page becomes `index.html`, the other files keep their names (the page and the script load them by name), every `.html`, `.js`, `.wasm`, `.data` gets `name.gz` (always) and `name.br` (when `import brotli` works), and `manifest.json` has `{game, threads, files: {name: {size, sha256, gzip, brotli}}}`. `threads` is `true` for a threaded build (the default) and `false` with `--single-thread` (`build_and_deploy.py` passes it for a `-single-thread` preset): `serve.py` reads it to decide on the cross-origin isolation headers. A `.br` left by an earlier run is deleted when this run makes none, and so is any page, script, module or package of an earlier run (with its `.gz` / `.br`) that the new manifest does not list: `dist/` holds what the manifest lists, plus files of other kinds, which are left alone. Several pages in the build folder need `--game`. A missing `.js` or `.wasm` is an error, and so is a missing `.data` when the script names it (emcc writes `<game>.data` into the script that loads it; a game without content has neither). The output folder must not be the build folder, hold it or sit in it (`PackageError`, exit 1: the cleaning would delete the page) |
| `serve.py` | The static server the Railway service runs. **One file that imports nothing of this repository** (the Docker image copies only it; a test checks that it imports only the standard library). `python serve.py --root dist [--host H] [--port P] [--cross-origin-isolation | --no-cross-origin-isolation] [--quiet]`; `PORT` from the environment (default 8080), `COOP_COEP=1` / `COOP_COEP=0` are the same as the switches. The decision on the isolation headers (first match wins; the start line prints it and the reason): a switch, then `COOP_COEP`, then the `threads` member of `manifest.json` in the root, then, with no manifest or no `threads` in it, **on** (see "The headers of `serve.py`, and why") |
| `build_and_deploy.py` | The one command: `cmake --preset web-release`, `cmake --build --preset web-release --target <game>`, `package.py`, and with `--deploy` the staging and `railway up <staging folder> --path-as-root --service <name> --detach`. `--single-thread` picks the single-thread page: the preset gets the suffix `-single-thread` (`web-release-single-thread`; a preset named with it already stays) and the build folder is `build/ClangWebSingleThread` instead of `build/ClangWeb` (`--build-dir` wins over both); the `package.py` step then gets `--single-thread` too, so the manifest says `threads: false`. `--dry-run` prints the commands and runs nothing. A program is started by the path that `shutil.which` found (so `railway.cmd` of an npm install works on Windows). Exit 2 with the message `run: python CI/scripts/setup_emsdk.py` when the Emscripten SDK is not installed in `external/emsdk` of the engine (the toolchain file, `emcc.py` and `.emscripten` are checked; also with `--dry-run`), when, with `--deploy`, `railway` is not on PATH, or when a program cannot be started or the staging fails |
| `Dockerfile`, `railway.json` | The image (`python:3.12-slim`, `COPY serve.py` and `COPY dist/`, `CMD ["python", "serve.py", "--root", "dist"]` with no isolation switch because the default does it, user `nobody`) and the Railway settings (builder Dockerfile, health check `/healthz`) |
| `tests/web_smoke.py` | The browser smoke: `python tools/web/tests/web_smoke.py --dist dist [--click X,Y] [--touch] [--device-scale-factor N] [--expect-console REGEX] [--browser-channel NAME \| --executable-path FILE]` serves the folder with `serve.py` on a free port (the isolation decision is `serve.decide_cross_origin_isolation(None, None, root)`: the manifest's `threads`, else on, like the real server), opens it in headless Chromium or Edge through Playwright for Python and checks (1) HTTP 200 and no uncaught page error, (2) the first frame: a screenshot of `canvas#canvas` that is not one flat color (polled up to `--timeout`, 60 s), (3) a click on the canvas (`--click` from its top left corner, else the middle; a tap with `--touch`) changes the picture: the pointer is moved to the click point first (so a hover effect is in every shot and cannot pass for the click's), then the canvas is watched with no click for `--settle` + 5 s (`CLICK_TIMEOUT_SECONDS`), the same time as it is watched after the click, and every shot must equal the first one, else the run FAILS with `(3) cannot judge` (the canvas moves by itself; no click is made); an unreadable shot there is reported as such; the shot after the click is compared with the last one before it, (4) no error-level console message outside the allow-list (`favicon.ico` plus every `--allow-console REGEX`, searched in the text and in the URL) and every `--expect-console REGEX` matched a message of any level within `--timeout`, (5) the canvas backing store (`canvas.width` x `canvas.height`) is the CSS size times `devicePixelRatio` to within a pixel (not for `--selftest`). It prints `window.crossOriginIsolated`, `typeof SharedArrayBuffer`, the pixel ratio, the CSS size and the backing store, and click or tap (the isolation is read as soon as the canvas shows, so a threaded page served without the headers, which never draws, still reports it; the sizes are read after the first frame, and a real build whose page cannot be read then fails (5)). Exit 0 passed, 1 failed (each reason printed; a browser that is installed but does not start is a failure too), 77 skipped (Playwright missing, or the named browser absent: the file of `--executable-path`, the channel of `--browser-channel`, else Playwright's Chromium file), 2 wrong command line. `--selftest` serves a page it generates (a canvas redrawn every animation frame with the same still picture, a moving one after a click; a `manifest.json` of `threads: false`) instead of a build; `--selftest-fault flat\|console-error\|page-error\|deaf\|moving` breaks that page and the run has to exit 1 |
| `tests/` | `unittest` classes (`python -m unittest discover tools/web/tests` from the engine root; pytest also runs them where it is installed): `test_package.py`, `test_serve.py` (also the decision on the isolation headers, and `serve.py` started the way the Dockerfile's `CMD` starts it), `test_deploy.py`, `test_setup_emsdk.py` (`CI/scripts/setup_emsdk.py`: the tag check, the "installed" detection, the commands, `--check`; fake runner, no SDK, no network), `test_cmake_web.py` (+ `check_bagi_web.cmake`, run under `cmake -P`, which also checks the stamp of `be_web_content_inputs`; skipped without cmake), `test_shell.py` (the source of the shell; `check_bagi_web.cmake` checks the copy CMake makes of it for both values of the thread flag), `test_web_smoke.py` (the browser-free parts of the smoke: the command line, the canvas-size and console decisions on given numbers, the tap path against a fake page; its four `RealBrowserTest` cases start a real browser and skip without Playwright or without the browser, run them with the venv's Python), and `web_fixtures.py` (a fake build output made in a temp folder; no binary file is committed) |

## The package, measured

`BagiMatch3`, `-O2`, emsdk 4.0.23, the output of `cmake --build --preset <preset> --target BagiMatch3` as `package.py` makes it in the venv of "The browser smoke" (gzip level 9, brotli quality 11), 2026-11-09, Windows 11, 24 threads. **Threaded** (`web-release`, `build/ClangWeb`, the default: `-pthread` everywhere, the pool of 5 Web Workers) and **single-thread** (`web-release-single-thread`, `build/ClangWebSingleThread`):

| File | Threaded | gzip | brotli | Single-thread | gzip | brotli |
|------|----------|------|--------|---------------|------|--------|
| `BagiMatch3.wasm` | 2,551,295 | 903,621 | 707,986 | 2,518,384 | 898,033 | 704,561 |
| `BagiMatch3.js` | 256,631 | 55,080 | 47,393 | 225,291 | 50,003 | 43,271 |
| `BagiMatch3.data` | 458,790 | 233,935 | 148,722 | 458,790 | 233,935 | 148,722 |
| `index.html` (the shell, minified by emcc) | 5,758 | 2,472 | 2,006 | 5,086 | 2,170 | 1,750 |

A browser that takes brotli downloads about 0.9 MB for the threaded page (`.wasm` 708 KB, `.data` 149 KB, `.js` 47 KB), 1.2 MB with gzip. Threads cost 33 KB of `.wasm` (+1.3 %) and 31 KB of `.js` (the pthread glue). emcc 4.0.23 writes **no** `<game>.worker.js`: a Web Worker starts from `<game>.js` itself (`new Worker(pthreadMainJs, ...)`), so `package.py` copies the same four files for both configurations.

**First frame**, headless Chromium 158 (SwiftShader) against `serve.py` on 127.0.0.1, brotli copies served, a new browser each time: the loading panel is gone and `Game started` is logged 0.21 to 0.23 s after `goto` (three runs each, threaded and single-thread; a localhost number: the download on a real network comes on top). With a throttled network (CDP `Network.emulateNetworkConditions`, 250 KB/s) the panel stayed for about 3 s and then went.

**What is in the package.** The `.data` package holds the engine's `config/` and the font `PT_Sans-Web-Regular.ttf` (443 KB of the 459 KB), the game's `config/` and the web overlay; nothing unneeded is packed, so `be_web_preload_args` needed no cut. **The `.wasm` was cut by 444 KB (2,995,429 to 2,551,105 bytes, -15 %, before the vsync change below) by building SDL_image without TIFF and WebP** (`SDLIMAGE_TIF=OFF`, `SDLIMAGE_WEBP=OFF` on the web, `cmake/BagiEngine.cmake`: the vendored libtiff and libwebp; PNG, JPEG, GIF, QOI and XPM stay, they are SDL_image's own stb-based decoders, and no game ships TIFF or WebP). That also takes libwebp, which compiled with `-pthread` even in the single-thread configuration, out of the build.

Other numbers: a full build of the single-thread page took 120 s, of the Debug single-thread page 105 s (`.wasm` 53,484,522, `.js` 443,276, `.html` 12,674, `.data` the same); the full build (768 steps) takes about 130 s, the link alone (wasm-opt included) about 18 s. emcc prints one link warning, `-pthread + ALLOW_MEMORY_GROWTH may run non-wasm code slowly [-Wpthreads-mem-growth]`; `-Wno-pthreads-mem-growth` is a link option (`cmake/BagiWeb.cmake`, with the reason: it is about the JS glue's views of the heap, not the wasm code). `-Oz` instead of `-O2` (`-DBE_WEB_OPTIMIZATION=-Oz` at configure, measured before the cut above): `.wasm` 2,267,084 (gzip -9: 861,020 against 1,023,551), `.js` 215,245, link 15 s, no measurement of speed. `-O2` stays the default: the difference is 0.7 MB of the download, and a game with a search (Chess) or a heavy frame pays for `-Oz` at run time. `web-debug` (`-g`, `-sASSERTIONS=1`, the asserts on, no editor) builds in about 100 s from scratch: `.wasm` 52,232,743 (DWARF; the threaded page), `.js` 473,152, `.html` 17,197 (not minified), `.data` the same; packaging it with brotli takes minutes (quality 11 on 53 MB), so a Debug run may package with a Python that has no `brotli` (gzip only). It writes the same `build/ClangWeb`: package between the two builds, and delete `build/ClangWeb/lib/*.a` when switching (the objects of the two preset folders are separate, so `ninja` does not see the other's archives).

`node build/ClangWeb/BagiMatch3.js` is a hint and not a test (the same for the threaded page, whose worker pool node creates as `worker_threads`): the module instantiates, the content package is read, `main` runs the engine start-up and stops at SDL video initialisation (`window is not defined`: no browser). The browser smoke is the test.

## The headers of `serve.py`, and why

| Rule | Why |
|------|-----|
| `Content-Type`: `application/wasm`, `application/octet-stream` for `.data`, `text/javascript`, `text/html; charset=utf-8`, `application/json` | The browser compiles a wasm only with `application/wasm` (streaming compile). The table is in the file and not in `mimetypes`: on Windows that reads the registry and has answered `text/plain` for `.js`. The type is that of the file, also when a compressed copy is sent |
| `name.br`, then `name.gz`, by `Accept-Encoding` (q-values read, `q=0` refuses, `*` allows both); `Content-Encoding`, `Vary: Accept-Encoding`, the `Content-Length` of the encoded body | The wasm and the content package are the large downloads. `name.gz` / `name.br` are never served as files of their own (404). A file with no variant gets no `Vary` |
| `index.html` and `manifest.json` (in the root): `Cache-Control: no-cache` plus `ETag` | A new deploy must show at once. The names of the other files are **not hashed** (`BagiMatch3.wasm` in every build), so a long cache or `immutable` would keep an old wasm beside a new page |
| everything else: `public, max-age=3600` plus `ETag`; `If-None-Match` (a list, `*`, weak tags) gives 304 with no body | An hour of reuse, then a cheap revalidation. The tag is `mtime-size-encoding`, so each encoding has its own and a changed file has a new one |
| `GET /healthz` -> 200 `ok` (`no-store`) | The health check of `railway.json` |
| `..`, `%2e%2e`, `%2f`, backslash, NUL, a link out of the folder -> 404 | The path is cut into segments before the file system is touched, and the resolved path must stay below the root |
| `HEAD` works, any other method (`TRACE`, `CONNECT` and unknown ones too) is 405 with `Allow: GET, HEAD` and `Connection: close` (the body is not read, so the connection is not kept) | The `Server` header is `BagiWebServe`, without the Python version |
| `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` on every answer, 304 and errors included. **On by default**, because the default web build is threaded; the single-thread page gets none. Who decides, first match wins: `--cross-origin-isolation` / `--no-cross-origin-isolation`, then `COOP_COEP=1` / `COOP_COEP=0`, then `"threads"` in `manifest.json` of the served folder (`package.py` writes it; `--single-thread` makes it `false`), then, with no manifest (or a manifest without a boolean `threads`), on. The start line says which and why (`cross-origin isolation on: manifest.json says threads: true, a threaded build`) | **The threaded build, the default of the web presets since slice 2, needs both headers:** a pthread wasm uses a `SharedArrayBuffer`, which a page gets only when it is cross-origin isolated, and a server that forgets them gives a page that does not start (the shell then says so, see "The page and the isolation"). **The single-thread build (`ENGINE_SINGLE_THREAD=ON`) needs neither:** no SharedArrayBuffer, no pthreads, so it is served without them, which keeps it working on a host that cannot send them. The headers break a page that embeds another origin without CORP. The image needs no switch (the default does it; `test_serve.py` starts the Dockerfile's `CMD` and checks both headers on `/`, the `.wasm`, a 404 and a 304). An unknown manifest means on rather than off: the cost of a needless header is a page that embeds nothing, the cost of a missing one is a game that does not start |

## The page and the isolation

**Decided (slice 2 of the entry `web-build`): threaded is the default, and the headers follow it.** The web presets build a threaded page, so `serve.py` sends the two headers unless something says the page is single-thread; the signal is `threads` in `manifest.json`, written by `package.py`, and not a guess from the file names. The deployed image therefore needs no switch.

The shell cannot know whether its build is threaded, so `be_web_configure_target` (`cmake/BagiWeb.cmake`) writes a copy of `web/shell.html` into the build folder (`<binary dir>/web/shell.html`, `be_web_generate_shell`: `configure_file(@ONLY)`, the placeholder `@BAGI_WEB_THREADS@`, `1` or `0`) and `--shell-file` points at the copy; `LINK_DEPENDS` has the source and the copy. In the copy of a threaded build the page first tests `window.crossOriginIsolated` and `SharedArrayBuffer`; when either is missing it shows "This page needs cross-origin isolation" with the two headers named, adds the secure-context sentence when `window.isSecureContext` is false (plain `http://` from a host that is not `localhost`), and does **not** start the module (a pthread wasm without `SharedArrayBuffer` fails with a cryptic error). The single-thread copy never shows it. `test_shell.py` reads the source (the placeholder is the only `@name@` pair, the test, the message, that the branch returns before `window.Module` and before the script starts) and `check_bagi_web.cmake` generates both copies and checks the `1` and the `0`. Built and read for real (emsdk 4.0.23, `-O2`): the generated copy says `var threaded = "1" === "1";` (threaded) and `"0" === "1"` (single-thread), and the HTML minifier folds the comparison, so `build/ClangWeb/BagiMatch3.html` keeps the `crossOriginIsolated` test and `build/ClangWebSingleThread/BagiMatch3.html` has none. The page was opened in headless Chromium and Edge: threaded with the headers it starts; threaded **without** them (`serve.py --no-cross-origin-isolation`, one-off script) it shows "This page needs cross-origin isolation" with the two headers named and does not start the module (`crossOriginIsolated` false, `SharedArrayBuffer` undefined, canvas left at 300x150); with WebGL off (`--disable-gpu --disable-3d-apis`) it shows "WebGL is not available" and does not start; with the `.js` or the `.wasm` blocked (Playwright `route.abort()`) it shows "The game could not be loaded" / "The game stopped" (the `onAbort` path); with only the `.data` blocked it shows "The game could not be loaded" through the `unhandledrejection` handler (emcc's package loader is an async function nobody awaits, so before that handler the page stayed on the loading bar with only a console line). A Quit button ends the runtime (`-sEXIT_RUNTIME=1`, `emscripten_cancel_main_loop()` then `Finish()`): the canvas goes blank, `Module.onExit` is called with **no status** (4.0.23, seen in Chromium) and the shell shows "The game has ended".

## Deploying

`build_and_deploy.py` does it all from the root of a project that has the web presets (the engine, or a game that carries it as `engine/`; `--source-dir` names another): needs the Emscripten SDK (no environment variable: `python CI/scripts/setup_emsdk.py` installs it into the submodule `external/emsdk` once per checkout, about 2 GB; the web presets find it by themselves), and for `--deploy` the Railway CLI, logged in (`railway login`) and the project linked (`railway link`), or with `RAILWAY_TOKEN` of the project in the environment; the script reads and writes no secret. Output defaults: the build in `<source>/build/ClangWeb` (the web build writes to `build/<Compiler><Platform>`, the compiler of Emscripten is Clang; the single-thread page, `--single-thread`, has `build/ClangWebSingleThread`, because its libraries are built without `-pthread` and must not meet the threaded ones), the package in `<source>/dist` (`dist/` is in the `.gitignore` of the engine; a game adds it to its own), the staging in `<source>/build/web-deploy`. `railway up` gets the staging folder explicitly (`railway up <folder> --path-as-root`, so it never uploads a linked parent such as the engine root) and runs in it, which holds `Dockerfile`, `railway.json`, `serve.py` and a fresh copy of `dist/`, because the Dockerfile copies those and nothing else.

By hand: build with `cmake --preset web-release` and `cmake --build --preset web-release --target BagiMatch3`, `python tools/web/package.py build/ClangWeb dist`, then open the result locally with `python tools/web/serve.py --root dist` (http://localhost:8080; it sends the isolation headers for the threaded page by itself). The single-thread page: `cmake --preset web-release-single-thread`, build it, `python tools/web/package.py build/ClangWebSingleThread dist-single --single-thread` and `serve.py --root dist-single` (no headers). A threaded page opened from a host that is not `localhost` over plain `http://` is not a secure context, so it is not cross-origin isolated whatever the server sends: use `localhost` or https. Create the service once in Railway: a project, an empty service (`railway add --service bagi-web`, or the dashboard), the domain under the service's Settings -> Networking; then `railway link` (once, choosing the project and the service) and `railway up <folder> --path-as-root --service bagi-web --detach` for a folder that holds the four files above, or let the script do it. How `link` and a path interact is not yet checked against a real Railway CLI (slice 3). Nothing is deployed by the tests or by the loop (the Railway service, the domain and the CI job are slice 3 of the entry).

**The `.data` package and relinks.** The content (`config/`, `assets/` of the engine, the game and the web overlay) is packed into `<game>.data` at **link time**. `be_web_configure_target` lists every file of those folders in `LINK_DEPENDS` (globbed with `CONFIGURE_DEPENDS`) and, per folder, a stamp file `web-content/<target>_bagi_<layer>_<folder>.txt` in the build folder that holds the sorted list of the files (`be_web_content_inputs`; written with `file(CONFIGURE)`, so only when the list changes). An edit relinks because the file is newer than the package; an added or a deleted file relinks because the re-glob changes the stamp (a deleted file alone would leave no trace in the inputs, and the `--preload-file` command line does not change). The link is the slow step (wasm-opt), which is the price of editing content. `CONFIGURE_DEPENDS` makes Ninja re-run the globs at the start of **every** `cmake --build`, and the link edge gets one input per content file; that is cheap at the size of today's `assets/` and grows with a large one.

## The browser smoke

Playwright is not a dependency of the repository and the tests never install it. The recipe used on this machine (Windows 11) keeps it in a virtual environment inside the git-ignored `build/`, so nothing is installed globally and the system Python stays without Playwright (the browser cases of `test_web_smoke.py` then skip):

```bash
python -m venv build/web-venv
build/web-venv/Scripts/python -m pip install playwright            # bin/python on macOS and Linux
build/web-venv/Scripts/python -m playwright install chromium       # about 170 MB, a cache under %LOCALAPPDATA%/ms-playwright; worked here
build/web-venv/Scripts/python -m pip install brotli                # optional: package.py then writes .br copies and the sizes table has the brotli column
build/web-venv/Scripts/python tools/web/tests/web_smoke.py --selftest                 # the script itself, on its generated page
python tools/web/package.py build/ClangWeb dist
build/web-venv/Scripts/python tools/web/tests/web_smoke.py --dist dist                # the build; --click 320,240 aims the click, --viewport 800x600 sizes the window
build/web-venv/Scripts/python tools/web/tests/web_smoke.py --dist dist --touch        # the click is a tap
build/web-venv/Scripts/python tools/web/tests/web_smoke.py --dist dist --device-scale-factor 2   # pixel ratio 2: checks the backing store
build/web-venv/Scripts/python tools/web/tests/web_smoke.py --dist dist --expect-console "Initialized with \d+ worker threads"
python tools/web/package.py build/ClangWebSingleThread dist-single --single-thread   # the single-thread page: no headers; its console says "single-thread mode"
build/web-venv/Scripts/python tools/web/tests/web_smoke.py --dist dist-single --expect-console "single-thread mode"
# a Debug build (web-debug) prints one error-level line by design, from the start-up wait of the main thread ("Blocking on the main thread is very dangerous", ASSERTIONS only):
build/web-venv/Scripts/python tools/web/tests/web_smoke.py --dist <debug dist> --allow-console "Blocking on the main thread is very dangerous"
build/web-venv/Scripts/python tools/web/tests/web_smoke.py --selftest --browser-channel msedge   # the installed Microsoft Edge, no download
build/web-venv/Scripts/python -m unittest discover tools/web/tests -p test_web_smoke.py   # also runs the RealBrowserTest cases instead of skipping them
```

If `playwright install chromium` cannot download (a proxy, no network), use an installed browser: `--browser-channel msedge` (or `chrome`) drives it through Playwright with no download, `--executable-path FILE` any Chromium-based executable. Both exit 77 only when the named browser is absent. Measured here (playwright 1.65): Chromium 158.0.8127.18 from Playwright and Edge 157.0.4341.42 both pass `--selftest`, `--touch` with `--device-scale-factor 2`, `--expect-console` and every `--selftest-fault`.

Run `--selftest` first: if it fails, the browser setup or the script is at fault, not the build. The same for the faults (`--selftest-fault flat --timeout 5` has to exit 1 with `(2)`, `console-error` with `(4)`, `page-error` with `(1)`, `deaf` with `(3)`, `moving` with `(3) cannot judge`; all five did, in Chromium and Edge). Without Playwright every run prints `SKIP: playwright is not installed` and exits 77; with Playwright but no Chromium file, `SKIP: the browser is not installed`; a Chromium that is there and does not start (a crash, a bad `--chromium-arg`, a sandbox problem) is `FAIL`.

**The whole thing, end to end, as run for the entry (Windows 11, 2026-11-09).** `python CI/scripts/setup_emsdk.py` (once), `cmake --preset web-release`, `cmake --build --preset web-release --target BagiMatch3`, `python tools/web/package.py build/ClangWeb dist`, then the smoke commands above; `python tools/web/serve.py --root dist` serves the same folder for a person (http://localhost:8080). Results, headless Chromium 158 from Playwright (and Edge 157 with `--browser-channel msedge`): the threaded release page passes `--expect-console "Initialized with \d+ worker threads"` (the log has `[ThreadPool] Created with 4 threads`, `[TaskManager] Initialized with 4 worker threads`, the config load of `ConfigManager::Initialize` finishes, `crossOriginIsolated=true`, `typeof SharedArrayBuffer=function`), `--device-scale-factor 2` (backing store 1280x960 for a CSS size of 640x480) and `--touch`, in both browsers; the single-thread page passes with `crossOriginIsolated=false` and the console line `[TaskManager] Initialized in single-thread mode (inline pool, no worker threads)`; the Debug threaded page passes with the one `--allow-console` above. The game itself was looked at in screenshots: the menu, the board after Play, a tile selected by a click and by a tap exactly once (a touch does not become two clicks), the same at a pixel ratio of 2 in a 800x600 window (crisp, the selected tile under the tap), and after `page.set_viewport_size` to 900x500 the canvas became 900x500 CSS pixels with a 1800x1000 backing store. A tile responds to a tap at the right place at ratio 2, so input and pixel density agree.

**What the first real run found and fixed** (each had passed every text test): (1) the log line `[CRTDebugHook] Skipped (non-Windows platform)` went to stderr, which the shell sends to `console.error`: the smoke failed on it, the line is no longer printed off Windows; (2) the loop ran on `setTimeout(0)`, not on `requestAnimationFrame` (counted in the page: 0 rAF callbacks and 633 `setTimeout(0)` in 3 s, now 181 rAF and 0): SDL's renderer without vsync asks for swap interval 0 at the first frame and SDL's Emscripten driver makes that a timer main loop, so `SDLRendererBackend` now turns vsync on in a browser; (3) the progress of the `.data` download counted decoded bytes against the compressed `Content-Length`, so the bar showed 0.4 / 0.1 MB and sat at full: once the count passes the total the shell shows the bytes alone and a bar that only moves back and forth; (4) a `.data` that did not download left the page on the loading bar with no message (the failure is an unhandled promise rejection): the shell has an `unhandledrejection` handler now; (5) after Quit the page was a blank canvas: the shell shows "The game has ended" from `Module.onExit`; (6) TIFF and WebP were compiled into SDL_image for nothing (444 KB, "The package, measured"). Not a bug, noted: the console has four `GL Driver Message (OpenGL, Performance, GL_CLOSE_PATH_NV, High): GPU stall due to ReadPixels` warnings in Chromium, which headless Chromium with SwiftShader prints for any WebGL page (a page that only clears a canvas every frame gets the same four lines), not the game; they are warnings and do not trip check (4).

**The browser flags (`DEFAULT_CHROMIUM_ARGS`: `--use-angle=swiftshader --enable-unsafe-swiftshader`), measured:** a headless Chromium 158 on this machine gives WebGL 2 from SwiftShader with no flag at all, but a headless Edge 157 gives it from the machine's GPU (Direct3D 11) unless the flags are there. With them both run the same software renderer, which makes a run independent of the driver (a real GPU is the owner's check, "Left for the owner" of the entry). The console allow-list holds only `favicon.ico`: nothing else was needed for the selftest page or for the Release pages of `BagiMatch3` (no error-level line in 26 messages), and SwiftShader's WebGL notices are warnings, not errors. A Debug page needs the one `--allow-console` above, and it is not on the default list on purpose, so a Release build that starts to print it fails.

**What each check proves, and what it does not.** (1) the page was served and no script threw; not that the game started. (2) something other than one flat color was drawn into the canvas, so the renderer, the shaders and the first present work; not that it is the right picture. (3) an input reaches the game and changes what is drawn; not that the right thing happened, and a tap is judged the same way as a click (SDL turns a touch into a mouse event). (4) no `console.error` outside the allow-list, and the messages the run expects came: with `--expect-console "Initialized with \d+ worker threads"` it proves the task system's workers started (threaded page). (5) the backing store follows the CSS size times the pixel ratio, so the picture is neither blurred nor half-sized; not that the UI scale is right. The page report (`crossOriginIsolated`, `typeof SharedArrayBuffer`) shows whether the headers reached the page.

What it does **not** check: that the game is right (only that something is drawn and that an input changes it); sound; a real device's touch and pixel ratio (the browser emulates a touch screen and a scale factor; the window is `--viewport`, 640x480, small because the screenshots are decoded in plain Python by `tools/control/tests/png_reader.py`, which the script imports from there and does not copy); a real GPU (SwiftShader draws); the messages of the shell for a missing WebGL, a page without the headers and a download that fails (looked at by one-off scripts, listed in "The page and the isolation", not part of the smoke); Firefox and Safari. Check (3) needs a canvas that stands still, with the pointer on the click point, for `--settle` + 5 s before the click (6 s by default): every shot in that window must equal the first one, so a game with an idle animation, a cursor that blinks, a label that changes every second or a fade-in that outlasts that time fails with `(3) cannot judge` (the idle shots are about 0.5 s apart, so a blink short enough to fall between two shots is not seen). That is a FAIL and not a pass, because a pass would claim a click that was never judged. A change slower than the window is not seen and can pass for the click's. For a slow start raise `--settle`; for a game that animates while idle there is no way out yet: the way is a switch, `--click-region X,Y,W,H` (compare only a region the animation does not touch) or `--no-click-check` (report (3) as skipped), which is not built because no target animates while idle (the entry's "Left for the owner"). The engine writes its log through `printErr` to `console.error` (`web/shell.html`; `ConsoleSink` sends only `Error` and above to stderr, warnings go to stdout and do not trip check 4), so a game that logs errors on stderr in a healthy run needs `--allow-console` entries.

## Tests

`python -m unittest discover tools/web/tests` from the engine root (in a game checkout: from `engine/`). `test_serve.py` starts the server on port 0 of 127.0.0.1 in a thread (`serve_forever(poll_interval=0.01)`, so a test does not wait half a second at its end) and one test starts `serve.py` as a program with `PORT=0`. `test_deploy.py` hands a fake runner to `build_and_deploy.run`; neither `railway`, `docker`, `cmake` nor an emsdk is needed. The real `brotli` module is tested only when installed; the other tests use a stand-in whose `.br` is a marker plus the input. If `docker` is at hand, `docker build` of the staged folder is a one-time manual check (not a test).
