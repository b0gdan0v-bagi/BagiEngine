# Web Tools Guidelines

## Overview

Python tools for the browser build (entry `web-build` of the todo store; the CMake side is `cmake/BagiWeb.cmake` and the presets `web-release` / `web-debug` (threaded, the default) and `web-release-single-thread` / `web-debug-single-thread`, `.claude/rules/cmake-rules.md`; the page is `web/shell.html`). They are separate processes with the standard library only (Python 3.10+; `brotli` is used when it can be imported). Nothing here names a concrete game apart from `BagiMatch3` as the default. `package.py` has run on the real output of `BagiMatch3` built with emsdk 4.0.23 (sizes below); `web_smoke.py` has not run in a browser yet (the tests build a fake build output).

| File | Purpose |
|------|---------|
| `package.py` | `python tools/web/package.py <build-dir> <out-dir> [--game NAME]`: the output of a web build (`<game>.html`, `.js`, `.wasm`, `.data`) into a folder to serve. The page becomes `index.html`, the other files keep their names (the page and the script load them by name), every `.html`, `.js`, `.wasm`, `.data` gets `name.gz` (always) and `name.br` (when `import brotli` works), and `manifest.json` has `{game, files: {name: {size, sha256, gzip, brotli}}}`. A `.br` left by an earlier run is deleted when this run makes none, and so is any page, script, module or package of an earlier run (with its `.gz` / `.br`) that the new manifest does not list: `dist/` holds what the manifest lists, plus files of other kinds, which are left alone. Several pages in the build folder need `--game`. A missing `.js` or `.wasm` is an error, and so is a missing `.data` when the script names it (emcc writes `<game>.data` into the script that loads it; a game without content has neither). The output folder must not be the build folder, hold it or sit in it (`PackageError`, exit 1: the cleaning would delete the page) |
| `serve.py` | The static server the Railway service runs. **One file that imports nothing of this repository** (the Docker image copies only it; a test checks that it imports only the standard library). `python serve.py --root dist [--host H] [--port P] [--cross-origin-isolation] [--quiet]`; `PORT` from the environment (default 8080), `COOP_COEP=1` is the same as the switch |
| `build_and_deploy.py` | The one command: `cmake --preset web-release`, `cmake --build --preset web-release --target <game>`, `package.py`, and with `--deploy` the staging and `railway up <staging folder> --path-as-root --service <name> --detach`. `--single-thread` picks the single-thread page: the preset gets the suffix `-single-thread` (`web-release-single-thread`; a preset named with it already stays) and the build folder is `build/ClangWebSingleThread` instead of `build/ClangWeb` (`--build-dir` wins over both). `--dry-run` prints the commands and runs nothing. A program is started by the path that `shutil.which` found (so `railway.cmd` of an npm install works on Windows). Exit 2 with the message `run: python CI/scripts/setup_emsdk.py` when the Emscripten SDK is not installed in `external/emsdk` of the engine (the toolchain file, `emcc.py` and `.emscripten` are checked; also with `--dry-run`), when, with `--deploy`, `railway` is not on PATH, or when a program cannot be started or the staging fails |
| `Dockerfile`, `railway.json` | The image (`python:3.12-slim`, `COPY serve.py` and `COPY dist/`, `CMD ["python", "serve.py", "--root", "dist"]`, user `nobody`) and the Railway settings (builder Dockerfile, health check `/healthz`) |
| `tests/web_smoke.py` | The browser smoke: `python tools/web/tests/web_smoke.py --dist dist [--click X,Y]` serves the folder with `serve.py` on a free port, opens it in headless Chromium through Playwright for Python and checks (1) HTTP 200 and no uncaught page error, (2) the first frame: a screenshot of `canvas#canvas` that is not one flat color (polled up to `--timeout`, 60 s), (3) a click on the canvas (`--click` from its top left corner, else the middle) changes the picture: the pointer is moved to the click point first (so a hover effect is in every shot and cannot pass for the click's), then the canvas is watched with no click for `--settle` + 5 s (`CLICK_TIMEOUT_SECONDS`), the same time as it is watched after the click, and every shot must equal the first one, else the run FAILS with `(3) cannot judge` (the canvas moves by itself; no click is made); an unreadable shot there is reported as such; the shot after the click is compared with the last one before it, (4) no error-level console message outside the allow-list (`favicon.ico` plus every `--allow-console REGEX`, searched in the text and in the URL). Exit 0 passed, 1 failed (each reason printed; a Chromium that is installed but does not start is a failure too), 77 skipped (Playwright missing, or the file `chromium.executable_path` names missing), 2 wrong command line. `--selftest` serves a page it generates (a canvas redrawn every animation frame with the same still picture, a moving one after a click) instead of a build; `--selftest-fault flat\|console-error\|page-error\|deaf\|moving` breaks that page and the run has to exit 1 |
| `tests/` | `unittest` classes (`python -m unittest discover tools/web/tests` from the engine root; pytest also runs them where it is installed): `test_package.py`, `test_serve.py`, `test_deploy.py`, `test_setup_emsdk.py` (`CI/scripts/setup_emsdk.py`: the tag check, the "installed" detection, the commands, `--check`; fake runner, no SDK, no network), `test_cmake_web.py` (+ `check_bagi_web.cmake`, run under `cmake -P`, which also checks the stamp of `be_web_content_inputs`; skipped without cmake), `test_shell.py`, `test_web_smoke.py` (the browser-free parts of the smoke; its two cases that start Chromium skip without Playwright), and `web_fixtures.py` (a fake build output made in a temp folder; no binary file is committed) |

## The package, measured

The sizes below are of the single-thread page (`web-release-single-thread`, `build/ClangWebSingleThread`); the threaded page (`web-release`, `build/ClangWeb`, the default) is listed after the table.

`BagiMatch3`, `web-release-single-thread` (`-O2`, emsdk 4.0.23), the output of `cmake --build --preset web-release-single-thread --target BagiMatch3` as `package.py` makes it (gzip level 9, brotli quality 11), 2026-11-09, Windows 11, 24 threads:

| File | Size | gzip | brotli |
|------|------|------|--------|
| `BagiMatch3.wasm` | 2,961,123 | 1,022,256 | 803,459 |
| `BagiMatch3.js` | 225,556 | 50,096 | 43,363 |
| `BagiMatch3.data` | 458,790 | 233,935 | 148,722 |
| `index.html` (the shell, minified by emcc) | 4,578 | 2,026 | 1,622 |

**Threaded** (`web-release`, `-pthread` everywhere, the pool of 5 Web Workers; 2026-11-09, same machine): `.wasm` 2,995,429 (gzip 1,027,541, brotli 806,545; +34 KB, +1.2 %), `.js` 256,913 (gzip 55,177, brotli 47,454; +31 KB: the pthread glue), `.data` and `index.html` the same as above. emcc 4.0.23 writes **no** `<game>.worker.js`: a Web Worker starts from `<game>.js` itself (`new Worker(pthreadMainJs, ...)`), so `package.py` copies the same four files for both configurations. A full build of the single-thread page took 120 s, of the Debug single-thread page 105 s (`.wasm` 53,484,522, `.js` 443,276, `.html` 12,674, `.data` the same). emcc prints one link warning, `-pthread + ALLOW_MEMORY_GROWTH may run non-wasm code slowly [-Wpthreads-mem-growth]`; `-Wno-pthreads-mem-growth` is a link option (`cmake/BagiWeb.cmake`, with the reason: it is about the JS glue's views of the heap, not the wasm code).

The full build (768 steps) takes about 130 s, the link alone (wasm-opt included) about 18 s. The `.data` package holds the engine's `config/` and the font `PT_Sans-Web-Regular.ttf` (443 KB of the 459 KB), the game's `config/` and the web overlay; nothing unneeded is packed. `-Oz` instead of `-O2` (`-DBE_WEB_OPTIMIZATION=-Oz` at configure): `.wasm` 2,267,084 (gzip -9: 861,020 against 1,023,551), `.js` 215,245, link 15 s, no measurement of speed. `-O2` stays the default: the difference is 0.7 MB of the download, and a game with a search (Chess) or a heavy frame pays for `-Oz` at run time. `web-debug` (`-g`, `-sASSERTIONS=1`, the asserts on, no editor) builds in about 100 s from scratch: `.wasm` 53,483,551 (DWARF; gzip 15,403,358, brotli 9,251,323), `.js` 443,240, `.html` 12,590 (not minified), `.data` the same; packaging it takes minutes because of brotli at quality 11 on 53 MB. It writes the same `build/ClangWeb`: package between the two builds, and delete `build/ClangWeb/lib/*.a` when switching (the objects of the two preset folders are separate, so `ninja` does not see the other's archives).

`node build/ClangWeb/BagiMatch3.js` is a hint and not a test (the same for the threaded page, whose worker pool node creates as `worker_threads`): the module instantiates, the content package is read, `main` runs the engine start-up and stops at SDL video initialisation (`window is not defined`: no browser).

## The headers of `serve.py`, and why

| Rule | Why |
|------|-----|
| `Content-Type`: `application/wasm`, `application/octet-stream` for `.data`, `text/javascript`, `text/html; charset=utf-8`, `application/json` | The browser compiles a wasm only with `application/wasm` (streaming compile). The table is in the file and not in `mimetypes`: on Windows that reads the registry and has answered `text/plain` for `.js`. The type is that of the file, also when a compressed copy is sent |
| `name.br`, then `name.gz`, by `Accept-Encoding` (q-values read, `q=0` refuses, `*` allows both); `Content-Encoding`, `Vary: Accept-Encoding`, the `Content-Length` of the encoded body | The wasm and the content package are the large downloads. `name.gz` / `name.br` are never served as files of their own (404). A file with no variant gets no `Vary` |
| `index.html` and `manifest.json` (in the root): `Cache-Control: no-cache` plus `ETag` | A new deploy must show at once. The names of the other files are **not hashed** (`BagiMatch3.wasm` in every build), so a long cache or `immutable` would keep an old wasm beside a new page |
| everything else: `public, max-age=3600` plus `ETag`; `If-None-Match` (a list, `*`, weak tags) gives 304 with no body | An hour of reuse, then a cheap revalidation. The tag is `mtime-size-encoding`, so each encoding has its own and a changed file has a new one |
| `GET /healthz` -> 200 `ok` (`no-store`) | The health check of `railway.json` |
| `..`, `%2e%2e`, `%2f`, backslash, NUL, a link out of the folder -> 404 | The path is cut into segments before the file system is touched, and the resolved path must stay below the root |
| `HEAD` works, any other method (`TRACE`, `CONNECT` and unknown ones too) is 405 with `Allow: GET, HEAD` and `Connection: close` (the body is not read, so the connection is not kept) | The `Server` header is `BagiWebServe`, without the Python version |
| `--cross-origin-isolation` (or `COOP_COEP=1`): `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Embedder-Policy: require-corp` on every answer, 304 and errors included | Off by default (WP 5 of slice 2 makes a threaded build turn them on by itself). **The single-thread build (`ENGINE_SINGLE_THREAD=ON`) needs neither:** no SharedArrayBuffer, no pthreads. **The threaded build, the default of the web presets since slice 2, needs both:** a pthread wasm uses a `SharedArrayBuffer`, which a page gets only when it is cross-origin isolated. The headers break a page that embeds another origin without CORP |

## Deploying

`build_and_deploy.py` does it all from the root of a project that has the web presets (the engine, or a game that carries it as `engine/`; `--source-dir` names another): needs the Emscripten SDK (no environment variable: `python CI/scripts/setup_emsdk.py` installs it into the submodule `external/emsdk` once per checkout, about 2 GB; the web presets find it by themselves), and for `--deploy` the Railway CLI, logged in (`railway login`) and the project linked (`railway link`), or with `RAILWAY_TOKEN` of the project in the environment; the script reads and writes no secret. Output defaults: the build in `<source>/build/ClangWeb` (the web build writes to `build/<Compiler><Platform>`, the compiler of Emscripten is Clang; the single-thread page, `--single-thread`, has `build/ClangWebSingleThread`, because its libraries are built without `-pthread` and must not meet the threaded ones), the package in `<source>/dist` (`dist/` is in the `.gitignore` of the engine; a game adds it to its own), the staging in `<source>/build/web-deploy`. `railway up` gets the staging folder explicitly (`railway up <folder> --path-as-root`, so it never uploads a linked parent such as the engine root) and runs in it, which holds `Dockerfile`, `railway.json`, `serve.py` and a fresh copy of `dist/`, because the Dockerfile copies those and nothing else.

By hand: build with `cmake --preset web-release` and `cmake --build --preset web-release --target BagiMatch3`, `python tools/web/package.py build/ClangWeb dist`, then open the result locally with `python tools/web/serve.py --root dist` (http://localhost:8080). Create the service once in Railway: a project, an empty service (`railway add --service bagi-web`, or the dashboard), the domain under the service's Settings -> Networking; then `railway link` (once, choosing the project and the service) and `railway up <folder> --path-as-root --service bagi-web --detach` for a folder that holds the four files above, or let the script do it. How `link` and a path interact is not yet checked against a real Railway CLI (slice 3). Nothing is deployed by the tests or by the loop (the Railway service, the domain and the CI job are slice 3 of the entry).

**The `.data` package and relinks.** The content (`config/`, `assets/` of the engine, the game and the web overlay) is packed into `<game>.data` at **link time**. `be_web_configure_target` lists every file of those folders in `LINK_DEPENDS` (globbed with `CONFIGURE_DEPENDS`) and, per folder, a stamp file `web-content/<target>_bagi_<layer>_<folder>.txt` in the build folder that holds the sorted list of the files (`be_web_content_inputs`; written with `file(CONFIGURE)`, so only when the list changes). An edit relinks because the file is newer than the package; an added or a deleted file relinks because the re-glob changes the stamp (a deleted file alone would leave no trace in the inputs, and the `--preload-file` command line does not change). The link is the slow step (wasm-opt), which is the price of editing content. `CONFIGURE_DEPENDS` makes Ninja re-run the globs at the start of **every** `cmake --build`, and the link edge gets one input per content file; that is cheap at the size of today's `assets/` and grows with a large one.

## The browser smoke

Playwright is not a dependency of the repository and the tests never install it. To run the smoke on a real build:

```bash
pip install playwright
playwright install chromium
python tools/web/tests/web_smoke.py --selftest                 # the script itself, on its generated page
python tools/web/package.py build/ClangWeb dist
python tools/web/tests/web_smoke.py --dist dist                # the build; --click 320,240 aims the click, --viewport 800x600 sizes the window
```

Run `--selftest` first: if it fails, the browser setup or the script is at fault, not the build. The same for the faults (`--selftest-fault flat --timeout 5` has to exit 1 with `(2)`, `console-error` with `(4)`, `page-error` with `(1)`, `deaf` with `(3)`, `moving` with `(3) cannot judge`). Without Playwright every run prints `SKIP: playwright is not installed` and exits 77; with Playwright but no Chromium file, `SKIP: the browser is not installed`; a Chromium that is there and does not start (a crash, a bad `--chromium-arg`, a sandbox problem) is `FAIL`.

What it does **not** check: that the game is right (only that something is drawn and that a click changes it); sound; touch (the click is a mouse click); the WebGL-missing message of the shell; a real device's pixel ratio (the window is `--viewport`, 640x480, small because the screenshots are decoded in plain Python by `tools/control/tests/png_reader.py`, which the script imports from there and does not copy). Check (3) needs a canvas that stands still, with the pointer on the click point, for `--settle` + 5 s before the click (6 s by default): every shot in that window must equal the first one, so a game with an idle animation, a cursor that blinks, a label that changes every second or a fade-in that outlasts that time fails with `(3) cannot judge` (almost always: the idle shots are about 0.5 s apart, so a blink short enough to fall between two shots is not seen). That is a FAIL and not a pass, because a pass would claim a click that was never judged. A change slower than the window is not seen and can pass for the click's. For a slow start raise `--settle`; for a game that animates while idle there is no way out yet: the way is a switch, `--click-region X,Y,W,H` (compare only a region the animation does not touch) or `--no-click-check` (report (3) as skipped), which is not built because no target animates while idle (the entry's "Left for the owner"). The engine writes its log through `printErr` to `console.error` (`web/shell.html`; `ConsoleSink` sends only `Error` and above to stderr, warnings go to stdout and do not trip check 4), so a game that logs errors on stderr in a healthy run needs `--allow-console` entries; the flags in `DEFAULT_CHROMIUM_ARGS` (SwiftShader for WebGL in a headless Chromium) are a first guess. None of this has run against a real build or in a real browser: it is the first thing slice 2 does (the entry's "Left for the owner").

## Tests

`python -m unittest discover tools/web/tests` from the engine root (in a game checkout: from `engine/`). `test_serve.py` starts the server on port 0 of 127.0.0.1 in a thread (`serve_forever(poll_interval=0.01)`, so a test does not wait half a second at its end) and one test starts `serve.py` as a program with `PORT=0`. `test_deploy.py` hands a fake runner to `build_and_deploy.run`; neither `railway`, `docker`, `cmake` nor an emsdk is needed. The real `brotli` module is tested only when installed; the other tests use a stand-in whose `.br` is a marker plus the input. If `docker` is at hand, `docker build` of the staged folder is a one-time manual check (not a test).
