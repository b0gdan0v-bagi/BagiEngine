# Config and data code reads XmlNode by hand where the factory and reflection path already fits

**Where:** `src/Modules/BECore/Application/` (`ApplicationFabric.cpp`, `IApplicationFabric.h`, `RunMode.cpp`), `BECore/Control/ControlSettings.cpp`, `src/Modules/SDL/src/CoreSDL/` (`SDL3ApplicationFabric.cpp`), `src/Modules/Games/src/Games/GameManager.cpp`, `BECore/Resource/TextureLibrary.cpp`, `src/Widgets/SceneEditor/SceneEditorWidget.cpp`, `src/Widgets/ConfigEditor/`, `games/Match3/src/Match3/Match3GameControl.cpp`, `src/Chess/ChessGameControl.cpp` of BagiEngine-Chess.

**What is wrong** (found by reading the code, not by running anything): the engine is built on one split. A type name picks the class through `AbstractFactory`, and the reflected fields are filled through `IDeserializer`, so the model does not know the file format (`XmlDeserializer` and `BinaryDeserializer` already exist). Scene components, widgets, runtime tests, games, resource loaders, log sinks, assert handlers and the managers built with `MakeFromConfig` follow it (a caller gets an `IDeserializer` from `ConfigManager::CreateDeserializer` / `OpenDeserializer`, and a factory list is a reflected holder filled by `MakeFromConfig`, see `BECore/Config/CLAUDE.md`). The places below read or write the format themselves instead (the numbers are kept):

1. `ApplicationConfig` has four hand-written readers, each pulling attributes by name: `ApplicationFabric::Create` (`type`), `SDL3ApplicationFabric::Create` (`path`, `renderer`), `ReadRunMode` (`mode`) and `ResolveControlSettings` (`control`, `controlPort`, `manualClock`, `headless`). `IApplicationFabric::Create` takes an `XmlNode`, so a factory-base interface knows the format. `ControlSettings` also has a second hand parser for the command-line flags, a merge rule (file first, flags override) and its own range checks.
2. `GameManager::Initialize` reads `defaultGame/@name` of `GamesConfig` through `XmlNode`.
3. `SpriteEntry` is not reflected: `TextureLibrary::Initialize` walks `<sprites>` with `XmlNode` and `Save` rebuilds the tree with raw pugixml.
6. A source that is not a file has no path to a reflected type. The start-up flags, the parameters of the control API and the planned CSS declarations of the UI plan (the UI plan in the local plan store, task 4.2) all mean "values for named fields of a typed object", and each is parsed and range-checked on its own. `Match3GameControl` and `ChessGameControl` build the state and the actions as `Json` objects by hand and read the parameters of `PerformAction`, `Reset` and `SetState` member by member through `Control/Json.h`. There is no `ISerializer` / `IDeserializer` over JSON or over a name → value map.
7. `BuildNodeXml` (`src/Widgets/SceneEditor/SceneConfigWriter.cpp`, the scene editor's save path) writes the `name` / `layer` of a `<node>` and the component list by hand, so a new reflected field of `SceneNode` is dropped on save. The scene part is done: the attributes of a `<scene>` come from `Scene::Serialize`. Writing the nodes through `SceneNode::Serialize` as well would add `enabled="true"`, `type="SceneNode"` and `layer="0"` to every saved node (and `enabled="true"` to every component) unless the factory-vector writer learns to leave them out.
8. `ConfigEditorWidget` edits XML attributes (`StagedChanges::ApplyTo` on the pugixml node) and keeps its field hints under XML paths (`ConfigFieldSchema`, `"sink/@type"`), guessing the type from the text (`"true"` is a bool, a number that parses is an int). The scene inspector already edits through `IPropertyVisitor` with the real types. Its sink `type` dropdown once offered names the logger factory could not resolve; it now lists what `AbstractFactory<ILogSink>` registers (`ConfigFieldSchema::RegisterFactoryTypes`), but every other hint is still a hand-written XML path.

**A fix has to cover** (goals, not a design):

- the application, game and control settings as reflected structs, with the file and the command line as two sources of the same struct (items 1 and 2);
- `TextureLibrary` entries reflected and saved through `ISerializer` (item 3);
- a source that is not a file: a name → value map and a JSON-backed pair, shared by the start-up flags, the control API and the UI plan (item 6); the JSON side keeps the rules of `Control/Json.h` (nlohmann aborts on a bad access in this build);
- both editors writing through the reflection (items 7 and 8); the two existing entries stay the place for their bugs.
