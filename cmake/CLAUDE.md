# cmake/ — the engine setup and the build options

`BagiEngine.cmake` is the engine setup and the `be_*` functions games build on (`.claude/rules/cmake-rules.md`); `BagiPlatformOptions.cmake` the platform options; `BagiWeb.cmake` the Emscripten side. A change to any `*.cmake` needs a configure.

## Presets

| OS | Presets |
|----|---------|
| macOS | `macos-debug`, `macos-release` (Clang + Ninja); `macos-release-editor`; `macos-profile` (RelWithDebInfo with the profiler and allocation tracking, no editor: `src/Modules/BECore/Profiler/HowToProfile.md`), `macos-profile-tracy` (the same with the Tracy backend), `macos-profile-editor` (the same with the editor, for the ImGui Profiler panel); `macos-rmlui-debug` / `-release` (`ENGINE_UI_RMLUI=ON`); `macos-asan` (Debug, Apple clang, ASan + UBSan on all code: "Sanitizers and fuzzing" below), `macos-fuzz` (Homebrew LLVM, ASan + UBSan, libFuzzer executables), `macos-fuzz-shipped` (the same in Release with asserts and expects OFF) |
| Windows | `windows-clang-{debug,release}` (default; configure and build through `python CI/scripts/vs_env.py cmake ...`), `windows-clang-asan` (Debug build type with the release dynamic CRT, ASan + UBSan, through `vs_env.py` like the others; not yet run on Windows), `windows-msvc-{debug,release}`, `windows-msvc-release-editor`, `windows-vs2022-*`, `windows-vs2022-clangcl-*`. The MSVC builds are fallbacks (their PDBs break parallel builds now and then: `LNK1103`, `C1090`) |
| Linux | `linux-server-release` (Clang + Ninja, Release, only for the room server: no Vulkan, no tests, no editor, static SDL built with `SDL_UNIX_CONSOLE_BUILD` since the server opens no window, `no-module-scan`, `CMAKE_POSITION_INDEPENDENT_CODE=OFF` because SDL_image's `option()` would turn it ON and the executables then get `-fPIE` against a PCH made for libraries: "is pie differs in PCH file"). It builds `BagiRoomServer` in the Docker image of `tools/rooms/Dockerfile` (README.md, "Hosting the room server"); no other target, game or test is built or checked on Linux |
| Web | `web-release`, `web-debug` (threaded, the default: the task system's workers are Web Workers, the page needs cross-origin isolation, which `tools/web/serve.py` and the Docker image send), `web-release-single-thread`, `web-debug-single-thread` (needs nothing). Always listed: they find the SDK in the submodule `external/emsdk` (pinned tag, about 2 GB), installed once per checkout by `python CI/scripts/setup_emsdk.py` (in a game `engine/CI/...`; `--check`); without it configure stops with "could not find toolchain file". Build only, no editor (also in Debug), no tests. Output `build/<preset>/bin` (the page `<Game>.html`). Entry `web-build` of the todo store; the browser side: `tools/web/CLAUDE.md` |

Per-machine settings go in `CMakeUserPresets.json` (git-ignored). Without presets: `cmake -B build -G Ninja -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++`.

**Output goes under the binary dir of the build**: executables and shared libraries in `build/<preset>/bin`, static libraries in `build/<preset>/lib`, so Debug, Release and every other preset sit side by side and nothing needs deleting when you switch presets. A build without a preset gets `<-B dir>/bin`. A multi-config generator (the `windows-vs2022-*` presets) adds the configuration, `build/<preset>/bin/<Config>/`. The old `build/{Compiler}{Platform}/` folders are not written any more and not removed by the build; delete them by hand. A game that carries the engine as a submodule gets `build/<preset>/bin` in its own `build/`; its docs and tools need their own follow-up (Mahjong: entry `mahjong-build-paths`). Switching `BE_WITH_EDITOR` inside one preset still needs the rebuild of "The editor option".

## The editor option

`BE_WITH_EDITOR` decides whether the editor panels (`src/Widgets/{ConfigEditor,EditorLayout,SceneEditor,TextureEditor,Viewport}`) and their tests are built:

- `AUTO` (default): ON except in a single-config `Release` / `RelWithDebInfo` / `MinSizeRel`. A multi-config generator picks sources at configure time, so `AUTO` is ON there.
- `ON`: also in Release (`-DBE_WITH_EDITOR=ON`, or the `*-release-editor` presets). `OFF`: none; **a Debug build ignores `OFF`** with a configure WARNING (except the web presets: no editor there in any configuration).
- Configure prints `Editor: ENABLED|DISABLED`. The definition `BE_WITH_EDITOR=1|0` is on every target (`kEditorBuilt` in `BECore/Application/RunMode.h`); code that needs an editor header is guarded with `#if BE_WITH_EDITOR`. ImGui and `ImGuiWidget` are in every build.
- `mode="Editor"` in a build without the editor starts in Game mode with one warning. With the editor, Ctrl+Shift+E switches modes at run time (`src/Modules/BECore/CLAUDE.md`, "Run mode").

## Web-like build on the desktop

`BagiPlatformOptions.cmake`: `ENGINE_WITH_VULKAN`, `ENGINE_WITH_REMOTE_CONTROL` (ON), `ENGINE_STATIC_SDL`, `ENGINE_SINGLE_THREAD` (OFF); Emscripten forces the first three to the web values (not `ENGINE_SINGLE_THREAD`: its web default OFF is the threaded page, the `web-*-single-thread` presets set it ON) and sets `ENGINE_TARGET_WEB` / `PLATFORM_WEB`. To check the web configuration without emsdk: `cmake -S . -B build/webcheck -G "Visual Studio 17 2022" -A x64 -DENGINE_WITH_VULKAN=OFF -DENGINE_SINGLE_THREAD=ON`, then build `BagiStress BagiEngineTests` with `--config Release`; run it with `ENGINE_SINGLE_THREAD` ON and OFF (the threaded page's task system is the desktop one). It has no preset: the Visual Studio generator writes to `build/webcheck/bin/Release/`, and `build/webcheck` can be deleted after.

## Sanitizers and fuzzing

`BagiFuzz.cmake`: `ENGINE_SANITIZE`, a `;` list of `address` and `undefined` (any other value is a configure error; `thread` and coverage are the entry `build-diagnostic-presets`), puts the sanitizers on every target, vendored code included (Clang or GCC; a configure error on `cl`; on Windows the compiler is clang, and `MSVC` is also true for clang with the MSVC target, so the guard tests the compiler id), with frame pointers, and sets `BE_SANITIZED` for the code after it (the fmt rule below reads it). `undefined` is `-fsanitize=undefined,float-cast-overflow` (a float to integer conversion out of range is not in `undefined`; the engine and the vendored code run the corpus and the fuzzers clean with it) with `-fno-sanitize-recover` on both, so a finding stops the process and fails its test. `ENGINE_FUZZ` is `address;undefined`, the same flags. `ENGINE_FUZZ_LIBFUZZER` (needs `ENGINE_FUZZ`) adds the libFuzzer instrumentation and `be_add_fuzz_executable(<Name> <Function>)`: the executable `BagiFuzz<Name>` over `BECore::Fuzz::<Function>`, all of them under the target `BagiFuzzers` (`tests/Fuzz/CLAUDE.md`). The commands are in `.claude/rules/build-project.md`, "Sanitizers" and "Fuzzing".

- `macos-asan` (hidden mixin `asan`: `ENGINE_SANITIZE=address;undefined`) is the ordinary Debug toolchain, Apple clang, no libFuzzer; asserts and expects stay ON. Its test preset sets `ASAN_OPTIONS` (`detect_stack_use_after_return=1`, `strict_string_checks=1`) and `UBSAN_OPTIONS` (`print_stacktrace=1`); the tests inherit them, and so does the game that `BagiStressControlSmoke` starts. The Apple ASan runtime has **no leak detector** (`detect_leaks=1` prints "not supported on this platform"), so there is no `LSAN_OPTIONS` and no leak finding on macOS.
- **Suppressions are compile-time**: `-fsanitize-ignorelist=cmake/sanitizers/ignorelist.txt`, because the runtime `UBSAN_OPTIONS=suppressions=` is not applied to a build with `-fno-sanitize-recover`. Clang only (Apple clang, LLVM): GCC has no `-fsanitize-ignorelist`, so a GCC sanitizer build gets no ignore list. A line there is a file that a vendored library owns and a check it cannot pass; the file's header says what each entry must state (library, report text, why not fixable here). An engine finding is fixed, never listed. A change to the list rebuilds everything.
- `windows-clang-asan` (not yet run on Windows) is `windows-clang-debug` plus the same `asan` mixin and `asan-windows-crt`: ASan's Windows runtime is the dynamic one and is built for the release CRT, so the Debug build type (asserts and expects ON, no `NDEBUG`) takes `CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreadedDLL`; the debug CRT (`MultiThreadedDebugDLL`) is the one-line change in that mixin if a later runtime supports it. `BagiFuzz.cmake` copies `clang_rt.asan_dynamic*.dll` into `build/<preset>/bin` at configure (an exe without it does not start, `0xc0000135`; a copy, not a `PATH` entry, so the control smoke's child and a double-clicked exe start too). Its test preset sets the same `ASAN_OPTIONS` / `UBSAN_OPTIONS`; no leak detector there either. Whether the ignore list's glob matches the Windows source paths is unverified.
- A game that includes the engine's presets gets `macos-asan` with the same `environment`; `${fileDir}` in a test preset is the folder of the preset file (the engine's), should a later entry need a path there.
- Apple clang has no libFuzzer runtime, so `macos-fuzz` uses Homebrew LLVM. Its hidden mixin `fuzz` holds the compiler paths (`CMAKE_C_COMPILER`, `CMAKE_CXX_COMPILER`: the Intel prefix `/usr/local/opt/llvm` goes into a `CMakeUserPresets.json`), `CMAKE_OSX_SYSROOT=macosx` (that clang has no default SDK), `-L .../lib/c++ -Wl,-rpath,...` (linked against the system libc++ the runtime fails on `std::__1::__hash_memory`) and `-L/usr/local/lib` (Apple's linker searches it by itself for the Vulkan SDK's `libvulkan.dylib`, this clang does not). Asserts and expects stay ON in `macos-fuzz`: an assertion that an input reaches is a finding. `macos-fuzz-shipped` inherits the same mixin and sets Release, `ENGINE_ENABLE_ASSERTS=OFF` and `ENGINE_ENABLE_EXPECTS=OFF` (the flags of a shipped build, where an `ASSERT` compiles out and the code after it meets the bad input); its build folder is its own. Never put Homebrew LLVM on `PATH` for `cmake --preset`.
- Clang 21 and later (Homebrew LLVM 21; emsdk's 22 on the web) refuses `FMT_STRING()` inside the vendored fmt, so with any sanitizer (`BE_SANITIZED`) the `fmt` target is compiled as C++17 (`BagiEngine.cmake`, next to the web case).
